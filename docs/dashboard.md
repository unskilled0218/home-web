# Photo dashboard

The home page `/` shows photos, a clock, weather, and an optional calendar, inspired by the `dash-board` desktop application. `/dashboard`, `/dashboard/`, and `/dashboard.html` redirect to `/`. The former widget canvas and layout editor have been removed. Existing photo-dashboard preferences remain under the browser-local `dashboard.preferences.v1` key on the same origin. Stored integration credentials and former home settings remain in the database; the photo dashboard does not overwrite them.

**Settings** uses five left-side tabs. **General** opens first and contains **Information layout**: desktop lower-left/right position and overall scale. **Time**, **Weather**, and **Calendar** each contain separate **Desktop display** and **Mobile display** visibility/scale controls, editable on any screen. Time's **Shared format** controls timezone, date style, 12/24-hour format, and seconds for both layouts. Weather's **Shared units** controls temperature, wind, and precipitation units for both layouts. Weather location search and the Calendar Baikal connection remain independent of display controls. **Images** contains shared slideshow/background preferences and NFS status. ArrowUp/ArrowDown navigate the tabs; Home/End select the first/last tab. The sidebar stays on the left on mobile, and long panels scroll while Save preferences and Close remain accessible.

At viewport widths up to and including 600px, information starts near the top below the page tools and appears in time → weather → calendar order. Each view uses its own mobile show/hide setting and scale; hidden views leave no empty section. Mobile ignores desktop position, overall scale, and per-view visibility/scale values. Above 600px, the existing bottom-aligned desktop presentation remains calendar → time → weather. Resizing or changing orientation switches the active layout immediately without saving preferences, reloading data, or resetting photo transitions. Vertical scrolling is allowed for tall content; mobile forecast rows wrap to the available width.

The mobile controls default to all three views visible at scale 1, including when an older stored record hides them on desktop. Mobile scales range from 0.5 to 2 in 0.1 increments; stored finite values are clamped and rounded to one decimal place, so 1.25 loads as 1.3. Invalid scales use 1. Both profiles save together through **Save preferences** under the existing browser-local `dashboard.preferences.v1` key and survive reload. Loading missing mobile defaults or switching layouts does not rewrite storage, and unsaved Settings drafts survive tab and viewport changes.

The clock timer follows the active profile's visibility. Weather location discovery and cached snapshot polling continue independently of the weather view's visibility. Calendar events refresh when either saved profile shows the calendar, keeping data available for a layout switch even if the current profile hides it. Hiding calendar in both profiles pauses event retrieval without deleting its connection. Existing document-visibility pause/resume behavior remains in effect; viewport changes do not create additional integration requests or refresh owners.

Switching tabs retains entered values without saving them. **Save preferences** saves display preferences from all five tabs together; invalid fields reveal their tab before reporting the error. Closing and reopening Settings reloads applied preferences. Selecting a weather location saves it immediately on the server for every browser, independently of Save preferences. The Weather tab shows the current saved location. A conflicting save reloads the newer server location and asks you to select again; a failed save preserves the previous location. **Clear results** empties the search results and cancels the current search without changing the selected location, saved preferences, or search text. Calendar connection/disconnection uses the server independently of Save preferences. Date styles use the browser's locale and `Intl` formatting rather than the desktop app's custom format strings. Display preferences remain under `dashboard.preferences.v1` in this browser's localStorage; blocked or corrupt storage falls back to defaults, and save failures are reported without stopping the page. A legacy browser-local weather location is ignored; select a location once to establish the server configuration.

The dashboard automatically loads JPEG, PNG, WebP, and GIF backgrounds from an optional read-only NFS share. It recursively scans up to 5,000 entries and eight directory levels, then accepts up to 100 files, 20 MiB per file, and 200 MiB total. Symbolic links, unsupported files, invalid images, and files outside the configured root are rejected or skipped. Reload `/` after changing the share. Choose name, modification-date, or shuffled ordering; none/fade/slide transitions; interval and transition duration; opacity; a solid or blurred-image background; and optional filename display. Transitions respect reduced-motion preferences, and slideshow timers pause while the page is hidden. If NFS is disabled or unavailable, the page continues with its solid background, clock, weather, and calendar. See [NFS backgrounds](nfs-backgrounds.md) for setup.

Search for a weather location in **Settings → Weather**. Search terms go directly from the browser to [Open-Meteo](https://open-meteo.com/) for geocoding. The server saves the selected label and coordinates in SQLite and uses those coordinates to retrieve current conditions, hourly and daily forecasts, and air quality at startup, after coordinate changes, and hourly even with all browsers closed. The selected location and latest successful weather survive server restarts. Browsers first display the stored snapshot, then request server-managed freshness and poll for updates; they never contact forecast or air-quality providers directly. Failed refreshes label retained data as stale, preserve successful update timestamps, and retry hourly, with forecast and air-quality failures handled independently.

The transparent weather overlay pairs visible condition text with local SVG artwork for current conditions, three-hourly samples of the next 24 hours, and seven daily forecasts; it does not request icons from another service. Hourly icons follow Open-Meteo's day/night flag, while daily icons use daytime variants. The artwork is bundled from the sibling `dash-board` project. The page also shows the **US AQI**, with air-quality data attributed to [CAMS ENSEMBLE](https://ads.atmosphere.copernicus.eu/). **Updated** shows when the server last successfully retrieved the displayed forecast, formatted with a date in the dashboard timezone and 12/24-hour format. It is not the provider observation time; failed refreshes and air-quality-only updates do not advance it.

Temperature, wind, precipitation units, and timezone remain browser-local preferences. The server stores canonical units and retains at most eight timezone-specific forecast snapshots, including UTC, plus one shared AQI snapshot. Each snapshot replaces its previous successful reading rather than accumulating history. Normal browser refresh requests update timezone activity; least-recently-used non-UTC variants can be evicted, and a visible browser re-registers an evicted timezone on its next normal polling cycle. A new or evicted timezone can briefly show no forecast while its first retrieval completes. Browser polls use five-second intervals during server work and sixty-second intervals otherwise, pausing while the page is hidden; server retrieval continues regardless of page visibility. Fresh data and failed attempts waiting for their hourly deadline do not cause extra provider requests. The public provider endpoints and their usage terms still apply. Internet access is needed for geocoding and server weather retrieval.

**Enter fullscreen** uses the browser Fullscreen API and may be unavailable or denied by browser policy. Escape exits fullscreen. The dashboard uses native browser modules without a build step, Tauri, or a runtime dependency on the reference checkout.

See [Baikal calendar](calendar.md) for calendar connection and TLS setup.
