# Photo dashboard

The home page `/` shows photos, a clock, weather, an optional calendar, selected Home Assistant devices, Wake-on-LAN buttons, and Linkwarden bookmarks, inspired by the `dash-board` desktop application. `/dashboard`, `/dashboard/`, and `/dashboard.html` redirect to `/`. All configured Settings preferences belong to one installation-wide SQLite preference record. Firefox, Chrome, fresh profiles, and other connected clients load the same saved values. Integration credentials, managed devices, and former widget settings retain their separate database records.

**Settings** uses eight left-side tabs. **General** opens first and contains **Display on background**, with independent **Desktop** and **Mobile** checkbox groups for Time, Weather, Calendar, Bookmarks, Home Assistant, and Wake-on-LAN. Both profiles are editable on any screen; Mobile applies up to and including 600px. Checkboxes take effect only after **Save preferences** and do not disconnect services or clear selections. **Information layout** sets desktop lower-left/right position and overall scale. **Time**, **Weather**, and **Calendar** retain separate desktop/mobile scales and shared format/units/connection controls. **Bookmarks** contains the nested folder/link picker, Linkwarden connection controls, and fullscreen hiding. **Home Assistant** configures its connection and selects up to 256 dashboard devices; **Wake-on-LAN** manages saved devices. **Images** contains slideshow/background preferences and NFS status. ArrowUp/ArrowDown navigate tabs; Home/End select first/last. Long panels scroll while Save preferences and Close remain accessible.

Above 1000px, enabled groups use information → devices → bookmarks columns. Only visible groups reserve tracks. Both enabled device sections have equal independently scrollable rows; one enabled section uses one row, and disabling both removes the device column. At 1000px and below, enabled sections stack in information → Home Assistant → Wake-on-LAN → bookmarks order. The separate mobile preference breakpoint remains 600px. Short windows may scroll vertically to keep headings and device actions accessible. Disabling all six sections collapses dashboard content without stopping the background. **Images → Show filename** remains independent and can retain the information wrapper; changing or clearing captions updates only DOM layout, not timers or integration requests.

At viewport widths up to and including 600px, information starts near the top below the page tools and appears in time → weather → calendar order. Each view uses its own mobile show/hide setting and scale; hidden views leave no empty section. Mobile ignores desktop position, overall scale, and per-view visibility/scale values. Above 600px, information retains calendar → time → weather order; above 1000px it remains bottom-aligned. Resizing or changing orientation switches the active layout immediately without saving preferences, reloading data, or resetting photo transitions. Vertical scrolling is allowed for tall content; mobile forecast rows wrap to the available width.

These flow rules describe Automatic layout, which remains the default. **General → Widget layout** optionally enables independent custom Desktop/Mobile profiles with free positioning, sizing, overlap, and plain-language layer controls. The editor uses a scaled preview and pixel fields; the live dashboard changes only after Save preferences. Custom cards fit the current usable window, normally at least 100 × 100 pixels, and scroll internally. See [Arrange dashboard widgets](dashboard-layout.md) for selection of covered widgets, cancel/reset, viewport fitting, and shared-save behavior.

All six sections default to visible in both profiles, with mobile information scales at 1. Upgrades preserve existing Time/Weather/Calendar hidden values and default only the new Bookmarks/Home Assistant/Wake-on-LAN flags to visible. Both profiles save together through **Save preferences**, survive reload/restart, and synchronize with revision conflicts. Each browser projects profiles onto its viewport; resizing does not save values. Scale, duration, and opacity match 0.1-step controls; interval and blur use integer steps. Global defaults use UTC.

Visible pages read shared preferences and public integration configuration every five seconds after the previous read settles. Hidden pages pause this synchronization and refresh when visible again. The aggregate read uses local server storage only; it does not fetch provider weather, calendar events, bookmark folders, or photo manifests. Only changed values reconfigure their affected owner, so unchanged polls preserve slideshow order/layers and existing timers. A slow local connection action defers only that service's metadata, keeping other preferences and sources live.

During upgrades, a valid legacy `dashboard.preferences.v1` record can initialize the shared preferences once if no record exists. Competing migration candidates atomically adopt one winner. A fresh browser without legacy values displays server-default preview until a migration or explicit save establishes the record. Once initialized, server values always override stale local preferences. `dashboard.shared-settings.v1` stores only a last-confirmed preference cache for startup outages; it is never used to initialize or replace server settings. Browser storage failure does not disable server persistence. Valid previous-schema server records and shared caches gain empty device selections without changing old values or rewriting records on reads. Already loaded older clients must reload before saving the expanded schema.

The clock timer follows the active profile's visibility. Weather discovery and cached polling continue independently of overlay visibility. Calendar events refresh when either profile shows the calendar; hiding both pauses events without deleting the connection. Home Assistant selected snapshots, saved device metadata, and selected/loaded bookmark content retain their existing bounded refresh owners even with overlays hidden. Settings can still configure hidden services. Existing document-visibility pause/resume remains in effect; no checkbox adds an owner or cancels a submitted Wake action.

Switching tabs retains entered values without saving them. **Save preferences** writes display preferences and Home Assistant selections atomically and reports **Preferences saved for all browsers.** only after confirmation; it does not submit integration forms. Invalid fields reveal their tab before reporting the error. Remote changes update the active dashboard behind an open dialog without replacing dirty drafts or their captured revision; pristine drafts adopt new confirmed values together with their revision. A stale save reports a conflict; **Reload shared preferences** explicitly reloads the latest display values and selections before you reapply edits, preserving separate credential/search drafts. Failed saves retain the prior confirmed settings and your form; no local-only success is reported. Closing/reopening discards unsaved display and selection drafts as before.

Home Assistant connection and Wake-on-LAN device actions save independently of **Save preferences**. Their shared server state is read immediately when Settings opens and polled every five seconds while the page is visible. Each service reads independently; a slow or unavailable service does not delay the other. Closing Settings keeps dashboard reads active; hiding the page pauses reads and resuming starts fresh reads. Propagation includes request latency and can be delayed by a pending mutation or an outage. Last confirmed state remains visible on read failure rather than pretending the configuration was removed. Home Assistant device snapshots use a separate 30-second cache-friendly loop only while selected devices exist or the picker is open. Display-only reads issue no control tokens.

These two forms preserve drafts during polling, including remote device changes. An edited device changed by another browser shows a warning; cancel and select Edit again to reload, or explicitly save your draft. Remote deletion keeps the draft without silently creating another device. Their APIs use last-successful-write semantics, not the revision conflicts used for display preferences; opaque Home Assistant configuration identity distinguishes committed credential changes without returning secrets. Affected fields are disabled during a pending action, but unrelated preferences and Close remain usable. Results from an earlier dialog session cannot clear newer drafts or move their focus. Closing clears unsent Home Assistant token input; it does not cancel or roll back an already submitted save. A timeout is an uncertain result: check saved status before retrying.

Weather location and calendar/Linkwarden connection actions remain independently server-owned and propagate through the same public configuration channel, including to initially unconfigured browsers. Tokens and passwords remain in encrypted server storage, never in preferences or their cache. Unknown/unavailable service metadata preserves the current service snapshot instead of pretending it disconnected. A local request timeout cannot prove a server operation failed to commit; subsequent status reads reconcile its result. **Clear results** remains limited to weather search results/query-related status. Date styles still use the browser's locale and `Intl`; the configured timezone and format options are global, while actual fullscreen entry, folder disclosure, and unsaved drafts remain session interactions.

Selected Linkwarden links appear as a flat list without parent folders, in a right-side desktop column or stacked page flow. Settings retains nested folders and individual link checkboxes; its disclosure is session state. The old mobile Compact/Expanded preference remains stored for compatibility, without a display control or effect on the flat list. **Hide bookmarks in fullscreen** defaults to off and combines with the active profile's checkbox. Exiting fullscreen never restores unchecked bookmarks. Display-only saves preserve photos and existing integration owners. See [Linkwarden bookmarks](linkwarden.md) for catalog behavior.

The dashboard automatically loads JPEG, PNG, WebP, and GIF backgrounds from an optional read-only NFS share. It recursively scans up to 5,000 entries and eight directory levels, then accepts up to 100 files, 20 MiB per file, and 200 MiB total. Symbolic links, unsupported files, invalid images, and files outside the configured root are rejected or skipped. Reload `/` after changing the share. Choose name, modification-date, or shuffled ordering; none/fade/slide transitions; interval and transition duration; opacity; a solid or blurred-image background; and optional filename display. Transitions respect reduced-motion preferences, and slideshow timers pause while the page is hidden. If NFS is disabled or unavailable, the page continues with its solid background, clock, weather, and calendar. See [NFS backgrounds](nfs-backgrounds.md) for setup.

Search for a weather location in **Settings → Weather**. Search terms go directly from the browser to [Open-Meteo](https://open-meteo.com/) for geocoding. The server saves the selected label and coordinates in SQLite and uses those coordinates to retrieve current conditions, hourly and daily forecasts, and air quality at startup, after coordinate changes, and hourly even with all browsers closed. The selected location and latest successful weather survive server restarts. Browsers first display the stored snapshot, then request server-managed freshness and poll for updates; they never contact forecast or air-quality providers directly. Failed refreshes label retained data as stale, preserve successful update timestamps, and retry hourly, with forecast and air-quality failures handled independently.

The transparent weather overlay pairs visible condition text with local SVG artwork for current conditions, three-hourly samples of the next 24 hours, and seven daily forecasts; it does not request icons from another service. Hourly icons follow Open-Meteo's day/night flag, while daily icons use daytime variants. The artwork is bundled from the sibling `dash-board` project. The page also shows the **US AQI**, with air-quality data attributed to [CAMS ENSEMBLE](https://ads.atmosphere.copernicus.eu/). **Updated** shows when the server last successfully retrieved the displayed forecast, formatted with a date in the dashboard timezone and 12/24-hour format. It is not the provider observation time; failed refreshes and air-quality-only updates do not advance it.

Temperature, wind, precipitation units, and timezone are global preferences. The server stores canonical units and retains at most eight timezone-specific forecast snapshots, including UTC, plus one shared AQI snapshot. Each snapshot replaces its previous successful reading rather than accumulating history. A changed global location revision prompts a cached snapshot read in other browsers; unit/time-format changes update presentation without another provider refresh. Weather content still polls every five seconds during server work and sixty seconds otherwise, separately from the provider-free settings channel. Server retrieval continues while pages are hidden. The public provider endpoints and usage terms still apply.

**Enter fullscreen** uses the browser Fullscreen API and may be unavailable or denied by browser policy. Escape exits fullscreen. Immersive fullscreen normally hides page tools, but when no effective dashboard sections remain visible, **Settings** and **Exit fullscreen** stay reachable, including caption-only pages and bookmark-only pages with fullscreen hiding enabled. The dashboard uses native browser modules without a build step, Tauri, or a runtime dependency on the reference checkout.
