# plan

## scope

Implement the updated goal: make `.env` the normal setup surface for Compose/direct/development launches; bootstrap a persistent shared integration key on first server start; and use `HOME_ASSISTANT_CA_FILE` consistently without requiring `NODE_EXTRA_CA_CERTS` for Home Assistant. Preserve explicit overrides, existing keys/encrypted records, container networking/privileges, NFS safety, TLS verification, and lifecycle ownership. No implementation, `.env`, key, user-data, runtime process, dependency, or version change is performed in this planning stage.

## Current Boundaries

- Compose currently enumerates application variables in `environment`, fixes database/key paths under `/app/data`, binds certs at `/app/certs` and photos at `/photos`, and maps `HOME_ASSISTANT_CA_FILE` into the process-global Node CA setting. `.env.example` mixes local paths, Compose-only values, and direct mount options.
- `npm start`/`start:lan` use Node's optional env-file flag. `scripts/dev-supervisor.js:13-17` uses Node's `parseEnv()` for a fresh child-only environment, with inherited values winning. The supervisor watches `.env`, but never mutates its original environment or watches data writes.
- `src/config.js:54-77` exports configuration on import and calls `resolveLinkwardenEncryptionKey()` during parsing. That performs file I/O only when a key-file path is supplied; no-path direct startup leaves encryption unavailable. `src/linkwarden-key.js` uses random 32-byte keys, `wx` creation/mode `0600`, and an EEXIST winner read, but does not create parents or validate explicit secrets immediately.
- `src/server.js` validates CA files, opens/attaches SQLite, constructs integration clients, prepares NFS, then listens. `src/db.js` creates database parents. Linkwarden/Home Assistant/CalDAV records share the legacy-named encryption key and retain separate encrypted configuration records.
- Home Assistant uses native WebSocket sessions for both registry snapshots and service calls, with injected factories for tests. Its current trust/error guidance depends on `NODE_EXTRA_CA_CERTS`; `src/ca-file.js` already validates certificate-only PEM bundles and extends default roots for scoped clients.
- The package has no runtime dependencies and the Dockerfile performs no npm installation. A scoped WebSocket dispatcher is not currently available as an application dependency. Node 24's WebSocket supports dispatcher-based configuration, but Node's bundled implementation is not a supported importable Agent API; do not import internal Node modules or implement a homegrown WebSocket/TLS transport.

## Implementation Plan

Keep only deliberate topology/path overrides in `environment`. Require the documented `cp .env.example .env` setup for Compose rather than relying on silent missing-file behavior or a new Compose-version-specific optional syntax.
- Keep image selection as Compose interpolation (`HOME_WEB_IMAGE`), host networking unchanged, writable `./data`, read-only `./certs`, and the read-only `${NFS_HOST_MOUNT_PATH:-./photos}` bind. Keep container database default `/app/data/wol.db` and NFS root `/photos` authoritative; host-only bind paths must never become application roots accidentally. Keep the key file under persistent `/app/data` by default, while an explicitly configured key-file override uses a documented container-visible path. Do not bake `.env`/keys/certificates into the image.
- Preserve the precedence boundaries explicitly: direct Node inherited environment wins over native `.env`, then application defaults; development inherits overrides and recomputes file values for every child; Compose's explicit `environment` path overrides win over `env_file`, which wins over image/application defaults. Shell values affect Compose interpolation, not arbitrary `env_file` values automatically; document selected overrides through a Compose override file or `docker compose run -e` rather than promising every inline shell variable still overrides the env-file runtime value.
- `.env.example` keeps ordinary settings/defaults and concise comments for Compose-only host paths versus direct paths. Make the explicit encryption secret optional/blank and automatic key path the default. Remove Home Assistant's Node-CA instructions. Preserve optional direct NFS settings while clearly stating that Compose supports host-mounted existing/disabled mode, not managed privileged mounting. Do not add NFS capabilities or change its safe default.
- Keep direct Node env-file loading and the supervisor's native parser; no dotenv package or custom shell sourcing. Plain `node src/server.js` continues to use supplied process values/defaults, whereas documented direct commands include the native env-file flag. Preserve inherited generic Node options without presenting `NODE_EXTRA_CA_CERTS` as the Home Assistant configuration interface.

### 2. Make configuration pure and choose a stable automatic key path

- Refactor `loadConfig()`/the exported `config` to validate and project values only. Remove key-file reads/writes and random generation from module import/config inspection. Project explicit key material and a resolved key-file path separately; validate a nonempty explicit secret with `encryptionKey()` without logging it. Keep the legacy variable names and complete runtime secret contract for consumers after startup initialization.
- Default the key file to `linkwarden-config-encryption.key` beside the resolved database file when the path setting is omitted or blank. - Retain a supplied external secret as the highest-priority source: validate it and do not read/create/modify a key file or its directories. A genuinely absent file can be created only through the startup bootstrap path described below.
- Introduce a small startup-only initialization boundary in the current key module, not a new settings owner/service. Unit/config tests can call pure configuration without touching a real data directory. Update fixtures that previously imported config expecting filesystem side effects to exercise actual startup or the explicit initializer instead.

### 3. Bootstrap keys safely during owned server startup

- In `src/server.js`, validate all configured CA bundles and ordinary configuration before initializing integration clients/listening. Initialize key storage only in the owned startup path, with stopping checks before new resource work. Create required new data/key parent directories with restrictive mode `0700` when owned by this startup; never chmod/chown existing directories/files. Open/attach the store through its current lifecycle ownership before later fallible work, and construct the final runtime configuration with the resolved secret only after initialization succeeds.
- Use existing safe storage getters, or a narrowly scoped store query if needed, to detect saved encrypted integration records before generating a missing file. If ciphertext already exists and there is neither an explicit secret nor a readable persisted key, stop with a sanitized restore-key/configure-original-secret error. Do not silently generate a new key for an existing encrypted installation, delete/reconnect services, migrate ciphertext to a random replacement, or attempt recovery without the original secret. Existing non-credential data alone does not block first-time generation.
- Reuse a valid existing key byte-for-byte; no regeneration, truncation, rewrite, ownership change, or exposure in logs/APIs/preferences/cache. Key-file read failure, invalid/empty content, invalid explicit secret, unwritable parents, and publication failure must fail startup nonzero without reaching readiness or advertising encryption as configured.
- Preserve cryptographic 32-byte random generation, canonical base64 validation, final file mode `0600`, and exclusive race-winner semantics. Avoid publishing a partially written key: write a complete restricted owned temporary file in the target directory, close it, and atomically publish through an exclusive same-filesystem operation (for example, a hard link that fails with EEXIST). A loser discards only its owned temporary file and validates the completed persisted winner. Never overwrite the final path, fall back to an ephemeral key, or delete a winner. Handle publication/cleanup errors honestly; unsupported exclusive-publication filesystems fail with actionable guidance rather than unsafe replacement.
- Test actual concurrent initializers rather than assuming an exclusive `writeFile()` makes winner contents fully visible before an EEXIST read. Keep races with an existing file safe and preserve bytes on every invalid-file path. No broader file-permission normalization or secret rotation mechanism is added.
- Keep SQLite closure after admitted-handler drainage, NFS preparation ownership, and supervisor readiness/failure semantics intact. Bootstrap failure must clean only owned resources; key creation after successful initialization is persistent and is not rolled back merely because another startup stage fails.

## Acceptance Criteria

- A documented `.env` setup followed by ordinary Compose/direct/dev commands supplies supported application settings, with accurate precedence and container-visible paths; no repeated inline configuration or manual default key generation is required.
- Pure configuration inspection has no filesystem/random-key side effects. Server startup chooses a persistent database-adjacent default key, creates required owned storage securely, reuses completed winner/existing keys, and preserves encrypted credentials across restart/recreation. Explicit secrets/file paths remain authoritative.
- Missing key material for an encrypted installation, corrupt/unreadable keys, and persistence failures stop startup safely without replacement, ephemeral success, secret exposure, or lost user state.
- `HOME_ASSISTANT_CA_FILE` works in both direct and Compose paths, grants trust only to the Home Assistant client, and preserves public/default roots plus hostname/certificate verification. No HA user configuration through `NODE_EXTRA_CA_CERTS` or process-global trust mutation is required.
- Scoped transport resources are owned and drained/disposed safely on shutdown/startup failure; injected factories remain caller-owned. Image dependencies install reproducibly at build time, never at server startup.
- A clean `npm ci --omit=dev` artifact resolves its own Undici dependency without developer/global fallbacks, excludes development/browser packages, and reaches actual server readiness with isolated storage before confirmed IPC shutdown. If prerequisites block this check, packaging remains explicitly unverified; static assertions and developer-tree success must not be reported as an equivalent pass. Built-image verification is recorded separately when performed.
- Focused/full tests and available Compose wiring checks are recorded with honest limitations. All development fixtures remain isolated from actual user `.env`, keys, databases, certs, mounts, and service processes.

## Risks And Decisions

- Compose's `.env` interpolation and `env_file` runtime injection have different shell precedence. Simplification must explicitly document that difference and test fixed paths; do not silently promise the old inline forwarding semantics for every setting.
- Native Node extra-CA loading is process-start-sensitive. Scoped loading through `HOME_ASSISTANT_CA_FILE` deliberately removes that dependency for Home Assistant while retaining normal env-file precedence/restart behavior. An explicit supported dispatcher dependency is preferable to global TLS mutation or undocumented Node internals.
- Adding Undici changes the previously dependency-free runtime/image contract. Build-time npm installation, documentation, lockfile, transport disposal, and release tests are necessary coordinated changes, not unrelated infrastructure work.
- The developer install can conceal a missing or misclassified production dependency. The clean-artifact smoke must not inherit developer modules, real application settings, or user storage. Registry/tooling failures may block packaging verification even when functional tests pass; report that distinction rather than weakening the smoke or modifying the user's services.
- Exclusive direct writes can expose incomplete winner contents to a competing read. Publish complete key bytes atomically and exclusively; never exchange a race for silent rotation or memory-only keys. Unsupported persistence primitives fail safely rather than inventing a fallback that violates the guarantee.
- Automatic defaults must not rotate a lost key for a database containing credentials. Detect that case in owned startup, and preserve the existing key filename for the standard data directory. Key-path overrides or database relocation remain explicit operator migrations.
- This task changes only the resource handling needed for key initialization/scoped TLS. Archived shutdown, bookmark membership, caption-request, and NFS guard findings remain out of scope. Do not touch `todo.md`.
