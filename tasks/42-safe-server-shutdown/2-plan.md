## Current Structure And Evidence

- `package.json` runs `dev` through `node --watch --env-file-if-exists=.env src/server.js`. The reported assertion is in Node's watch supervisor (`node:internal/watch_mode`, `FSWatcher.close`, `FSEventWrap`), not an application watcher. An application signal handler cannot repair that supervisor's native teardown.
- `src/server.js` installs SIGINT/SIGTERM handlers only after CA loading, SQLite creation, asynchronous NFS preparation, weather startup, and `server.listen()`. Its current shutdown waits for `server.close()` and `weather.stop()`, then closes SQLite and calls `process.exit(0)`. There is no overall deadline or rejection handler, and signals during asynchronous startup bypass this lifecycle.
- `src/weather.js:161-164` already stops scheduling, clears queued jobs, aborts the active provider request, and awaits its draining promise. Reuse this behavior rather than writing another weather shutdown owner.
- `src/app.js` returns an HTTP server and launches each request handler through an asynchronous promise without exposing handler-drain state. Closing TCP connections does not prove those promises, queued integration mutations, or store accesses have settled. `readJson()` can wait for an unfinished request body until its connection is closed.
- Existing Home Assistant/Linkwarden/CalDAV requests have bounded transport work, but integration mutation queues can outlast an individual timeout. `src/nfs.js` also awaits preparation and may start a mount subprocess under the existing optional configuration. No new mount/unmount behavior belongs to this task.
- `test/env.test.js` and `e2e/server-setup.js` already use an IPC-owned wrapper that emits SIGTERM inside the child. Their comments explicitly distinguish this from permission to deliver an OS signal.
- Read-only runtime diagnostics found Node `v24.21.0`, npm `11.19.0`, `/usr/bin/node`, Linux, and UID/GID 1000. A disposable owned child with an error listener and a self-exit fallback confirmed that `child.kill('SIGINT')` emits `EACCES` and returns false; sending shutdown through IPC instead produced exit code 0. No native watch supervisor, real server, user database, or existing listener was stopped for this probe.
- The installed `/usr/lib/node_modules/npm/node_modules/@npmcli/run-script/lib/signal-manager.js:12-15` forwards SIGINT/SIGTERM by calling `proc.kill(signal)`. This is a separate permission-sensitive layer outside project code. Replacing Node watch mode alone cannot guarantee that npm will stop printing its forwarding error under the current policy.
- `Dockerfile` runs `node src/server.js` directly and copies `src/` and `public/`, not development scripts. Keep production image entry and packaging unchanged unless a narrowly justified lifecycle change requires otherwise.

## Implementation Plan

### 1. Establish the failure boundaries before changing launch behavior

- Record the runtime/npm versions and the above owned-child signal/IPC evidence in `4-implemented.md`. Inspect the current process hierarchy for controlled launches only; do not inspect secrets, signal user processes, or reproduce the known native crash against the live project checkout.
- Treat three layers independently: application resource shutdown, Node's built-in watch supervisor, and npm's signal forwarding. Existing IPC tests prove application handlers, not terminal Ctrl+C or OS signal permissions.
- Use the no-native-watcher supervisor below as the default project-level remedy. Do not patch global npm, modify installed Node internals, suppress stderr, disable core dumps, or weaken the container policy.
- Keep `npm run dev` as the conventional alias for the new supervisor. Also document `node scripts/dev.js` as the supported development command in environments that deny npm's signal forwarding. Normal runs have the equivalent direct command `node --env-file-if-exists=.env src/server.js` when npm is unsuitable.
- State the npm limitation explicitly: clean `npm run dev` Ctrl+C in this specific restricted environment is not an application-only guarantee. If forwarding still emits EACCES, record that acceptance gap and the operator prerequisite of allowing ordinary signal delivery to owned processes through the existing environment policy, or using the direct launcher. Do not invent a minimum Node/npm upgrade version without evidence that it fixes the problem. No privilege changes are executed by implementation.

### 2. Add one application shutdown coordinator

- Add `src/shutdown.js` with a small explicit coordinator for this application, not a generic hook/plugin framework. Its states cover startup, running, stopping, and stopped; its shutdown method returns one shared promise. Inject clock/timers, reporting, and final termination at the test boundary so deadlines and failures are deterministic.
- Install SIGINT/SIGTERM ownership at the beginning of the `src/server.js` bootstrap, before asynchronous startup. Load side-effectful configuration after the lifecycle is installed, using dynamic import where needed; do not broadly rewrite `src/config.js` or key persistence. Track constructed store, weather, and server resources explicitly and check the stopping flag after each asynchronous startup phase.
- Once shutdown begins, prohibit weather startup, a later listen callback, or a new listener after interrupted initialization. Await or cancel owned startup work where its API supports cancellation, using existing NFS preparation bounds rather than performing new privileged mount actions. Cleanup operates only on resources actually created and only after startup can no longer add another resource.
- Normal shutdown closes admission immediately, starts weather cancellation, and drains admitted HTTP-handler work in parallel. Use a five-second connection grace period followed by destruction of only this server's remaining connections. Use one 30-second overall shutdown deadline, including startup settlement and request draining. Keep these as named constants, not a new configuration surface unless deployment evidence requires it.
- Close SQLite exactly once, only after startup, weather drainage, and tracked store-using HTTP handlers have settled. A closed listener or destroyed socket alone is not enough to establish that invariant. Do not close the store beneath queued integration mutation work.
- Catch and classify shutdown/cleanup failures. Continue safe independent cleanup without skipping other owners when one cleanup fails. A normal cooperative interruption exits 0; startup/runtime/cleanup failures remain nonzero. Repeated signals join the same shutdown rather than closing the store twice or restarting the process.
- At the overall deadline, report a concise forced-shutdown diagnostic and terminate this application process with a nonzero status. Do not manually close SQLite while unsettled handlers could still use it; process termination closes OS resources without running later application callbacks. Preserve already committed SQLite data and do not claim that interrupted operations completed.
- Keep final process termination in the entrypoint's lifecycle owner, with the cleanup logic itself testable independently. Remove registered listeners/deadline timers during completed disposal; retain an active deadline capable of ending a stalled shutdown.

### 3. Track HTTP request work without changing API behavior

- Refactor only the outer request-dispatch boundary in `src/app.js` to register each admitted handler promise in a Set and remove it in `finally`. Preserve current host/origin checks, route handlers, error responses, and safe diagnostics.
- Add a narrow server lifecycle interface for closing admission and awaiting active handlers, using the returned server object or an explicit attached lifecycle object. Register the handler before its first awaited work. Work queued inside a handler remains covered until that handler's promise settles.
- Once shutdown starts, reject any newly dispatched keep-alive request without invoking store-dependent API logic. Call `server.close()` and close idle connections; at the connection grace deadline destroy the remaining owned HTTP sockets so incomplete body reads and stalled responses can settle. Do not use process-wide socket cleanup.
- Ensure static/photo response streams are canceled through their socket/pipeline ownership when connections close. If a handler continues an integration call after socket closure, keep it tracked until completion or the overall process deadline; no new cancellation protocol across every provider is required for this task.
- Make close-before-listen and listen-failure handling explicit. Startup errors must clean any already-created resources and retain a failure status rather than being converted into a normal stop. Test that queued handlers cannot touch a closed store and that shutdown does not accept another mutation.

### 4. Replace native watch mode with a polling development supervisor

- Add `scripts/dev.js`, plus a small `scripts/dev-supervisor.js` module if separation is needed for tests. Use native Node modules only. Change `package.json`'s dev command to `node scripts/dev.js`; do not add nodemon, a runtime package installation step, or an OS file-watcher dependency.
- Watch a fixed project-root scope using asynchronous filesystem metadata polling, not `fs.watch()`, `fs.watchFile()` watcher teardown, or `node --watch`. Include server `.js` sources under `src/`, `.js` files under `public/` that include server-shared helpers/data, repository-root `.env`, and `package.json`. Exclude `.git`, `node_modules`, data/database files, logs, core artifacts, tests, tasks, and build outputs. Enumerate additions/removals and compare metadata including high-resolution modification/change times and size.
- Poll at a named 500ms interval with at most one scan in flight. Coalesce editor save bursts into one pending restart, including changes observed during child startup or shutdown. Missing `.env` is valid; permission or enumeration failures must produce actionable diagnostics rather than silently disabling reloads or starting a crash loop.
- Spawn exactly one direct child using `process.execPath`, `--env-file-if-exists=.env`, and the absolute `src/server.js` entry, with project-root working directory and an IPC channel. Do not spawn through a shell. Inherit the original process environment and normal output; keep child ownership and exit/error listeners explicit.
- Do not load `.env` into the supervisor's environment. Let each new server child load it natively before startup, so changed `.env` values and `NODE_EXTRA_CA_CERTS` take effect after reload and do not become accidentally pinned as parent-environment overrides. Existing externally supplied environment values still win.
- Restart only after the previous child has completed shutdown and exited. Use IPC shutdown as the primary mechanism, not `child.kill()`, because the current environment denies owned-child signals. The application entrypoint recognizes a narrow supervisor shutdown message and IPC disconnect only when launched with an IPC channel; these join the same signal-triggered shutdown coordinator. Do not expose a browser/HTTP shutdown endpoint.
- SIGINT/SIGTERM received by the supervisor must first stop polling, invalidate late scans, clear pending restarts, and request child shutdown. Terminal process-group delivery may signal both supervisor and child; both sides must be idempotent and tolerate a child that is already exiting or whose channel has closed. An IPC callback error is not permission to launch a replacement child.
- On IPC disconnect, the child cooperatively shuts itself down even if its owner has disappeared. The supervisor waits for owned-child exit/output closure before finishing. A requested reload starts a replacement only after a clean old-child stop; a requested final stop never does. Unexpected child startup/runtime failure or failed shutdown ends the supervisor with a meaningful nonzero result rather than automatically respawning forever.
- Add a supervisor wait deadline slightly above the child's 30-second deadline, for example 35 seconds. Any optional OS-signal escalation targets only the tracked child, handles both a false kill return and the emitted `error` event, and is used only where permitted. If IPC fails and the environment also forbids termination of an unresponsive child, stop scheduling replacements and report the inability to guarantee cleanup as an operator-level blocker; do not silently exit successfully or claim no orphan remains.
- Keep the supervisor out of production Docker entrypoints. Public asset changes remain available through existing static serving and normal browser reloads; this task does not add live-browser reload or a second HTTP server.

## Acceptance Criteria

- The supported direct development launcher performs automatic reloads without Node's native watch supervisor, maintains one child, and stops through cooperative signals/IPC without a watcher assertion, segmentation fault, or new core artifact.
- Successful normal/development stops release the listening port and all owned children, cancel restart intent, preserve committed data, and close SQLite only after store-using work has settled.
- Repeated signals, interruption during startup/reload, stalled connections, and cleanup failures have deterministic bounded behavior and meaningful exit status. Forced termination is reported as a failure, not disguised as a successful graceful stop.
- Every replacement child reloads optional `.env` before Node initializes TLS, while externally supplied environment values retain precedence. Native env loading and LAN protections remain intact for start/start:lan and production Docker runs.
- SIGINT/SIGTERM and terminal Ctrl+C results are verified separately from self-emitted signals where the environment supports them. The known npm forwarding restriction is not claimed fixed by project code; any remaining npm-specific acceptance gap and exact operator prerequisite are explicitly recorded.
- Existing tests pass, new lifecycle/reload tests cover the stated edge cases, and no live service, user core/log artifact, system package, container privilege, dashboard UI, or `todo.md` is changed by verification.

## Risks And Decisions

- Native watcher teardown and denied kill syscalls are independent. Polling removes the former dependency; IPC avoids denied signals between owned supervisor/server processes. Neither changes npm's external signal-forwarding implementation.
- An npm script cannot grant permission its parent lacks. The direct launcher is the project-controlled fallback; guaranteeing silent npm Ctrl+C under the current policy remains conditional on an operator-controlled prerequisite. Treat this as a documented acceptance constraint, not a hidden successful test skip.
- HTTP socket closure does not drain asynchronous request work. Track handlers before closing SQLite; at a forced process deadline, do not close it while callbacks remain runnable.
- Startup shutdown must prevent late resource creation and listening. Static imports with side effects and optional NFS subprocess preparation need explicit sequencing; do not add broad infrastructure cancellation or mounting behavior to solve a watcher bug.
- Polling uses small, explicit source scopes and a single owner. Database/weather writes must not create restart loops, and child shutdown must complete before a replacement can bind the port.
- Loading `.env` into the supervisor would turn those values into explicit child environment overrides and defeat reloads. Keep env-file loading in each server child's Node startup.
- No JavaScript supervisor can guarantee termination of a native/event-loop-frozen child when the environment also rejects OS signals. Report that condition truthfully and do not orphan a process while claiming cleanup succeeded.
- Tests must not recreate the reported crash in the actual checkout or rely on permission to kill arbitrary processes. Signal probes use disposable cooperative children only.
