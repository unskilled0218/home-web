## Outcome

Implemented narrow Gitea `28.2.0` package-link compatibility on branch `70-server-package-link-compatibility`, version `0.17.39`. The new path requires matching version and Gitea API schema metadata, backed by exact upstream source inspection rather than merely allowing a new version string. Stable Gitea `1.25.x` behavior, read-only correct links, exact association identities, early readiness, refreshed final evidence, and one-POST reconciliation remain unchanged. The real isolated local verifier passed, including all application/release tests and production packaging. No live package association or publication was attempted.

## Server identity and source evidence

- Read-only unauthenticated public observations at `https://git.lan`: `/api/v1/version` returned `{"version":"28.2.0"}`; `/` identified Gitea through page metadata, upstream product links, and footer version; `/api/swagger` identified the Gitea API; `/swagger.v1.json` returned `info.title = "Gitea API"` and `info.version = "28.2.0"`, with the package link route and empty HTTP 201 response. The schema measured 951547 bytes, below the existing 4 MiB limit. `/api/forgejo/v1/version` returned 404, which is corroborating context only, not independently sufficient product identification.
- Upstream [tag lookup](https://api.github.com/repos/go-gitea/gitea/git/ref/tags/v28.2.0) resolved annotated tag object `1dc1ecdddcdc60ab14ec14e30e7bb4d84242f21f` to commit `829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1`. GitHub reports the tag signature key as unknown; no cryptographic signature verification or binary attestation is claimed. The immutable source links below are the inspected association contract for this exact upstream release.
- [Version endpoint](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/routers/api/v1/misc/version.go): `Version()` returns `setting.AppVer` in the standard version record. [Route registration](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/routers/api/v1/api.go), lines 1752–1772, requires a token, package token scopes, package read access, and package write access for the link POST. [Package context](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/services/context/package.go) resolves owner and package access; an association cannot be granted solely by knowing the route.
- [Package handler](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/routers/api/v1/packages/package.go): `GetPackage()` uses `convert.ToPackage()`; `LinkPackage()` loads package and repository under `ctx.ContextUser.ID`, calls `LinkToRepository()`, maps invalid arguments to HTTP 400 and permission denial to HTTP 403, and returns empty HTTP 201 on success. Missing package/repository is HTTP 404. The client still uses the configured image package name and configured repository name as distinct route values.
- [Converter](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/services/convert/package.go): `ToPackage()` includes the repository only when the caller has any unit access; inaccessible associations can appear as null. It returns version ID, owner, package type/name, and version, matching the existing exact-identity checks. Null is not proof of no stored association.
- [Association service](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/services/packages/package_update.go), lines 20–39: `LinkToRepository()` rejects owner mismatch, rejects any stored positive `pkg.RepoID`, requires `CanWrite(unit.TypePackages)` on the target, then calls `SetRepositoryLink()`. The positive-association guard applies before filtered API serialization and protects hidden foreign links under writer exclusion.
- [Model update](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/models/packages/package.go): `SetRepositoryLink()` updates `repo_id` by package ID without a compare-and-set predicate. There is no claim of atomic protection against concurrent writers; all writers and in-flight requests must remain excluded as required by the existing release contract. Lost transport responses do not change the persisted state; the client must reconcile once by exact readback, never replay POST.
- Existing support comparison: upstream Gitea `v1.25.0` resolves to commit `cf644d565d09d1592526919f7eabbb683f5d83ae`; its [LinkToRepository service](https://github.com/go-gitea/gitea/blob/cf644d565d09d1592526919f7eabbb683f5d83ae/services/packages/package_update.go) has the same matching-owner, stored-positive-link refusal, packages-write permission, and model-update sequence. Established stable `1.25.x` policy is preserved, not broadened to unrelated versions.

## Changes

- `scripts/release-data.py::supported_link_server()` retains the existing stable `1.25.x` path and adds only exact `28.2.0` with fresh `/swagger.v1.json` Gitea title/version evidence from the same configured HTTPS origin. It reuses bounded authenticated HTTP helpers and does not introduce a discovery subprocess, new configuration field, force option, persistent authority cache, or fabricated product field. Error text names the supported policy and directs identity/compatibility inspection without echoing raw remote values.
- Both readiness and final association use the shared boundary. Exact existing links still return before discovery, including on unsupported versions. Missing/unlinked readiness still precedes staging writes; final association still requires explicit package evidence, refreshed identities, one POST, and fresh exact readback. HTTP refusal never enters transport-loss reconciliation. No unlink, reassignment, rollback, or unrelated mutation is added.
- Fake HTTP ports now expose the observed schema metadata and existing fault-injection machinery for discovery. The stored-link rejection is documented against both inspected Gitea services; they share this contract, so no speculative product hierarchy or duplicate fake mutation algorithm was added. GET hiding and stored association remain distinct fixture state.
- Added four helper test methods and two owned-publication methods, and updated the two earlier readiness scenarios. Cases cover strict exact-release discovery, mismatched products/versions, malformed/failed responses, unverified patches/prereleases/custom suffixes, empty 201, uncertain transport, exact readback, explicit refusal, fresh absent/unlinked packages, completed read-only retries without discovery, and hidden foreign-link refusal with foreign/unrelated sentinels preserved. Existing Gitea and association fault coverage remains in place.
- Updated README, release operations, testing docs, versioned notes, and all version mirrors. Documented pinned source evidence, required permissions, null/hidden associations, trusted metadata limitations, non-atomic updates, writer exclusion, and unchanged reconciliation. Dependency resolutions and deployment behavior are unchanged.

## Limits and inherited findings

- Public metadata and exact upstream source establish the supported compatibility contract; they do not cryptographically attest the deployed binary or guarantee that a fork copying those fields preserves the implementation. Operators must not claim patched/forked behavior is verified from copied metadata. No independent real server instance was installed or mutated; fixtures test client behavior, not live server execution.
- Writer exclusion remains an operator prerequisite, including in-flight requests, other checkouts, registry/UI writers, and association writers. The checkout lock is not distributed locking, and the inspected model update is not compare-and-set. Discovery does not replace final identity refresh or readback.
- No live no-argument release, publisher token-file read, package link/unlink/reassignment, remote Git write, build/push/runtime probe, server downgrade, privileged setup, or emulation installation occurred. Public metadata and version inventory GETs are not release execution certification. Actual ARM64 support remains separate operator work.
- Task 69's regular-file offset and suppressed-heartbeat warnings and task 67's inherited cleanup sequencing, ambient Node probe environment, and persistent real-`local()` regression-coverage findings remain separate. This task neither repairs nor waives them. Existing tests and current verifier execution do not certify those broader issues as resolved. Archived tasks and `todo.md` are unchanged.
