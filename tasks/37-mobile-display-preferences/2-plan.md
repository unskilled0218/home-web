# plan

## scope

Implement the top-aligned mobile order and independent time, weather, and calendar visibility/scale preferences in `1-goal.md`. Use the active photo dashboard, its existing five Settings tabs, and browser-local `dashboard.preferences.v1` storage. The responsive boundary remains `(max-width: 600px)`. The main integration points are `public/dashboard-helpers.js`, `public/dashboard.js`, `public/dashboard.css`, and `public/index.html`; verification belongs in the existing dashboard Node and Chromium checks, and user instructions in `docs/dashboard.md`.

## Implementation Plan

### 1. Normalize independent mobile preferences and resolve active presentation

- Add six flat preference fields in `normalizeSettings` in `public/dashboard-helpers.js`: `mobileTimeVisible`, `mobileTimeScale`, `mobileWeatherVisible`, `mobileWeatherScale`, `mobileCalendarVisible`, and `mobileCalendarScale`. Follow the existing strict boolean and finite-number normalization. Each visibility defaults to `true`; each scale defaults to `1`, clamps to 0.5–2, and rejects strings or non-finite numbers by using the default. Keep existing desktop fields and their defaults unchanged.
- Keep the `dashboard.preferences.v1` key. Existing records missing mobile fields acquire these defaults in memory without automatically rewriting localStorage. Saving preferences persists both desktop and mobile fields together. Preserve unrelated preferences and the server-authoritative weather location behavior.
- Add a pure `resolveDisplayPreferences(settings, mobile)` helper returning the effective visibility and scale values needed by the three views, plus effective overall scale and alignment. Desktop resolution uses current `timeVisible`, `weatherVisible`, `calendarVisible`, per-view scales, `scale`, and `position`. Mobile resolution uses the six mobile fields, overall scale `1`, and left alignment. Return a fresh presentation object; never overwrite the normalized saved settings with projected mobile values.
- Define the media-query string in the dashboard helper module for use by the runtime. Keep CSS's 600px query as its explicit styling boundary and verify both sides of the boundary in browser checks. Detect viewport width through `matchMedia`, not user-agent or device classification.

- Relabel the existing per-view display fieldset legends as **Desktop display**, preserving the existing individual control labels and names. Clarify in General that lower-left/right position and overall scale apply to desktop. ## Acceptance Criteria

- At widths at or below 600px, the dashboard begins below page tools and presents visible sections in time → weather → calendar order, including actual DOM reading order. Above 600px, the current desktop order and bottom-aligned presentation remain intact.
- Each view has an independently saved mobile show/hide toggle and scale in Settings. Mobile effective sizing ignores desktop overall/per-view scales and position; desktop behavior uses its existing values.
- Mobile scales normalize to 0.5–2 and visibly affect the intended view at 0.5, 1, and 2. Legacy records default all mobile views to visible at scale 1 without replacing existing desktop preferences.
- All six mobile fields save through the existing action, survive reload, participate in hidden-panel validation, and retain unsaved drafts across tab and viewport changes.
- Narrow populated layouts at 320px and 390px have readable values, wrapping forecasts, and nonoverlapping sections with no horizontal page scroll. Vertical scrolling is allowed, and Settings remains usable at short viewport heights.
- Resizing across 600px switches active order, visibility, and scales immediately without storage writes, lost cached data, duplicate refresh owners, new integration requests, or restarting photo presentation.
- Weather location, weather update timestamps, calendar connection, units/timezone, and image preferences keep their existing shared behavior. Calendar events remain ready when either profile displays them, and both profiles hiding calendar pauses event refresh.
- All required Node, syntax, and Chromium checks pass, dashboard documentation matches the behavior, and implementation results and version changes are recorded through the task workflow.

## Risks And Decisions

- Flat mobile fields fit the current generic form/save mechanism and avoid nested preference editing. Defaults are deliberately independent: all views visible at scale 1, even if an older desktop record hides a view. This must be documented and verified rather than silently copying desktop settings into mobile fields.
- A presentation projection is transient. Saving the projected values would overwrite desktop settings, while calling the current full `apply` on every resize would restart the photo controller and reschedule integration work. The media listener therefore uses the narrower presentation path.
- The calendar controller currently refreshes immediately when `configure` changes it from disabled to enabled. Resolving its enabled flag from the active viewport would create calendar requests on breakpoint crossings. Stable eligibility across both saved profiles avoids this while retaining fresh cached data; a hidden active calendar can continue refreshing when the other profile enables it.
- Actual DOM movement keeps visual and reading order aligned. Move existing section nodes only on mode changes so service state, IDs, and event ownership remain stable. The existing leading heading and trailing photo caption must not move into the information order.
- Existing mobile CSS caps and rem-based clock sizing can mask scale controls even when the CSS variables are correct. Validate actual computed sizes and geometry at supported extremes rather than only variable values or screenshots.
- CSS and JavaScript must agree on the inclusive 600px boundary. Browser assertions at 600px and 601px protect this explicit cross-layer contract. Width changes need not refill Settings or save any preferences.
