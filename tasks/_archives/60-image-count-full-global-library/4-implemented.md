## Changes

- Replaced capped Global discovery with a complete metadata inventory in `src/photo-library.js`. Incremental directory enumeration and cooperative metadata merge sorting in `src/photo-inventory.js` remove the former 5,000-entry, eight-level, 100-image, and 200 MiB Global limits. Supported nonempty regular images retain the 20 MiB per-file limit and containment/no-symlink checks. Images stream on demand with at most eight admitted streams.
- Added coalesced refresh ownership, atomic inventory publication, content revisions, explicit exclusion counts, last-good recovery, cooperative stop/drain, and conservative 64 MiB metadata accounting across active/staging/retained generations. File-local permission/race exclusions differ from incomplete directory/source failures. Budget exhaustion discards staging and reports an explicit resource limit.
- Replaced the 1,000-token cache with active-generation token ownership and a 30-second previous-generation grace period. Unchanged metadata keeps stable URLs; observed replacements change URLs. Expired generations release their accounting and active tokens remain usable after index 1,000.
- Updated `src/photo-slideshow.js` and the shared snapshot validator for complete Global playback. Name/date/random sequences traverse the full eligible inventory; unchanged refreshes preserve sequence and deadlines without whole-pool JSON copies. Discovery continues when Global preferences cannot load, while shared playback pauses and later resumes from cache.
- Kept projection rules in the library. Local selects up to 100 eligible files in stable relative-name order within its 256 KiB transport bound. Legacy keeps its name treatment, 100-file limit, and 200 MiB skip-and-continue byte budget. Neither manifest read starts discovery or advances shared playback.
- Added validated, compact `GET /api/dashboard/photos/status` metadata and a dedicated Settings → Images count. The count stays visible through playback/decode errors, distinguishes unknown from zero, reports exclusions and stale/incomplete results, and works in both settings scopes. A separate bounded request owner polls only while Images settings is visible and cancels on close, hide, or disposal.
- Attached the library to production startup/shutdown ownership. Added filesystem error, large-library, token-expiry, budget-recovery, preference-recovery, controller-lifecycle, and real-browser count coverage. Updated existing display-status assertions and fixture cleanup for cached inventory ownership.
- Updated `docs/nfs-backgrounds.md` and `docs/testing.md`; added `scripts/benchmark-photo-library.js` for reproducible memory evidence.

## Memory benchmark results

Runtime: Node `v24.22.0`, Linux `x64`. Each process used 7,001 temporary 68-byte PNGs, a complete 7,001-selection virtual warm-up cycle, five unchanged refreshes, one replacement refresh, and grace-expired/GC-settled comparison points. Processes were isolated but ran concurrently with automated checks, so timings include shared-host contention and are not NFS performance claims. All values below are bytes except durations, which are milliseconds.

- Run 1: baseline RSS `64118784`, baseline heap `5247024`; sampled peak RSS `135557120`; current process-image peak RSS `136126464`; peak RSS increase `72007680` (68.67 MiB); sampled peak heap `38801480`. Warm settled heap `8506984`; subsequent settled heaps `[8476112, 8473288, 8474528, 8471832, 8478648, 8523440]`; final heap `8523664`; growth `16680`. Baseline/initial scan and subsequent refresh durations: `[2863.41, 801.18, 769.66, 768.34, 857.10, 790.89, 729.92]`. Passed.
- Run 2: baseline RSS `63660032`, baseline heap `5246552`; sampled peak RSS `134918144`; current process-image peak RSS `135720960`; peak RSS increase `72060928` (68.72 MiB); sampled peak heap `38772280`. Warm settled heap `8512200`; subsequent settled heaps `[8479520, 8471840, 8473944, 8472088, 8477344, 8521704]`; final heap `8521928`; growth `9728`. Durations: `[2678.27, 829.30, 781.57, 764.55, 877.23, 839.60, 740.21]`. Passed.
- Run 3: baseline RSS `64077824`, baseline heap `5246552`; sampled peak RSS `135360512`; current process-image peak RSS `136134656`; peak RSS increase `72056832` (68.72 MiB); sampled peak heap `38885640`. Warm settled heap `8517392`; subsequent settled heaps `[8485168, 8477520, 8482832, 8470552, 8480024, 8523776]`; final heap `8524000`; growth `6608`. Durations: `[2802.63, 818.03, 764.59, 791.19, 868.47, 838.36, 750.64]`. Passed.

All three runs stayed below the 128 MiB RSS-increase target and the 4 MiB settled-heap tolerance, which was larger than 10% of their warm settled heaps. The benchmark samples at cooperative scan/transform batches, publication/sequence construction, and settled expiry boundaries; these are metadata-only server measurements, not browser decoding measurements.

The first benchmark attempt incorrectly treated `process.resourceUsage().maxRSS` as a fresh process-image peak; it reported approximately 1 GiB despite sampled RSS near 128 MiB. Linux `/proc/self/status` `VmHWM` confirmed the current process-image peak separately. The benchmark now records both values and uses `VmHWM` for peak acceptance, because the harness's pre-exec resource high-water mark survives into `getrusage`. In the final runs that inherited value was `1091977216` bytes, while actual process-image peaks were approximately 129–130 MiB. Acceptance thresholds were not relaxed.
