## Follow-up: Bottom-Left Origin (`0.17.18`)

Changed custom profiles to a bottom-left origin as requested. X measures from the left; Y measures upward from the bottom of the usable dashboard area. Live widgets and preview boxes now use CSS `bottom`. Upward moves increase Y, and the upper-right resize handle grows height upward while retaining the bottom offset unless containment requires adjustment. Automatic layout, visibility, stacking, field-preservation semantics, and shared save ownership remain unchanged. Labels, announcements, and dedicated documentation explain the new coordinates.

Nested layout version 2 identifies this coordinate contract. Valid stored/cache version-1 layouts decode once using `newY = 1,000,000 - oldY - height`, preserving normalized placement and record order without a database/cache write or revision bump on read. Minimum-size projection now clamps against the bottom anchor. Current writes reject version-1 layouts with a reload instruction, preventing older pages from silently saving top-origin geometry. The next explicit save persists the converted layout through the existing revision owner.

Added model, API, cache, and browser regressions for migration validation/idempotence, unchanged read revisions/bytes, rejected old-coordinate writes, bottom anchoring, numeric Y/height changes, upward move/resize, and viewport changes. Browser verification also exposed a measurement callback overwriting an in-progress numeric entry; measurement-only renders now retain the focused input until its edit commits. The browser regression explicitly remeasures while a height field is being edited.

Verification: the complete Node suite passed 389 tests, and the complete browser suite passed 115 tests, including Firefox/Chromium sharing. After adding the explicit in-progress-entry assertion, the final focused layout suite passed all 13 scenarios. `npm run check`, individual syntax checks for all changed JavaScript files, and `git diff --check` passed. Package manifests now use `0.17.18`; no dependencies, runtime data, or legacy layout settings were changed.

## Changes

- `public/dashboard-layout.js` owns the six fixed widget identities, exact nested layout validation, deterministic templates/layers, viewport projection, and field-specific edits. Canonical geometry uses bounded integer proportional units; displayed widgets normally have a 100×100px minimum and fit the usable current window. Tiny surfaces temporarily lower that minimum, and unavailable surfaces disable editing. Intentional overlap never invokes collision avoidance or moves another widget.
- Implemented the plan-review remedy: moves preserve canonical width/height exactly, layer changes reorder unchanged records, numeric edits preserve unrelated fields, and size edits make only necessary same-axis containment adjustments. Gestures derive from a fixed original record and projection, not successive rounded previews. Minimum-clamped moves, already-displayed values, canceled gestures, and zero-net-change gestures do not resize/rebase the stored layout or create unnecessary revisions.
- `public/dashboard-layout-view.js` owns a single isolated custom stacking surface, viewport/safe-area/tool/status/caption measurement, and coalesced resize observation. Existing live widget nodes move into that surface only when custom mode starts and restore through stable anchors for Automatic mode; IDs, handlers, focus, selections, and content are preserved. Layers remain bounded below tools/status/dialogs. Each card scrolls internally; the photo caption remains a separate non-widget strip. Clock/weather/calendar scales retain their existing scope rather than scaling device/bookmark widgets accidentally.
- `public/dashboard-layout-editor.js` owns only the unsaved layout draft and labeled preview. It supports profile/arrangement/widget selection, move/resize pointer capture, finite pixel fields, keyboard edits, layer controls, reset, cancel, and status announcements. Its preview contains no live links, service controls, or credentials. Secondary pointers cannot cancel the active gesture; primary cancellation, Escape, and viewport/profile changes restore original geometry.
- Extended `public/dashboard-helpers.js` and the existing shared settings flow with one `widgetLayout` preference, not a new endpoint/table/cache owner. Older valid records/caches gain Automatic profiles without read-time writes. Invalid present layouts fail validation; incomplete old-page saves receive an actionable reload error. Complete-layout saves retain existing selections, strict bounds, payload budgets, transaction/revision ownership, and conflict behavior.
- `public/dashboard.js` integrates the editor with the existing form save, revision, and pending-write flow. Layout-only snapshots and caption/resize callbacks update DOM projection without reconfiguring providers or timers. Failed/conflicting saves preserve drafts; confirmed cached layouts remain display-only during server outages. Layout cancellation preserves unrelated raw/invalid form drafts, and an old save completion cannot clear a newer Settings session. Existing integration credential forms remain separate.
- Updated `public/index.html` and `public/dashboard.css` for the editor/custom surface while retaining the eight Settings tabs and existing Automatic flow. Added `docs/dashboard-layout.md`, linked it from `docs/dashboard.md`, and documented verification in `docs/testing.md`. Both package manifests now identify `0.17.17`; dependencies and the legacy home-layout/settings API remain unchanged.

## Investigation And Limits

Initial browser verification was blocked by missing Playwright executables. The user installed Chromium/Firefox and confirmed availability before testing continued; no host packages or privileged changes were installed by this implementation. Browser testing exposed a real Escape handling issue: focus outside the preview allowed native dialog cancellation to discard more than the gesture. Explicit gesture focus and dialog-cancel ownership now cancel only the active drag, with a passing regression.

Other initial fixture corrections distinguished a small preview's resize corner from its move target, allowed the documented zero-surface defer behavior, avoided an unintended edge-containment adjustment in a resize assertion, and supplied required SQLite device fields. Native browser fullscreen exit is verified through the Fullscreen API; synthetic headless Escape is not claimed as an OS/browser-chrome fullscreen test. The original assertions remain meaningful rather than being skipped to force success.

The proportional representation intentionally fits a shared profile differently on differently sized windows; pixel edits affect only their explicit canonical fields, and resize alone never writes. At 100px not all content is visible simultaneously, so internal scrolling is the supported tradeoff. Browser touch verification uses Chromium's actual touch input protocol; the focused Firefox case checks rendering/persistence, not a claim of hardware-touch testing or Safari coverage.

No application dependency, database table, retired layout engine, user `.env`, real credentials, NFS mount, running user service, existing core artifact, or `todo.md` was changed. All test storage/processes were owned fixtures. No release, image build, host policy change, push, or merge was performed. This implementation and its report are committed together on the task branch.
