## Scope

Give custom dashboard profiles a local fullscreen-oriented reference canvas. Project canonical widget records into that reference once per reference context, then uniformly fit the entire canvas and its content into the current usable window. Keep independent desktop/mobile profiles and existing shared save ownership. This stage writes only this plan; it does not change implementation, tests, dependencies, versions, or user data.

## Current Boundaries

- `public/dashboard-layout.js` owns version-2 normalized bottom-left geometry, the 100px projection minimum, field-specific edits, layer order, and templates. Its projection takes a surface; passing the current window independently scales both axes and reapplies minimum clamps on each resize.
- `public/dashboard-layout-view.js` measures a destination from viewport dimensions, safe insets, visible tools/status, and a conditional 48px caption strip. It moves existing nodes into `#widget-surface`, assigns geometry/padding variables, observes destination changes, and restores Automatic nodes/styles. There is currently no separate reference context.
- `public/dashboard-layout-editor.js` receives `layoutView.surface` and uses that changing window measurement for pixel fields, preview scaling, and pointer conversion. It already keeps original canonical records during gestures and preserves unrelated fields.
- `public/dashboard.js:34-35` composes view and editor. Settings opens at lines 289-298 and closes at line 301. Fullscreen changes run `applyBookmarkPresentation()` at line 372, which updates DOM visibility and layout. Existing service and save owners must not acquire new geometry responsibilities.
- Task 50 fixed live padding and preview border floors. Its pure/view tests and three controlled-viewport browser scenarios currently expect projection directly into the available window; those expectations must change explicitly to reference projection followed by uniform fitting, not be removed.
- `public/dashboard-display.js` toggles the global `bookmarks-shown` class when fullscreen bookmark hiding changes visibility. Existing `.bookmarks-shown` rules in `public/dashboard.css:70-73` change weather-value flex behavior and forecast-temperature wrapping even inside custom widgets. Transforming a reference-sized stage alone does not isolate these content-layout decisions.

## Design Decisions

### Reference coordinates and destination coordinates

- Keep `widgetLayout` version 2 and its existing normalized records unchanged. X/Y remain bottom-left proportional coordinates and item order remains layer order. This is a documented rendering/editor-pixel contract change, not a new wire format or reinterpretation of Y. No schema migration, read-time write, initialization, or cache rewrite is needed solely for this change.
- Define reference pixels as CSS pixels in a locally estimated or confirmed fullscreen usable canvas. They are not physical display pixels and must not be multiplied by `devicePixelRatio`. Existing layouts retain their normalized positions, dimensions, and layers, but their displayed pixel sizes can change under the new fitting policy. Document that explicitly.
- Apply `projectWidget()` and its 100px minimum only against reference dimensions. Fit the result with one scalar; never run a second projection/minimum clamp against the destination. Windowed physical sizes may therefore fall below 100px. Padding, fonts, borders, scrollable content, and hit regions scale together with the canvas. Do not change global or per-widget user font preferences to simulate fitting.
- Custom widget content must use a stable internal layout independent of unrelated widget visibility. Automatic group-composition classes such as `bookmarks-shown` must not alter a custom weather card's flex policy or forecast wrapping. Intentional desktop/mobile profile differences remain supported; invariance comparisons apply to the same accepted reference and active profile.
- Let `A` be the current usable destination and `R` the reference. For positive finite dimensions, use `s = min(1, A.width / R.width, A.height / R.height)`. Anchor the transformed canvas at `A`'s bottom-left; unused space stays above or to the right. Do not upscale beyond 1. Reference cards retain their exact projected rectangles; screen rectangles are those rectangles multiplied by `s`, without independent pixel rounding per card.

### Reference sizing and lifecycle

- Maintain one local, in-memory reference owner with desktop/mobile entries. It has no SQLite, localStorage, shared cache, or network writes. Reload starts a fresh estimate; another browser derives its own screen-local reference from the same canonical layout.
- Before fullscreen, validate `screen.width` and `screen.height` as finite positive CSS dimensions whose floored values are safe integers. Do not read `screen.availWidth`/`screen.availHeight` as fullscreen bounds. If screen dimensions are missing or invalid, snapshot the initial valid layout viewport as an explicitly labeled fallback; do not replace that fallback on every window resize. If neither source is valid, defer until a valid source is observed.
- Use mode-specific margins of 16px for desktop and 8px for mobile. Reference reservations are stable CSS-pixel policy: safe insets captured for the reference context, a 32px status band plus an 8px gap, and a 48px caption band, whether those bands currently contain text or not. Thus `R.width = max(0, floor(rawWidth - 2 × margin - safeLeft - safeRight))` and `R.height = max(0, floor(rawHeight - 2 × margin - safeTop - safeBottom - 32 - 8 - 48))`. Never include the measured windowed tools height in reference sizing. Keep these constants in one reference-policy module, not separate view/editor implementations.
- Keep actual destination measurement separate. It continues to reserve actual visible tools/status, current safe insets, and the displayed caption strip. Longer status text can reduce destination space and scale the canvas further; it must not change reference geometry. Empty reference bands may leave unused space even in fullscreen. This deliberately favors stable coordinates over filling every pixel.
- On fullscreen entry, obtain the actual layout viewport from validated `innerWidth`/`innerHeight`, after fullscreen activation and coalesced layout settlement. Use consecutive animation-frame samples to avoid immediately confirming the pre-transition size; later fullscreen-entry resize notifications may replace a provisional sample until settlement. Do not confirm from visual viewport scrolling, pinch-zoom dimensions, keyboard opening, or ordinary window resize. Update the reference's raw dimensions and fullscreen safe-inset snapshot once that entry is confirmed, retaining the result on exit.
- First confirmation may correct an estimated aspect ratio or reference minimum clamp and therefore change reference-pixel projection once. Do not claim impossible exact knowledge before fullscreen. Canonical unit geometry remains untouched. Repeated entry on the same unchanged display/orientation confirms the same result and must not cause cumulative drift.
- Identify a display/orientation context from valid screen width/height and available orientation metadata. Recheck on resize, orientation change, fullscreen entry, and persisted-page resume, but ignore ordinary window size changes when this identity is unchanged. A changed context invalidates the old confirmation and obtains a new estimate, later confirmed on fullscreen entry. If screen metadata is unavailable, retain the fallback across ordinary window resizes; explicit orientation changes can invalidate it. Do not request multi-screen permissions or attempt to infer a display change from `screenX` alone. Same-sized monitors without distinguishing metadata may remain indistinguishable; document this limit.
- Construct both profile references from the same raw screen context with their own margins. Actual live profile selection remains the existing inclusive 600px viewport breakpoint; crossing that breakpoint can deliberately select a different saved profile. Do not promise identical arrangements between different profiles.
- Freeze the reference owner's accepted entries for the entire Settings session, including inactive-profile editing. Acquire the lock before `fillForm()` on open. Queue the latest screen/orientation/fullscreen reference update while locked; the live custom view and editor both keep the accepted reference, while destination fitting may continue. On close, cancel any active gesture, release the lock, and apply the queued reference once. Do not advance preference revisions, dirty state, or reset editor drafts because a measurement changed. This local coordinate lock does not fix the inherited polling-induced draft-reset issue.

## Acceptance Criteria

- Custom profiles use an estimated fullscreen reference before first fullscreen, confirm it using actual settled fullscreen layout dimensions, and retain it after exit. Invalid screen data has a stable fallback or safe deferral, with no false promise of exact pre-fullscreen knowledge.
- For an accepted reference and the same profile, every destination uses one capped scale for the complete canvas and content. Relative reference geometry never changes because tools hide, captions change, or the window resizes. Unused space stays above/right of the bottom-left anchored canvas.
- Live rendering, editor preview, numeric controls, and pointer conversion use the same accepted reference contract. Settings freezes reference updates until close, without mutation, cumulative drift, hidden autosave, or loss of unrelated canonical fields.
- Existing normalized layouts remain valid without database/cache migration or revision changes on read. First-confirmation pixel correction and different local screens are documented rendering changes, not silently rewritten preferences.
- Tiny-surface containment, zero-area deferral, visibility, layering, content scrolling, Automatic layout, saved selections, pending actions, and service/timer ownership retain meaningful coverage. Windowed physical minima do not defeat uniform scaling.
- With a fixed accepted reference and active profile, fullscreen bookmark hiding changes only the bookmark's visibility and destination fit, not weather flex behavior, forecast line wrapping, or normalized child layout. Deterministic and real fullscreen regressions protect this content-level invariant, while Automatic composition behavior remains unchanged.
- Focused/full Node/browser and syntax/diff verification pass with actual geometry, text-scaling, reference lifecycle, and zero-write assertions. The inherited polling/editor ownership warning remains separate and unresolved.

## Risks and Limits

- Browsers cannot guarantee future fullscreen viewport bounds beforehand. The first estimate-to-confirmation correction is a deliberate one-time calibration, not a promise of exact initial placement. Fullscreen rejection leaves the valid estimate usable.
- Session-local confirmation is not persisted. Reload or a new screen context starts an estimate again; this avoids unauthorized per-browser settings stores and geometry writes. Identical-looking monitor metadata cannot reliably identify a different monitor without extra browser permissions, which are out of scope.
- Fixed status/caption bands in the reference trade some fullscreen space for stable coordinates. Actual destination status wrapping may shrink the fit further. Do not let live measured tool height or caption presence leak into reference sizing.
- Uniformly scaling the canvas also scales text and control targets. They can become small in narrow windows; users may enlarge the window or enter fullscreen. Avoid post-fit minimums or selective font scaling that silently breaks the chosen invariant.
- Screen estimate correction and screen/orientation context changes can change reference aspect ratio or minimum-clamped projection. Restrict those changes to explicit context/confirmation boundaries and freeze them during Settings. Ordinary destination changes must never masquerade as reference recalibration.
- Native fullscreen transitions can deliver events in different orders. Confirmation and cancellation require generation ownership and settled sampling, not a permanently running polling loop or an assumed synchronous viewport change. Tests must exercise delayed/obsolete notifications and disposal.
- A transform preserves an existing rendered layout, not the stylesheet decisions that produce it. Global visibility/composition classes must be isolated from custom card content explicitly; outer rectangle and scale assertions alone cannot prove this invariant.
- This task changes custom rendering, not the inherited global draft-polling policy. No new persistence schema, dependency, real provider request, Wake packet, NFS mount, privileged operation, user-data/configuration edit, legacy-layout change, or `todo.md` edit is authorized.
