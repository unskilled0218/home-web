## Scope

Add **Settings → General → Settings scope** with **Local — this browser** and **Global — all Global browsers**. Local is the default when no valid mode has been saved. Each browser independently remembers its choice. Changing browser A to Local must neither change browsers B/C's mode nor modify their shared global configuration. Global browsers retain the current SQLite-backed settings, conflicts, synchronization, server weather location, and server-owned slideshow.

Local mode independently owns every dashboard preference in `PREFERENCE_KEYS`, both Desktop/Mobile layouts, and the selected weather location. It does not inherit, publish, or apply global preference/weather-location changes. Local time format, weather units/location, visibility, selections, layout, and image ordering/interval must work rather than merely display different form values. Add validated JSON import/export for the global preference and weather-location configuration.

Existing integration accounts, credentials, managed Wake-on-LAN inventory/history, and NFS mount configuration remain installation resources, as they were before global display preferences were introduced. Local mode can display shared integration content using local selections but cannot change installation configuration through its settings controls. Connection/device-management mutations require explicitly selecting Global; normal Wake actions retain their current separate action contract. Import/export is a settings transfer, not a database/credential/device backup. No implementation code or version files change during this planning stage.

## Implementation plan

### 1. Define settings ownership and storage contracts

- Keep `public/dashboard-helpers.js` as the canonical dashboard preference schema; do not add `scope` to `PREFERENCE_KEYS`, SQLite preferences, shared snapshots, or transfer files. Reuse strict preference/layout/selection validation instead of maintaining a separate list of local display fields.
- Add browser-safe `public/dashboard-settings-data.js` for scope/local-record/transfer validation. Store the mode in `dashboard.settings-scope.v1` as `{ schema: 1, mode: 'local' | 'global' }`. Store independent local state in `dashboard.local-settings.v1` as `{ schema: 1, revision, preferences, weatherLocation }`, with a nonnegative safe-integer local revision and a validated location or `null`. Separate keys ensure saving an old local draft cannot overwrite another tab's newer mode choice. Bound each local serialized record to 128 KiB of UTF-8 JSON.
- Bootstrap Local from a valid existing local record; otherwise restore valid legacy `dashboard.preferences.v1` values, including its browser weather location, or use canonical defaults with no location. Use supported historical schema decoding only for stored records. Never seed Local from `dashboard.shared-settings.v1`, current SQLite values, or global weather metadata. Preserve the legacy record until any explicit local persistence succeeds.
- Missing/corrupt mode data defaults to Local without writing global state. Invalid stored local data produces an explicit recovery message and safe preview, not silent global adoption. Reads must not overwrite invalid records. A storage/quota failure must not report a successful persistent save or mode change; keep the prior confirmed state and user draft. Startup previews remain usable when storage is unavailable.
- Treat a browser as one profile/origin storage area: tabs in that area share the mode/local record through `storage` events; independent contexts/profiles remain independent. Local records use a read-before-write revision check for already-observed conflicts and last-successful-write semantics for truly simultaneous cross-tab writes; do not claim `localStorage` offers SQLite-style atomic compare-and-swap.

### 2. Add one scope-aware preference coordinator

- Add `public/dashboard-settings-scope.js` as the sole owner of active scope and effective preferences. It wraps the existing `createSettingsSync` Global adapter and a small Local storage adapter, exposing the current snapshot, source identity/epoch, pending/error/writability state, save/reload, scope changes, visibility, and disposal. Keep the current global revision-conflict implementation rather than duplicating it inside `dashboard.js`.
- Publish a validated Local baseline immediately without waiting for `/api/dashboard/settings`. Local preference and layout saves write only the local record. Do not call global preference initialization, preference PUT, or global weather-location PUT. Stop the global preference polling owner while Local is active; retained global caches remain inactive caches rather than local authority.
- Remove automatic publication of legacy browser preferences from the shared controller's startup path. Entering Global reads the current confirmed global record or its existing offline cache; entering Global alone must not upload Local values or initialize a global row. Only an explicit Global save/import writes global settings. Existing legacy initialization API behavior can remain for compatibility with older clients, but updated browsers must not invoke it automatically.
- Switching back to Local restores that browser's prior local record, never the most recently rendered Global values. On first Local use without a record, use the Local bootstrap rules. Selecting Global while offline can retain Global mode with an unconfirmed global preview/cache and disabled global writes; do not silently continue operating as Local.
- Capture `{ scope, epoch, revision }` when opening preference/layout drafts and beginning saves. Reject a save whose captured source no longer matches the active source, even if numeric local/global revisions happen to match. Abort/retire old reads, observers, photo/weather decodes, and file-import completions on source transitions. A late Global response must not overwrite Local state, and a late Local completion must not apply to Global.
- Same-tab mode changes require no pending settings/import/location/configuration mutation and no dirty preference or active layout draft; keep the current choice and show how to save/discard the draft first. If another tab changes scope during editing, retain the captured draft, cancel active gestures, and block its Save until explicit reload/discard adopts the new source. Do not redirect the old draft into a different store. Already-admitted global writes may still commit; retire their UI adoption after a cross-tab transition without pretending cancellation rolls back SQLite.

### 3. Add the Settings scope controls and route all saves

- In `public/index.html`, add the **Settings scope** fieldset at the start of General with the two labeled choices and a short explanation that the choice affects this browser only. Make scope selection a separate local action, not another field submitted by the global preference form. Keep tab navigation, native form ownership, mobile sizing, and save/close accessibility.
- Update `public/dashboard.js` to consume the coordinator's effective snapshot, not `createSettingsSync` directly. Route Save preferences, bookmark/device picker choices, weather-location selection, and direct-layout Save/reload through the captured active source. Local state must be editable/savable without a healthy global preference endpoint. Keep local settings and the saved mode intact on reload, browser restart, and temporary server outages.
- Make success/loading/conflict text identify Local versus Global. Local saves say they apply to this browser; Global saves retain their shared meaning. Reload labels in both Settings and the layout toolbar refer to the active source. Update `public/dashboard-layout-editor.js` and `public/dashboard-layout-session.js` to carry source identity and support a valid local baseline rather than requiring server confirmation for Local writes.
- Apply effective local/global time, units, visibility/fullscreen flags, captions, selections, and Custom geometry through the existing presentation functions. Only actual changed values reconfigure an owner; a storage event or unchanged poll must not restart clock intervals, transitions, provider requests, or layout measurement ownership.
- Mark installation-wide connection and managed-device editing controls clearly. In Local mode, gate their mutation handlers as well as disabling the controls, while retaining read-only connection status, local device/bookmark selection, content display, and existing Wake action feedback. Switching scope must not disconnect an integration, clear a token, delete a device, or dispatch a Wake.

### 4. Isolate local weather location and retrieval

- `public/dashboard-weather.js` currently adopts the global location and calls `/api/weather/location`. Add an explicit source mode: Global keeps the existing server location/revisions; Local uses only the location in the local settings record. Local location selection persists locally before adopting the change and must not rewrite global location, cache rows, revisions, or registrations. Global location observers must never apply in Local mode.
- Add a bounded query service in `src/local-weather.js` and `POST /api/weather/local` in `src/app.js`. The request is exactly `{ location, timezone }`, with a 2 KiB body limit and existing coordinate/label/timezone validation. It reads or schedules volatile forecast/AQI data for that requested source; it is not a saved-location mutation. Use existing trusted-LAN/Host/Origin/method checks, fixed provider URLs, no-store responses, and explicit 400/429/503 outcomes. Do not accept provider URLs or a force-refresh bypass.
- Extract reusable bounded provider retrieval into `src/weather-provider.js` from `src/weather.js` rather than duplicating provider queries, response parsing, normalization, and deadlines. Retain the 1 MiB provider-body and ten-second request/body bounds. Global weather continues its existing persisted hourly/no-viewer operation without being reconfigured by Local requests.
- Keep local weather cache state memory-only, keyed by validated coordinates and canonical timezone, with at most 16 retained keys, 512 KiB of normalized cached payloads, two active provider requests, and a bounded queue within admitted keys. Coalesce matching demand, throttle successful and failed attempts to the existing hourly refresh policy, evict inactive least-recently-used entries, and return bounded busy feedback when no entry can be reclaimed. Reject late publications after eviction/stop. Labels remain the requesting browser's local presentation value rather than shared cache identity.
- Return a validated snapshot with explicit local source identity matching requested coordinates/timezone, normalized data, update times, refreshing/stale/error states, and a 256 KiB response cap. Do not reuse global location revisions as Local authority. With no local location, show setup state and issue no provider request. While visible, the Local browser polls pending work at five seconds and settled data at sixty seconds; unchanged metadata does not force another provider fetch. Stop browser reads while hidden; no background local query loop runs without demand.
- Inject the local-weather owner through `src/server.js` and drain it through `src/shutdown.js`. Construction starts no requests; stop cancels queued work/timers, aborts and owns active work, and participates in the existing global shutdown deadline. Reuse weather snapshot/unit rendering with source-aware guards so a late global response, evicted local result, or prior local city cannot replace the active city's data. Preserve last-good data only for the same source.

### 5. Separate local photo playback from the shared slideshow

- Keep `src/photo-slideshow.js`, `/api/dashboard/slideshow`, and the existing snapshot follower as the Global owner. The server still scans/rotates with no connected Global browsers. Local order/interval changes must not call its `configure`, reset its deadline, or alter the image observed by Global clients.
- Add a dedicated `GET /api/dashboard/photos/local` projection in `src/app.js`, registered before opaque-token routing, with existing trusted-LAN/Host/Origin checks, no-store responses, and 405 handling for unsupported methods. Reuse the existing shared photo-library instance and its coalesced `list` operation; do not create another library, shared cursor, or request-owned slideshow. Pass configured NFS enablement from `src/server.js` independently of preparation availability, so a failed enabled source is not mislabeled disabled. Disabled sources return immediately without scanning or retrying mounts.
- Extend browser-safe `public/photo-slideshow-data.js` with a strict Local manifest validator and shared `MAX_LOCAL_PHOTO_MANIFEST_BYTES = 262144` constant. The exact version-1 shape is `{ version: 1, enabled, available, count, photos }`, with boolean source flags, at most 100 records, and `count === photos.length`. Disabled means `enabled: false`, `available: false`, and an empty array; an enabled but failed/unprepared source has `enabled: true`, `available: false`, and an empty array. Successful scans have `enabled: true`, `available: true`; a successful all-rejected scan is authoritative empty with `count: 0`, not an outage. Unavailable states must not contain photos. These flags describe the installation source, not the browser's Local/Global mode.
- Apply the existing shared current-photo validator to each record before it enters the Local projection or is serialized. Retain exact accepted names/opaque URLs, deterministically exclude ineligible records, count only eligible photos, and do not scan beyond the library's accepted pool to replace exclusions. Validate the projected envelope and enforce its complete JSON-serialized UTF-8 size at 256 KiB before response publication; never serialize the raw legacy result as the Local response. Unexpected producer invariant failures return a bounded 503 rather than an invalid success body. Preserve the unfiltered `/api/dashboard/photos` legacy response and existing opaque image streaming contract.
- Add `public/dashboard-local-photos.js` for explicitly selected Local playback, consuming only the new bounded `/api/dashboard/photos/local` contract and existing opaque streaming URLs. It owns only that browser's name/date/random traversal, interval, decode, and visibility pause/resume. Reuse the shared manifest/photo validators and existing renderer/presentation callbacks; do not use Local playback as an error fallback for Global mode, or fall back to the raw legacy manifest when the Local endpoint fails.
- Load/refresh the Local manifest at startup/resume and at a sixty-second settled cadence while visible. Enforce the existing 100-photo/eligible-name limits, a 256 KiB UTF-8 manifest-body cap, ten-second request/body/decode deadlines, one in-flight manifest read, and bounded refresh/rotation/decode timers. Keep unchanged file identity/order/current deadlines where appropriate; reconcile replacements/removals, distinguish confirmed empty from transient failure, and avoid re-decoding unchanged selections.
- Local random mode traverses shuffled eligible pools without immediate cycle-boundary repeats for multiple images. A failed image must not create a tight skip loop; retain a previous good background and retry with a bounded delay or on the next scheduled selection. A confirmed empty/disabled source clears the layer. Neither Local reads nor decode failures send shared advance/configuration commands.
- Add a small scope dispatch at the photo-controller composition point so exactly one playback owner is active. Dispose the prior owner and reject late work when switching, immediately adopt the server selection on entering Global, and start the independent Local sequence on entering Local. Share rendering/caption/animation logic, not selection state. Existing NFS file/depth/byte/token/stream protections and shutdown ownership remain authoritative.

### 6. Add atomic global settings import and export

- Define a strict portable JSON envelope in `public/dashboard-settings-data.js`: `{ format: 'home-web.global-settings', version: 1, preferences, weatherLocation }`. `preferences` is a complete current canonical dashboard preference object, including both layout profiles and selected opaque device/bookmark identities; `weatherLocation` is validated or `null`. Reject unknown fields/versions, malformed nesting, invalid values, and oversized input without normalization that silently changes imported choices.
- Limit files/envelopes to 128 KiB of UTF-8 JSON and canonical inner preferences to the existing 65,536-byte settings bound. Validate before application on both browser and server. Transfer no scope/mode choice, revisions, integration credentials/account configuration, managed devices/Wake history, NFS paths, ephemeral image URLs, provider caches, or browser cache records. Unsupported identity references remain unresolved selections; never substitute by name or create integrations/devices from an import.
- Add `GET /api/dashboard/settings/export` for a consistent, read-only validated global bundle and `POST /api/dashboard/settings/import` for an explicit global replacement. Import accepts the envelope plus separately supplied expected preference/weather revisions captured from live Global state, not revisions trusted from the file. Use existing network/method protections, no-store responses, download naming, bounded body reads, and 400/409/503 errors. Export must not initialize preference rows, contact providers, or alter service state.
- Add a store-level transfer operation through `src/db.js` and a focused `src/dashboard-settings-transfer.js`. Read both global components consistently and import them in one SQLite transaction after checking both revisions inside that transaction. Refactor the transaction boundary shared by `src/dashboard-preferences.js` and `src/weather-store.js` as needed so this does not open nested `BEGIN` transactions. Any validation, conflict, or persistence failure leaves both components and service configuration unchanged. No-op imports preserve existing revisions.
- Support `weatherLocation: null` as an explicit imported clear, retiring the old global weather work/cache correctly. After commit, notify slideshow configuration and weather location-reload logic from the committed result, without a second preference/location write. Add a bounded post-commit weather adoption hook rather than calling the existing saving method again. Notification failure must not relabel an already committed import as uncommitted.
- Place **Export global settings** and **Import global settings** under General. Export always reads current global state, even when Local is selected, and never exports unsaved drafts or substitutes local values. Import is enabled only in Global mode with confirmed baseline revisions and no pending/dirty settings/layout work; choosing a file alone does not commit it or switch mode. The explicit import action validates and submits once, preserves the chosen file on conflict/failure, and updates active Global owners only from the confirmed result. Other Local browsers, their local records, and every browser's saved scope choice remain untouched. Release download object URLs and retire pending file reads on scope changes/disposal.

## Acceptance criteria

- An unconfigured browser starts in Local mode and can persist its own dashboard options and weather location without initializing or modifying Global settings. Existing stored mode choices survive reload; missing/invalid choices never silently select Global.
- Switching A to Local affects only A's profile/origin. B/C remain Global, retain their saved mode, and continue synchronizing with each other. Local edits leave global preference/weather revisions, Global weather configuration, shared slideshow sequence/deadline, credentials, and device inventory unchanged.
- Local browsers ignore Global preferences/weather location for active rendering, drafts, and saved values. Different Local contexts can show different time formats, units/cities, layouts/selections, and photo sequences. Returning to Local restores that browser's local record; joining Global adopts current confirmed shared state without uploading Local values.
- Every save path, including layout edits and weather selection, targets its captured source. Pending reads/decodes/file operations from another source cannot publish into the new one. Dirty drafts are preserved and cannot be silently applied across scopes; failed persistence never reports durable success.
- Global import/export transfers validated preferences and weather location only. Import checks both current revisions and commits both components atomically; failures/conflicts leave both unchanged. Import never changes anyone's scope choice or local settings, and export never substitutes local/unsaved values or includes installation credentials/history/paths.
- Global weather retrieval and photo rotation continue with no viewers. Local weather/cache work and photo playback remain bounded, preserve failure semantics, and cannot reconfigure Global owners. No duplicate polling/timer/transition ownership appears after switching, hiding, reconnecting, or persisted-page restoration.
- Every successful Local photo manifest passes the same server/browser validator and fits within 262,144 serialized UTF-8 bytes after producer-side eligibility filtering. Mixed oversized legacy metadata cannot hide eligible Local photos. Confirmed disabled or available/empty manifests clear the Local background; enabled/unavailable or transport failures retain last-good state. Legacy manifest/stream behavior and the Global cursor remain unchanged.
- Existing shared integration content, Wake actions, fullscreen/reduced motion, Custom geometry, selected identities, Global conflict handling, and safe shutdown retain their established contracts. Installation-wide settings mutations are clearly identified and require Global mode in the updated UI.
- Node/syntax/diff checks pass. Browser scenarios prove independent-context behavior when dependencies are available; any environment blocker is recorded explicitly.

## Risks and decisions

- “This browser” means a profile's storage for this dashboard origin, not one tab and not a server-wide flag. The scope selector never belongs to the global settings payload or import file. This directly preserves the user's clarification that other Global browsers remain Global.
- Local isolation includes weather location and image order/interval, not only visual formatting. Adding local preferences alone would still let current server-owned weather/photo mutations change Global browsers. Explicitly selected Local query/playback owners address that mismatch while retaining current Global behavior.
- The raw legacy photo manifest can exceed the Local reader's cap because JSON escaping expands ineligible filenames, and it cannot distinguish disabled from failed sources. Local playback therefore uses a separate producer-filtered projection with explicit source flags; increasing a client cap or filtering only after reading the legacy body does not resolve that contract mismatch.
- Shared connection credentials, device management, and mount configuration are installation resources rather than display preferences. Local settings cannot silently change them; this task does not introduce per-browser integration accounts or a multi-tenant credential store. Read-only shared content remains available with independent Local choices.
- Fresh/previously unmarked browsers now default to Local even when a shared cache exists. Global SQLite data is preserved for users explicitly choosing Global; automatic legacy-to-global publication is retired. Copying Local values into Global requires an explicit Global save/import, never just a mode switch.
- Local storage writes are synchronous and profile-local but lack multi-tab transactional compare-and-swap. Detect already-changed drafts, isolate source keys, synchronize observed events, and document true simultaneous writes as last-writer-wins rather than inventing server revisions for Local.
- Global import includes weather location because it is a user-visible global setting currently stored outside `PREFERENCE_KEYS`. A single transaction and post-commit service adoption are necessary; two successful HTTP saves would not provide atomic import. Shared credentials and server inventory are deliberately outside the transferable format.
- Local weather coordinates necessarily reach the dashboard server for retrieval, but do not become the installation's saved location. Volatile bounded data caching is not a new persistent per-browser settings store. Separate Local resource budgets must not evict or cancel Global weather work.
