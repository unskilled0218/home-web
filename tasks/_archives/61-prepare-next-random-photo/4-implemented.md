## Changes

- Added browser-safe `public/photo-batch-sequence.js`, shared by Global and Local owners. It stores filename reservations, one current/queued metadata batch, an unreserved index bag, and visited identities. Random draws occur without replacement; commitment, not reservation, advances visited progress. Complete stable cycles avoid immediate random boundary repeats. Name/date modes retain their existing comparison semantics.
- Batch targets use `ceil(30 / intervalSeconds)`, clamped to 1–32 entries and available candidates, with a combined 64 KiB serialized UTF-8 photo-metadata admission budget. Bootstrap counts toward the initial preparation horizon. Bounded asynchronous fills own one job and one five-second failure retry; stop retires generations and drains actual outstanding preparation. There is no new preference or Settings control.
- Replaced full shuffled-record sequences in `src/photo-slideshow.js` and `public/dashboard-local-photos.js`. Both reconcile inventory by relative filename, retain surviving visited progress/reservations, remove deleted bookkeeping, and resolve current/queued metadata from the active inventory. Metadata replacements update URLs without making filenames unseen. Interval changes preserve published previews and traversal progress. Deleted current files receive a prompt eligible replacement even when preparation is deferred.
- Kept Global rotation independent of HTTP readers, browser visibility/readiness, and Local selection. Missing Global preferences still permit discovery and cached Local/Settings access. Due selections retain the frame and rearm a bounded retry when metadata is pending. Unchanged scans preserve deadlines. Shutdown still drains scans, HTTP, and preparation before SQLite cleanup.
- Added an exact version-2 snapshot contract with nullable `next` and independent `queueRevision`, retaining the strict version-1 contract and 8,192-byte bound. `GET /api/dashboard/slideshow?version=2` opts in; default/explicit version 1 stays compatible, and unsupported or duplicate explicit versions receive bounded HTTP 400 responses. Reads do not fill, scan, stream, or advance playback.
- Global followers request version 2 and accept version 1 without prefetch. They reject stale current/queue revisions and inconsistent same-revision metadata. Pending multi-image previews use the same single metadata timer at up to 500-millisecond readiness cadence; failed reads retain five-second recovery. Preview-only changes preserve current rendering and transitions.
- Local followers receive synthetic version-2 snapshots through coalesced dirty-flag deliveries, including preparation completion during an earlier snapshot read. Automatic follower HTTP polling remains disabled. Hidden/resumed generations suppress late deliveries and resume with fresh metadata without consuming another selection.
- Retained decoded resources in `public/dashboard-photos.js`: current work takes priority, one immediate preview is decoded, repeated metadata reuses pending/ready work, and an in-flight or ready resource is promoted only when selected. Ten-second decode deadlines and five-second retry recovery preserve held frames. Suspension, scope/instance retirement, replacement URLs, and disposal retire obsolete resources.
- Updated `public/dashboard.js` to adopt the decoded foreground element. The view owns promoted resources and releases sources when outgoing/current/blur layers are removed. Ownership remains one foreground, at most one outgoing layer, and one speculative slot, with optional blur presentation layers.
- Added deterministic sequence/lookahead tests, version-negotiation/schema/API cases, active-URL reconciliation and preparation-drain tests, delayed Global/Local browser delivery across batch boundaries, and a larger-image browser resource check. Updated fixtures for the versioned query while retaining version-1 coverage. The former random-shuffle call-count assertion now checks pure reads and traversal behavior because the implementation draws candidates incrementally.
- Updated README.md, `docs/nfs-backgrounds.md`, and `docs/testing.md`. Extended the existing server benchmark with a complete unique metadata-batch traversal, preparation timings, queue capacities, and metadata-byte measurements.

## Browser resource measurements

The final full browser run exercised the production Global view with 20 eligible filenames and generated 2048×1536 PNGs of `3555113` compressed bytes each. Estimated RGBA storage is `12582912` bytes (12 MiB) per decoded image before implementation-specific browser overhead. The test uses real browser elapsed time, one-second fades, blur backgrounds, repeated promotions, and one stalled upcoming request followed by invalid image bytes. The held frame stayed visible during the failure and later authoritative selections recovered.

- Actual image requests: `10` across `10` distinct URLs, rather than all 20 inventory entries or every metadata batch member. Nine successful decode durations were `[120.7, 125.7, 139.1, 117.5, 143.8, 134.4, 133.7, 112.1, 133.1]` milliseconds. One requested image deliberately failed.
- Ownership samples: initial `{ foreground: 1, blur: 1, speculative: 1, released: 0 }`; transition peak `{ foreground: 2, blur: 2, speculative: 1 }`; settled frames repeatedly returned to `{ foreground: 1, blur: 1, speculative: 1 }`. Cleared source counts advanced through `3, 5, 7, 9, 11, 13, 15` rather than accumulating sourced detached images.
- Test-only weak references observe decoded images without retaining a hidden image batch. Production releases canceled speculation and removed presentation resources; no detached sourced speculative accumulation was observed. Separate delayed-preview browser checks verify that the production foreground is the same decoded element prepared before authoritative selection.
- This demonstrates bounded application resource ownership with larger images. It does not measure total browser-process RSS, browser/OS cache retention, or physical-device decode headroom. Crossfade and blur overlap can exceed two decoded images, as documented.
