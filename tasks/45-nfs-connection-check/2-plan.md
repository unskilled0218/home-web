## Current Boundaries

- `src/config.js:13-28` derives NFS configuration. A source defaults direct runs to mount mode; explicit disabled mode wins. Enabled modes require a mount path, mount mode requires a source, and unsafe options are rejected. Paths resolve relative to the process working directory.
- `src/nfs.js:13-40` parses mountinfo and combines VFS/superblock options, then requires `ro,nosuid,nodev,noexec,soft`, `timeo <= 50`, and `retrans <= 2`. Existing mode requires an exact visible mount point but currently does not require the filesystem type to be NFS. Mount mode requires NFS/NFS4 and exact source equality. These distinctions need evidence, not automatic relaxation.
- `prepareNfs()` validates mount topology and calls `stat()` in existing mode, but directory metadata alone does not prove traversal, enumeration, or image readability. Mount-command errors, topology conflicts, safety failures, and filesystem failures collapse to `{ available: false, reason: 'failed', root: null }`.
- `src/server.js:53-57` owns preparation through the shutdown coordinator, refuses unconfirmed helper cleanup, and logs one generic unavailable warning before creating an unavailable photo library. Disabled mode is intentionally quiet.
- `docker-compose.yml:20-25` defaults to `NFS_MOUNT_MODE=disabled`, uses `/photos`, and binds `${NFS_HOST_MOUNT_PATH:-./photos}` read-only. It does not forward a source for application-managed mounts. `Dockerfile` has neither an NFS client installation nor an added mount capability. Host-mounted existing mode is the documented container path; image user/export root-squash may affect access.
- `src/photo-library.js` resolves the root, opens directories/files without following symlinks, traverses through `/proc/self/fd`, enforces scan/file/cache limits, and returns unavailable on traversal failure. An available empty catalog is distinct from unavailable. Its scan deadline is checked between awaits, not a guarantee that a stalled kernel filesystem operation is cancellable.
- `public/dashboard-photos.js` validates the manifest, decodes images, skips failed decodes, and uses generic no-photo statuses. Photo-manifest APIs expose only availability, relative names, and opaque URLs; host/export paths and raw errors must stay out of public responses.
- `test/nfs.test.js`, `test/config.test.js`, `test/photo-library.test.js`, `test/dashboard.test.js`, process/lifecycle tests, and browser photo cases cover simulated boundaries. None establishes live access to this export. `docs/nfs-backgrounds.md` is the dedicated setup reference.

## Risks And Decisions

- The actual failure is not yet diagnosed. Compose disabled defaults, exact mount-point validation, missing mount clients, hostname reachability, version/path mapping, and root-squash are hypotheses, not confirmed defects. Evidence chooses the correction branch; a blocked diagnosis must not trigger speculative runtime edits.
- A read-only bind is not proof of bounded NFS retry behavior, and a readable local directory is not proof of the requested export identity. Check application-visible topology and operator-provided host evidence together without silently expanding the trust boundary.
- `stat()`, `opendir()`, `realpath()`, and file reads can stall below JavaScript. Hard deadlines require an owned execution/cleanup mechanism; this container's signal restrictions may require operator-run live access checks. Keep cooperative mocked/local tests distinct from claims about real NFS termination.
- NFSv4 may not publish the expected export through `showmount`, and its client-visible path can differ from the server dataset path. A discovery failure does not authorize changing TrueNAS configuration or trying unrelated exports.
- Documented diagnostics should remain specific to the observed failure. Avoid new dependencies, a diagnostics service, UI redesign, arbitrary source defaults, and unsolicited repairs to task 42/task 44 review findings.
