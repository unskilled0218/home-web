## Scope

Adopt the Bash/Python release workflow from `https://git.lan/dev/container-release-template` at commit `3c73528231ac1cbdd43600a5ca723390db804bac` (template version `0.5.0`). Replace home-web's archive-upload/rebuild workflow with one two-platform staging build, immutable digest verification, annotated version tags, digest promotion to `latest`, notes-only releases, and explicit package association checks. Preserve the Node 24 application image, root execution, runtime dependencies, host networking, persistent data, certificates, and optional photo mounts.

This delivery is validation-only adoption, not activation of live publishing. Keep the checked-in publication entry point disabled until separately reviewed changes resolve the known upstream blockers and establish server/package readiness. The planned publication sequence is exercised only through isolated fixtures in this task. Full operational release enablement remains pending; successful local adoption must not be reported as completion of that outcome.

This task changes release tooling, packaging metadata, tests, and documentation only. It does not change dashboard behavior, install host tools, provision credentials, publish a release, push source, delete historical assets, or repair existing remote state.

### 3. Replace the old publication path

1. Keep real publication unconditionally disabled as specified in step 1. In the underlying fixture-tested workflow, require clean, already-pushed `main`, exact remote destination/source agreement, committed release notes, and a builder advertising both platforms before publication. Run application tests separately before committing/pushing; the release command must not push `main` or embed application test hooks.
2. Add a bounded, read-only package-readiness check after source/credential preparation but before registry login, staging build, tag push, alias promotion, or release creation. Read the exact target repository and configured container package at the literal `latest` endpoint using the existing strict identity validators. An exact existing link passes without a version-dependent write decision. On `28.2.0` or another unsupported server, an explicitly unlinked or missing package must stop before publication writes; conflicting, malformed, unauthorized, or unavailable evidence must also stop. On supported stable `1.25.x`, an absent/unlinked package may proceed as a candidate for later association, subject to all existing final checks and exclusive-writer requirements. A package HTTP 404 is absence only after a successful HTTP read; failed reads never authorize continuation. Do not broaden the server allowlist or link during preflight. Keep this helper internal to the guarded workflow; do not expose an alternative publication entry point.
3. After readiness succeeds in fixtures, preserve the upstream sequence: bounded remote inventories and conflict classification; predecessor capture; verified staging reuse or one build from a private committed snapshot; exact annotated tag publication; digest promotion without rebuilding; notes-only release creation; fresh publication verification; package association and final checks. Preserve staging tags as recovery evidence rather than promising that `latest` is the only registry tag. Early readiness is not permission to skip fresh final association checks and does not eliminate the exclusive-writer prerequisite.
4. Preserve completed-retry verification and refusal of tag-only/release-only, old-format, conflicting, or changed-identity states. No force pushes, remote rollback, image deletion, asset replacement, unlinking, or automatic repair is allowed.
5. Preserve package identity checks and the existing exact-link read-only path. An unlinked package may be linked only under the upstream supported-server guard and exclusive-writer prerequisite; conflicting links must stop without reassignment.
6. Before retiring `scripts/check-build-platforms.js`, adapt the Python builder-advertisement parser to preserve the consumer contract: collect platforms only from explicitly running node blocks; combine running nodes; strip trailing stars; recognize canonical platform tokens and slash-delimited variants such as `linux/arm64/v8`; reject substring impostors, malformed output, stopped/error-only capability, missing platforms, and inspection failure. Keep strict published OCI index/config validation unchanged; normalizing builder advertisements is not permission to accept variant-bearing published manifests.
7. Remove `scripts/export_image.sh` and `scripts/publish_image_release.sh` from the supported release path and repository after checking active callers. Remove `scripts/check-build-platforms.js` only when no active caller remains and its characterization matrix passes against the new helper. Do not alter archived task records or delete existing ignored `dist/` artifacts.

## Acceptance Criteria

- The configured release targets only `dev/home-web` and `git.lan/dev/home-web`; no template target or private credential is committed.
- `VERSION`, npm metadata, configured notes, Git tag derivation, and effective image labels agree; drift fails an automated check.
- Local validation succeeds without credentials, network, Docker, or release-state creation; unsupported legacy arguments fail safely.
- The checked-in no-argument entry point unconditionally refuses before helper sourcing, credential access, prerequisite checks, lock/temp state, or external commands. No flag, configuration setting, environment variable, or alternate launcher enables publication. Only a separately reviewed code change may remove the guard after the activation prerequisites are met.
- Isolated temporary-copy tests demonstrate one multi-platform staging build, immutable verification, promotion without rebuilding, notes-only release creation, package-link guards, and conservative retry behavior. Their test-only guard removal cannot affect the real checkout or enable live publication.
- Early package-readiness tests prove that unsupported-server missing/unlinked packages, conflicting identities, and failed prerequisite reads cause zero publication writes. Exact existing associations remain read-only on `28.2.0`; final association checks remain mandatory after early readiness.
- The new builder preflight passes the explicit existing consumer characterization matrix, including variants, stars, multiple running nodes, stopped/error nodes, malformed output, inspection failures, and no publication writes on refusal. Published-manifest strictness remains unchanged.
- The existing Node 24 image and Compose runtime/data/network/mount behavior remain unchanged, except for corrected release metadata.
- Active tests/docs no longer prescribe archive uploads, inline token values, automatic source pushing, or rebuilding via `--promote-latest`; historical task files remain untouched.
- Application and release checks pass or have explicit prerequisite blockers. No remote publication, deletion, reassignment, source push, or credential provisioning occurs during implementation.
- Documentation explicitly distinguishes completed local adoption from blocked live publication readiness and states that the old publisher is retired while the replacement remains disabled. N1/N2 safety regressions and server/package readiness are mandatory prerequisites for a separate enablement change, not waived by local tests or an existing package link.

## Risks And Decisions

- **Observed server mismatch and early refusal (F1):** read-only `GET https://git.lan/api/v1/version` returned `28.2.0` during planning. The pinned template authorizes new package links only on stable `1.25.x`; an existing exact association is read-only and does not need that version guard. Preserve the final guard and add the read-only readiness check before any publication writes. A missing/unlinked package on this server blocks publication pending a separate review of server refusal semantics or an operator-approved association process with fresh identity evidence afterward. Neither this task nor preflight may create links, broaden accepted versions, or repair remote state. The global activation guard remains in force even if readiness evidence is correct.
- **Known upstream warnings and activation boundary (F2):** the pinned template documents N1, a later release guard accepting the predecessor after promotion, and N2, config-local Buildx plugin discovery changing under private auth. Retain an unconditional production publication guard until a separately reviewed fix or verified newer pin resolves both with the specified safety regressions. Fixing N1/N2 and removing the guard are not part of this adoption task. No operator bypass is supported; validation and isolated tests remain usable. This intentional temporary loss of live publishing must be recorded, not concealed as a completed operational migration.
- **Platform compatibility (F3):** adopt the old helper's explicit running-node and slash-delimited-variant advertisement semantics through a documented local parser adaptation. Preserve the characterization matrix before deleting old helper/tests; do not silently trade consumer behavior for a green upstream suite. Keep advertisement normalization separate from strict image identity/platform validation.
- **History compatibility:** existing home-web tags/releases use the old format. Leave them intact and start with an unused version; retries cannot adopt old evidence or changed script/config hashes.
- **Workflow compatibility:** archives and `--promote-latest` are intentionally retired to match the reference. Existing downloaded archives remain usable, but new releases are registry/digest based. Do not introduce a second maintained legacy workflow.
- **Version authority:** npm still requires version fields, so those fields become checked mirrors rather than independent authorities. Keep this check local to home-web rather than extending the template's strict configuration schema.
- **Operational limits:** the checkout lock does not serialize other checkouts or package UI actions. Trusted TLS, working emulation/native builders, private token provisioning, and exclusive writers remain operator responsibilities; no privileged setup runs automatically.
