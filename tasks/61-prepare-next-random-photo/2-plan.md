## scope

Implement nonrepeating metadata batches with one-image-ahead browser decoding. While one batch plays one image at a time, prepare the next metadata batch. Ten is an example rather than a required batch size. Global playback uses the complete eligible server inventory; Local playback uses its existing independent eligible manifest, currently capped at 100 images. Apply the same queue behavior to both owners without making Local browsers advance the Global cursor.

The existing implementation already avoids random repeats during an unchanged traversal and discovers files periodically. The missing pieces are explicit bounded current/next metadata batches, progress-preserving reconciliation when the inventory changes, an upcoming-image transport contract, and a retained decoded image that can actually be reused at presentation. `public/dashboard-photos.js` currently decodes only after selection, discards the decoded element, and `public/dashboard.js` constructs a new element for presentation.

## Implementation Plan

### 1. Define a shared metadata-batch sequencer

- Add a browser-safe `public/photo-batch-sequence.js` module, imported by both `src/photo-slideshow.js` and `public/dashboard-local-photos.js`. Keep selection policy separate from filesystem discovery, browser decoding, HTTP requests, and timers. Inject randomness and cooperative scheduling through the owners so tests can exercise exact traversal and delayed preparation.
- Own a current batch, one queued batch, remaining eligible identities, reserved identities, and visited identities for one cycle. Use relative filename as image identity; changing a URL or modification time must not make the same filename unseen again. Different filenames containing identical image bytes remain distinct files; do not read/hash image contents for duplicate detection.
- Draw random candidates without replacement using a remaining-index bag or equivalent bounded-work operation. Queue identities/references rather than copying complete photo records or image bytes. Mark a queued item reserved, and mark it visited only when the playback owner commits it as the current selection. A retry or continued display of the current frame is not a second selection.
- Choose a deterministic initial batch target of `ceil(30 / intervalSeconds)`, clamped to 1–32 images and the remaining unreserved count. Thirty seconds provides a preparation horizon; additionally cap combined current/queued projected metadata at 64 KiB, counting actual serialized UTF-8 photo metadata when admitting entries. Reduce batch size to fit rather than fixing it at 10. Keep these internal limits injectable for verification; no new saved preference or Settings control is required. Include queue/index/visited bookkeeping within the existing conservative metadata accounting allowance and measure the resulting actual memory use.
- Fill the next batch cooperatively as soon as the current batch begins playing; allow at most one fill job per owner. Bootstrap the first selection promptly, then fill its remaining batch and the queued batch without blocking the first image on a complete batch. Queue preparation reads only discovered metadata, never `/photos` or image bytes.
- When fewer unseen images remain, produce a smaller final batch. Do not start another cycle merely because all remaining images are reserved: wait until the last outstanding selection in the current cycle has been committed. Then refill during that last image's display. Avoid choosing that last filename as the first selection of the next cycle when two or more eligible filenames exist. Empty and single-image pools must not spin or invent duplicates.
- Retain name/date ordering as explicit modes using the same queue ownership where practical; their batches must follow the existing sort semantics. Changing order intentionally starts a new traversal. Interval-only changes update deadlines and future batch sizing without resetting visited progress or changing an already published next selection.

### 2. Integrate batch ownership and inventory reconciliation

- Replace the full shuffled-record `sequence` in `src/photo-slideshow.js` with the shared sequencer. Keep server-owned rotation, zero-viewer operation, pure snapshot reads, and the existing 60-second discovery cadence after each scan settles. Missing Global preferences must still allow discovery and cached Settings/Local access while Global selection remains paused.
- Commit each due selection from the queue once, preserve the last displayed/current selection while metadata preparation is pending, and retry a failed fill within five seconds with one owned retry. If a deadline arrives before any next metadata is ready, retain the current selection and rearm a bounded retry rather than emitting an empty selection or advancing twice. Do not tie queue progress to the number of HTTP readers.
- Reconcile completed inventory changes by relative filename. Preserve visited progress for surviving files, retain surviving reservations in their existing order, drop deleted/ineligible names, and admit newly eligible names into the unreserved remainder. Remove identities no longer in the eligible pool from retained bookkeeping so repeated changes cannot grow a permanent history. Unchanged content revisions must preserve batches, next preview, and rotation deadlines.
- Resolve queued filenames against the active inventory when projecting metadata and committing selections. Update preview metadata when a surviving file's URL changes, without resetting its visited state. Do not retain obsolete full inventory generations just to keep long-lived queued URLs valid: the library's previous-token grace is only 30 seconds, while an interval can be 3,600 seconds. A disappeared current file selects an eligible replacement when possible; confirmed empty/disabled sources retain their existing authoritative clearing behavior.
- Integrate the shared sequencer into `public/dashboard-local-photos.js` with the same reservation/cycle rules over its manifest. Manifest changes reconcile rather than blindly rebuilding a shuffled sequence. Opening/closing Settings or changing presentation preferences must not reset either playback owner's progress.
- Stop/dispose must cancel pending fills/retries, retire their generation, release queues, and await actual outstanding cooperative preparation work where the owner exposes a drain. A late fill must not publish after stop, scope replacement, or disposal. Keep library scan drainage and the existing HTTP/SQLite shutdown order intact.

### 3. Publish bounded next-image metadata

- Extend `public/photo-slideshow-data.js` with an explicit version-2 snapshot: the version-1 fields plus `next` and a nonnegative safe-integer `queueRevision`. `revision` continues to identify current-selection changes; `queueRevision` advances whenever the advertised upcoming metadata changes. Validate both current and upcoming records with the existing filename/token rules and retain the 8,192-byte serialized snapshot limit.
- `next` is either one eligible upcoming record or null while preparation is pending. It is always null for disabled/unavailable/empty/single-image pools and must name a different file from `current` for multi-image pools. Validate version-2 field sets and relationships independently of the strict version-1 contract. A prepared preview is never permission to display early.
- Add opt-in `GET /api/dashboard/slideshow?version=2` handling in `src/app.js`, backed by a pure `snapshot({ version: 2 })` projection from the owner. Keep the default endpoint's strict version-1 response for existing callers; reject unsupported explicit versions with a bounded 400 response. Preserve method, host/origin, cache, and read-only behavior. Do not serialize either metadata batch or the full inventory to Global viewers.
- Update `public/dashboard-photos.js` to request version 2, accept validated version-1 responses as a no-prefetch compatibility path, and track current and queue revisions per server instance. Reject old current revisions, old queue revisions, retired instances, and inconsistent metadata at an unchanged revision. A newer preview alone must not re-render the current frame or restart its transition.
- Make the Local follower's synthetic snapshot version 2 with its own next preview and queue revision. Update `test/fixtures/photo-slideshow.js`, `e2e/photo-fixtures.js`, and direct request interceptors to recognize the versioned query and provide explicit preview metadata when testing lookahead. Retain version-1 coverage rather than weakening strict validation to accept arbitrary extra fields.

### 4. Decode and retain exactly one upcoming image

- Refactor the decoder/controller boundary in `public/dashboard-photos.js`, extracting a small `public/dashboard-photo-decoder.js` owner if useful. A successful decode must return a retained image resource, not only a resolved promise. Keep one upcoming resource and at most one active decode operation; an urgent current-image decode takes priority over speculative next-image work.
- After the current image is successfully displayed, prepare only the advertised immediate next image. Repeated metadata polls for the same upcoming identity must reuse its pending or ready resource. Future batch entries remain metadata-only; do not fetch/decode every image in a batch. If metadata arrives before the current decode finishes, queue its intent and prepare it after that decode settles.
- When the owner selects the prepared next identity, transfer its already-decoded element to presentation without decoding it again. Update `public/dashboard.js` to adopt that element instead of constructing another foreground `Image`. Define resource ownership explicitly: the prefetch owner releases canceled/unpromoted resources; the view owns promoted elements and releases them when their layers are removed. Presentation-only updates must reuse the current element.
- Keep at most one foreground layer plus the existing single outgoing transition layer; release canceled/completed transition resources and any associated blur layer. One upcoming decode slot is additional to those presentation layers. Do not claim total decoded memory is exactly two images during crossfades or blurred rendering, and do not create a hidden decoded batch.
- A warm image must remain undisplayed until the authoritative current selection matches it. Global browsers continue following server selection deadlines; they do not independently advance a batch or send readiness acknowledgements. If a browser falls behind, it adopts the current server selection and retires obsolete lookahead rather than playing missed queue entries locally.
- Preserve the current frame on upcoming/current preparation errors. Retain ten-second decode deadlines and a retry within five seconds of failure settlement while the same work remains relevant. Failed speculative preparation must not clear the frame, overwrite the persistent image count, or cause an early transition. If its image becomes current, reuse valid in-flight work or retry with current priority. The Global schedule continues independently of one browser's decode failure.
- Changing scope, instance, source identity, current/next filename or URL, or page visibility must retire affected work and reject late results. Unchanged current metadata must not cancel a valid current decode just because its preview changed. On hidden/persisted-page suspension release speculative resources; resume from a fresh snapshot. Disposal cancels metadata/decode/retry timers and prevents later DOM publication.

## Acceptance Criteria

- Batch size is determined by a documented preparation horizon and entry/byte bounds rather than a literal requirement of 10 images. Only current and next metadata batches are queued; future metadata does not trigger bulk image reads.
- For a stable eligible pool, the authoritative random selection sequence visits every filename exactly once per cycle across all batch boundaries, including a smaller final batch. The next cycle avoids an immediate boundary repeat when at least two files exist. Current-frame holds and retries do not consume another identity.
- While a current batch plays, its owner prepares the next metadata batch. Browsers decode at most one upcoming image and promote its retained element only after that filename/URL becomes current. Failed preparation keeps the current frame visible and retries with bounded ownership.
- Default version-1 clients remain supported; version-2 snapshots provide at most current and next metadata within 8,192 bytes. Polls, speculative decoding, and Local playback cannot advance the Global cursor or trigger extra directory scans.
- Unchanged inventory refreshes and interval/presentation changes preserve random-cycle progress. Additions, deletions, and metadata replacements reconcile explicitly without replaying an already visited surviving filename. Long-lived queues cannot depend on expired tokens or retain obsolete inventory generations.
- Unit/API/controller/browser checks cover queue boundaries, resource reuse, failures, and cancellation. Resource benchmarks meet their stated limits; all verification outcomes and any baseline/environment failures are recorded honestly.

## Risks And Decisions

- Batching is a selection/preparation policy, not a way to avoid full metadata discovery. The server still needs the complete eligible inventory for complete Global coverage and exact no-repeat tracking; queue metadata and image pixels have separate budgets.
- The no-repeat guarantee applies to each playback owner's committed selection sequence. A hidden/offline/slow Global browser may miss selections, and a corrupt file may never decode; there is no all-browser display acknowledgement. Keeping a prior frame visible during a failure is intentional, not a duplicate queue entry. Tests must distinguish healthy traversal coverage from failure recovery.
- Global's full eligible inventory and Local's bounded eligible manifest define different playback pools. Batch size does not alter discovery count or expand Local's 100-image transport contract. The persistent Settings count remains the complete Global inventory count.
- A changed filename is a new identity; a changed URL at the same filename is not. Continually changing libraries can extend a cycle, so exact once-per-cycle coverage is specified for a stable pool and reconciliation is tested separately. Changing the configured order or restarting a process deliberately starts a new traversal.
- Current-selection revision and preview revision are distinct. Preparing the next batch must not masquerade as a new current selection, and preparing an image must never become a client-owned Global rotation clock.
- Decoded image size can greatly exceed compressed file size. Stable application ownership is current presentation plus one upcoming resource, with a bounded outgoing/blur presentation overlap during transitions; batch size must never multiply decoded resource ownership. Actual device/browser measurements remain necessary for physical memory guarantees.
