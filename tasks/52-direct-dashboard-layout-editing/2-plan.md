## Scope

Replace the Settings widget layout editor with direct dashboard editing. Long press enters edit mode and selects a widget; an accessible Edit layout button provides an equivalent entry. Users move/resize widgets in place, select covered widgets, change layers/profiles, reset to Automatic, and explicitly Save or Cancel. Reuse existing canonical geometry, reference sizing, and shared settings transactions. This planning stage changes only this document.

## Current Boundaries

- `public/dashboard-layout.js` already supplies six identities, version-2 bottom-left unit records, strict normalization, reference-space projection, field-specific edits, templates, layer operations, and uniform canvas fitting. Keep those contracts rather than restoring legacy collision relocation or inventing a pixel persistence format.
- `public/dashboard-layout-view.js` owns live node relocation, reference/destination measurement, the transformed stage, and a single reference lock. It currently accepts confirmed layouts through `update()` and notifies the Settings editor through `onMeasure`. It needs an explicit temporary presentation override, not mutation of global confirmed `settings`.
- `public/dashboard-layout-editor.js` currently owns a Settings-only draft, a scaled label preview, numeric fields, and pointer capture. Repurpose this module as the sole direct editor; do not keep a hidden preview editor or duplicate draft controller.
- `public/dashboard.js:52-82,240-271` currently fills/reads layout drafts with the general preference form, forwards every synchronization state to `setSaving()`, and validates old preview fields. Settings open/close also acquires/releases the reference lock. Remove those layout-specific links while preserving unrelated scalar/selection/integration drafts and stale-save ownership.
- `public/dashboard-settings-sync.js` is the single snapshot/cache/poll/write owner. Its save validates complete preferences and checks the captured revision; a 409 can accept the latest confirmed snapshot before rejecting the write. The new editor must distinguish that confirmation from its local draft.
- Live actions include selected bookmark links and `createDashboardDeviceView()`'s injected Wake callback. Home Assistant dashboard rows currently display readings, not action buttons. Guard existing action boundaries without adding new Home Assistant controls or stopping pending actions/providers.
- `.page-tools` currently hides in ordinary fullscreen, and the view reserves only tools/status/caption destination space. Direct editing requires a reachable fullscreen entry/toolbar and measured toolbar space outside the scaled stage. Existing layout browser tests use the Settings preview; migrate their behaviors to direct editing rather than discarding them.

## Design Decisions

### One session, one writer, two presentation states

- Keep confirmed preferences in the existing synchronizer/coordinator. Direct editing owns only an immutable entry baseline, captured revision, cloned `widgetLayout` draft, selected profile/widget, raw geometry inputs, gesture, and session generation. Pass saves to the existing `settingsSync.save()`; do not create an endpoint, table, cache key, polling loop, or second network owner.
- While editing, project the draft onto the actual live nodes through the layout view's temporary override. Never assign the draft to confirmed `settings`, cache it, or configure service controllers from it. Other browsers continue to see confirmed data. Cancel removes the override and shows the latest confirmed layout, including remote changes accepted during editing.
- Capture complete normalized preferences and revision on entry. Save changed layout preferences as `{ ...entryPreferences, widgetLayout: draft }` with that revision. If any remote preference changed, let the existing whole-record 409 protect unrelated fields. Do not merge a newer revision silently or rebuild a stale submission from newer scalar preferences. Explicit Reload shared layout discards the local layout/raw inputs and adopts the newest complete confirmed baseline and revision.
- No-op Save exits without a PUT when the canonical layout is unchanged. Merely entering, choosing a widget/profile, or viewing an Automatic template is not a canonical change. Changed Save disables all editing, Reload, Cancel, and exit transitions until the existing write settles; aborting a request is not proof that the server did not commit it. Success adopts the confirmed result and exits; network/validation/409 failure retains the draft, original base revision, action blocking, and actionable status. Do not auto-retry mutations.
- Permit local editing of a displayed offline cache, but capture no writable base revision unless the server is confirmed. Save stays disabled until an explicit Reload shared layout adopts a confirmed snapshot; a background confirmation alone must not rebase the draft. A confirmed uninitialized server may use its existing revision-0 save contract. Keep existing legacy initialization behavior owned by the synchronizer, not the editor.
- Settings and direct editing are mutually exclusive. Do not enter direct editing while Settings is open or another shared preference write is pending. Disable/guard Settings entry during direct editing with a clear Save or Cancel message; do not open a second dialog or discard either session implicitly. Repeated Edit layout/long-press activation while editing only focuses/selects within that session, never reloads its baseline.

### Automatic profiles, inactive profiles, and reference ownership

- On entry, select the actual viewport profile and targeted widget, defaulting to Time for button entry. Keep both saved profiles in the draft. Pin the selected edit profile until the user changes its selector, even if viewport resizing crosses 600px; clearly label when editing an inactive profile.
- For an Automatic profile, show a deterministic bounded template from `initialWidgetProfile(mode, confirmedPosition)` on the dashboard as a local editing aid. Keep its canonical draft value `null` until an operation actually changes geometry/layers or the user explicitly chooses Custom. Show a clear message that the template is temporary and moving/resizing creates a Custom draft. This can temporarily rearrange an Automatic dashboard on entry; it is not saved, and Cancel/no-op Save restores confirmed Automatic flow.
- Compare operations against the effective template before materializing a Custom profile, so a no-op/clamped/canceled gesture or boundary layer action cannot turn `null` into Custom. Reset selected profile sets only that draft profile to `null` and discards its template edits. The toolbar provides an Automatic/Custom arrangement selector and Reset selected profile; no equivalent layout editor remains in Settings.
- The edit profile controls geometry/reference selection only. Keep live visibility, font preferences, content selections, and service eligibility based on actual confirmed display state. Editing an inactive or hidden widget must not enable providers or alter shared visibility. Represent hidden widgets with labeled editing placeholders rather than exposing/fetching hidden content.
- Acquire the existing reference lock exactly once on edit entry; release it exactly once after restoring confirmed rendering on exit/disposal. Settings no longer owns a layout-reference lock. Display/orientation/fullscreen confirmations queue behind the edit lock as in task 51. Keep reference dimensions frozen for both profiles; destination fitting and toolbar measurement may still change.

### Safety and interaction model

- Use separate unscaled editing chrome outside the real widgets: a persistent toolbar and six fixed-position frames projected from the same reference rectangles and fit as the live canvas. The frames own labels, selection, movement, and the selected widget's upper-right resize handle; they contain no cloned bookmark links, device controls, or private content. Their layer order follows the same canonical array. Hidden-widget placeholders are explicitly labeled and exist only in edit mode.
- Make every real widget root `inert` for the entire edit session and retain its prior inert state for restoration. Put editing chrome outside inert roots. Add narrow capture guards for activation/navigation events originating in those real widget subtrees, plus an edit-state guard at the injected Wake dispatcher. This protects keyboard, pointer, delayed clicks, and stale row handlers without rewriting button disabled state or interrupting an in-flight Wake. Do not block toolbar/fullscreen actions or unrelated browser interactions globally.
- Keep the Edit layout action reachable in fullscreen. Add it to page tools and adjust fullscreen tool rules so this action remains visible, while preserving existing immersive hiding of other tools and the background-only tools exception. Show the edit toolbar outside `.page-tools` and the scaled stage. During editing, disable Settings/entry controls as appropriate and offer a toolbar fullscreen toggle through the existing Fullscreen API handler.
- Reserve the toolbar's actual bottom edge in destination measurement before placing the stage or frames. Keep chrome above all widget layers with its own bounded stacking context. Cap toolbar height and allow internal toolbar scrolling on narrow/short screens so Save/Cancel remain reachable without scrolling the scaled dashboard. When no destination/reference space remains, disable geometry handles/inputs and retain safe exit/reload controls.

## Implementation Plan

### 1. Establish task ownership and a cancellable activation controller

- During implementation, create branch `52-direct-dashboard-layout-editing` from the task-bearing HEAD and create `4-implemented.md` with a table of contents. Preserve unrelated work and historical task documents. Do not change application code in this planning stage.
- Add `public/dashboard-layout-activation.js` for long-press ownership only. Inject scheduling/cancellation and activation eligibility callbacks so unit tests control time. Delegate from stable document/root listeners, locating actual widget IDs through `WIDGET_ELEMENTS` in either Automatic or Custom parents. Do not register handlers on transient rendered device rows or duplicate timers per widget.
- Arm one 600ms timer for a primary button-0 pointer on an eligible widget background. Treat movement of at least 8 CSS screen pixels as cancellation, independent of canvas scale. Exclude interactive descendants using the composed path bounded by the widget root: links, buttons, form controls, labels/summary, editable/draggable content, media/embedded controls, focusable descendants, and actionable ARIA roles. Do not exclude the widget itself solely because it received temporary focus for restoration.
- Do not prevent default or take pointer capture during the hold; retain native scrolling. Observe pointer release/movement/cancel at document scope and capture-phase scroll events, including internal widget scrolling. A second simultaneous pointer cancels a pending hold rather than initiating a competing activation; non-primary events cannot arm one. Cancel on window blur, hidden page, pagehide, target removal/hidden state, conflicting Settings/save state, and disposal.
- Give timers a generation token. Before firing, recheck connection, visibility, eligibility, actual hit target at the pointer position, current page/session state, and the original widget. Reparenting or overlapping content must not make an old timer select an obscured widget. Clear all listeners/timers and reject late callbacks after disposal.
- Narrowly suppress a matching eligible pending/consumed hold's context menu; do not disable context menus on links, controls, or the entire dashboard. Avoid `touch-action: none` outside editing affordances. Preserve existing noncollapsed text selection rather than hijacking a copy gesture. Evaluate a pending-only touch-callout class if required by supported engines, documenting any platform limit.
- After activation, wait for the initiating pointer's release before allowing a move/resize. Consume that release and its matching compatibility click/context menu so a newly placed handle or toolbar Save cannot receive click-through. Scope suppression to that pointer sequence/location with bounded cleanup; keyboard clicks and later unrelated clicks must work. Add deterministic tests for stale timers, movement, nested scrolling, second pointers, eligibility changes, context menu scope, and release/click suppression before wiring saves.

## Acceptance Criteria

- Long press and keyboard-accessible Edit layout enter the sole direct dashboard editor, selecting the intended visible target/profile without accidental device/navigation actions. Context menu, native scrolling, early release, movement, and lifecycle cancellation remain safe.
- No layout editor remains in Settings. Unrelated Settings saves preserve complete confirmed layout fields and existing stale-revision protection; other settings/integration functionality remains intact.
- Direct frames and live draft use one accepted reference and actual fit scale. Movement, resizing, layering, profile selection, hidden placeholders, Automatic templates/reset, and numeric alternatives preserve canonical field/no-op/cancel invariants and tiny-surface containment.
- The persistent fullscreen-accessible toolbar exposes Save/Cancel and recovery controls. Real dashboard actions remain blocked by pointer and keyboard until edit mode fully exits; existing pending actions still finish exactly once.
- Only explicit changed Save publishes a draft through the existing writer/revision contract. No-op Save, entry, selection, gestures, refitting, and Cancel do not write. Remote updates and failed/stale saves cannot erase the draft or silently rebase it; explicit Reload adopts the newest baseline.
- Settings/edit sessions and reference locks cannot overlap incorrectly. Polls and measurement callbacks preserve focused raw entries, active gesture ownership, and captured revision in the replacement editor. Complete cleanup restores confirmed rendering, focus, inert state, and observation ownership.
- All previous relevant layout/settings safety regressions remain covered through the replacement, with new deterministic and real-browser action-blocking/long-press coverage. Focused/full verification and syntax/diff checks pass with honest environment limits.

## Risks and Limits

- Direct editing deliberately previews unsaved geometry on live content. Keep the mode unmistakable and all actions inert; never publish that local presentation as confirmed shared state. Do not solve conflicts by auto-merging complete preference records.
- Automatic flow is not an invertible reference layout. A temporary deterministic Custom template is an explicit editing aid, not a promise to preserve every Automatic pixel on entry. No-op/canceled operations must keep its saved `null` value unchanged.
- Transformed cards make unscaled editing targets and exact pointer conversion important. Avoid mixing reference pixels, canvas pixels, viewport offsets, and device pixels or adding post-fit card minimums. Tiny windows may require numeric editing or enlargement rather than usable drag handles.
- Browser touch callouts, compatibility clicks, pointer cancellation, and text selection differ across engines. Keep suppression narrow and test trusted input. Do not claim pen hardware, mobile Safari, or OS/browser-chrome shortcuts were verified by synthetic desktop events.
- `inert` alone does not guard programmatically dispatched events; capture guards and the actual action boundary must also reject edit-time activation. Do not mutate per-row disabled state that pending controllers own or stop those controllers to fake safety.
- The session and toolbar add state, but existing save, provider, reference, and geometry owners remain authoritative. Favor small activation/editor/view boundaries over a generic interaction framework. Removal of Settings layout coupling is authorized; unrelated polling/integration redesign is not.
- No new persistence schema, runtime dependency, real Wake packet, live provider account, NFS mount, privileged change, user-data/configuration edit, retained legacy-layout deletion, or `todo.md` edit is authorized.
