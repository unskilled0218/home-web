# plan

## scope

Add optional, independently saved desktop/mobile arrangements for the six live dashboard widgets, with intentional overlap, plain-language layer controls, free pixel-based editing, and current-window size bounds. Extend the existing shared preferences/revision owner, not the retired home layout/settings API. Keep automatic layout as the default and reset target so existing installations retain their current presentation until a user explicitly enables a custom profile. This stage writes only this plan; it does not modify implementation, dependencies, version, user settings, or runtime data.

## Current Boundaries

- `public/index.html:14-32` groups Calendar/Time/Weather and the photo caption under `#information`, Home Assistant/Wake-on-LAN under `#dashboard-devices`, and Bookmarks in a sibling aside. `public/dashboard.css` gives those groups their own stacking contexts and changes their flow at 1000px/600px. Individual widget rectangles cannot currently overlap across groups.
- `public/dashboard-helpers.js` owns the complete preference schema, normalization, strict writes, old-record/cache decoding, and the shared mobile boundary `(max-width: 600px)`. Its strict scalar comparison must explicitly support any new nested layout field; normalizing a new object and comparing object references would reject valid writes.
- `src/dashboard-preferences.js` persists the preference JSON in SQLite with one revision, initialize-once semantics, and conflict-checked updates. `src/app.js:330-346` already validates bounded shared-setting requests and returns canonical snapshots/409 conflicts. No new table or persistence endpoint is needed.
- `public/dashboard-settings-sync.js` owns confirmed snapshots, cache, polling, request deadlines, and revision-based saves. `public/dashboard.js:188-249` applies snapshots while preserving dirty Settings drafts, and serializes the existing form plus non-scalar selections. A nested layout draft must join that save path explicitly rather than becoming a form string or a second writer.
- `applyDashboardDisplay()` is deliberately DOM-only and is also called from photo/caption updates. `applyPresentation()` currently reorders information sections when the active profile changes and restarts the clock. Layout projection must not route every resize, caption change, or pointer movement through those service-affecting paths.
- `public/home-layout.js`, `src/home-settings.js`, and `/api/home/settings` are retained legacy functionality. Their collision avoidance, canvas growth, larger minima, and 768px breakpoint are not suitable for this feature and remain untouched.

## Design Decisions

- Use 100px × 100px as the minimum displayed widget rectangle for every type. Content can scroll internally; widget dimensions do not imply that all content must fit without scrolling. If the usable surface is smaller than 100px on an axis, use that axis's available size as its temporary minimum/maximum instead. Do not reintroduce the old 120px/180px widget-specific minima.
- Store bounded proportional geometry, but expose/edit pixel values. This lets the same saved desktop profile fit different desktop windows without any resize-induced write. Use integer units on a fixed 1,000,000-unit square, not viewport-sized server state or floating-point CSS values. A profile has exactly six unique widget records in back-to-front order, each `{ id, x, y, w, h }`, with integer coordinates/sizes, positive sizes, and `x + w`/`y + h` within that fixed range. Layer is array position, not an additional independently drifting z-index field.
- Add one nested preference, `widgetLayout: { version: 1, desktop: null | profile, mobile: null | profile }`. `null` means existing automatic layout. A non-null profile contains `items` in canonical property order; accepted array order is deliberately meaningful. The current mobile boundary remains inclusive at 600px. Both profiles retain records for all six widgets even when visibility preferences hide some of them.
- Project saved unit geometry into the current usable surface: round to CSS pixels, clamp each displayed width/height between `min(100, availableAxis)` and the available axis, then clamp its position so the complete rectangle remains reachable. Never mutate the saved object during projection. Pixel edits map only the edited widget back into units using the current surface dimensions; layer edits only reorder records. Unedited widgets and the other profile remain byte-equivalent in the canonical draft. Allow one-pixel controls with at most one-pixel round-trip tolerance from rounding.
- The usable surface is the current visible dashboard area after reserving page tools/status, safe-area margins, and a bounded displayed photo-caption strip. It must not exceed the window or grow with widget contents. Measure availability independently of hidden widget/content wrappers so users can configure layouts when all six widgets are hidden. A genuinely zero-sized/unavailable viewport defers measurement and disables direct edits rather than dividing by zero or saving fabricated dimensions. Resize/fullscreen/orientation changes affect presentation only.
- Put the editor in Settings → General using the existing modal and Save preferences flow. Its scaled, labeled preview supports dragging/resizing without cloning live links, controls, or provider content. Pixel fields provide an exact alternative; a list selects covered/hidden widgets. This avoids putting actionable dashboard content into an editing drag surface or creating a separate nonmodal draft/save owner.

## Implementation Plan

### 5. Integrate draft, save, cancel, and conflict behavior

- Initialize the editor's draft from confirmed or displayed cached preferences alongside the existing form. - Explicitly merge `editor.getDraft()` into the preferences submission before normalization; do not serialize nested layout data from HTML control strings. Preserve confirmation/error messaging and the existing single pending-write owner.
- Keep live dashboard geometry confirmed until a successful save; use the preview for unsaved geometry. This prevents a failed save from advertising a shared arrangement or changing live controls underneath the user. On successful save adopt the canonical server layout and clear the submitted draft only if it is still the same owned save. Failed/409 saves leave the layout and other form drafts intact; a remote snapshot may update the live dashboard but must not overwrite dirty editor values or silently advance their base revision.

Cancel layout edits restores only the layout portion to its editor-session baseline while retaining unrelated preference drafts and their dirty status. Recompute dirty state from actual draft differences so canceling layout edits does not accidentally clear another changed field.
- Reset changes only the chosen profile and remains a normal unsaved draft until Save preferences. A save conflict never automatically rebases the entire preference object onto a newer revision. Preserve existing global initialization and legacy-cache authority rules.

## Acceptance Criteria

- Existing dashboards remain in usable Automatic mode until customized; confirmed custom desktop/mobile layouts survive restart and converge across browsers through the current shared settings revision owner.
- Users can place/resize all six widgets freely, overlap them intentionally, select a fully covered widget, and change front/back order without knowing CSS z-index or displacing unrelated widgets.
- Pixel controls and direct preview manipulation enforce 100×100px displayed minima where space permits and a current-window-bounded maximum. Every widget remains reachable on smaller windows, and large content/actions remain accessible within its rectangle.
- Normalized saved geometry is deterministic and independent of rendering viewport. Projection, selection, profile/fullscreen/orientation changes, and photo callbacks do not write settings or mutate saved state. A layer-only edit does not change geometry; editing one profile/widget does not silently alter the other profile/widgets.
- Settings save/cancel/reset/reload/conflict behavior is explicit and preserves unrelated drafts/preferences. A failed save never presents the unsaved arrangement as confirmed shared state.
- User layers cannot cover Settings/tools/status; the photo background/caption, visibility flags, existing integration controls, selected links, and Wake safety continue to work. Layout-only changes do not restart controllers/timers or introduce provider demand.
- Focused/full unit/API/browser verification passes with honest prerequisite limits. Old settings upgrade without read-time writes or lost selections/credentials, and the retired home-layout/settings path is not revived.

## Risks And Decisions

- A shared server cannot validate dimensions against every client's current window. Bounded proportional geometry plus a shared pure pixel projection enforces physical min/max locally without trusting a client-supplied viewport or writing per-client resize state.
- 100px widgets cannot display every forecast/control simultaneously. Scrollable content and compact/wrapping presentation are the chosen tradeoff; no automatic card growth, text-scale replacement, or hidden critical controls is acceptable.
- Existing wrapper stacking contexts and responsive flow rules are the main DOM/CSS risk. Establish one custom layer surface and test all widget types across the current breakpoints; do not apply a z-index number to nested groups and assume cross-group ordering works.
- The automatic fallback and null profiles intentionally avoid forcing a lossy migration of the current flow layout into fixed geometry. Reset returns to that existing responsive arrangement, not a blank layout or the archived widget defaults.
- Preview manipulation uses the same pixel projection as the live view but no live service controls. A smaller screen edits either profile relative to its current available window; only explicit widget edits are mapped back into saved units, preventing unintentional whole-profile rebases.
- Nested preference handling and mixed dirty drafts require explicit ownership. Keep one server revision/cache/save flow and a testable editor draft; do not add layout autosave, a second preference endpoint, a generic widget registry framework, or archived cleanup remedies.
