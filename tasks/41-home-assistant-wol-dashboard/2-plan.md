# plan

## scope

Implement `1-goal.md`: add a middle dashboard column with Home Assistant above Wake-on-LAN, persist Home Assistant device selections globally, display selected device readings, and add name-and-Wake rows for saved Wake-on-LAN devices. Keep Home Assistant display read-only. Preserve connection settings, device CRUD, encrypted credentials, wake auditing, photos, other dashboard sections, and existing display preferences. Do not restore the retired widget-layout system or change `todo.md`.

## Current Structure

- `public/index.html` puts calendar, clock, and weather inside `#information`, followed by the bookmarks aside. `public/dashboard.css` creates a two-column desktop grid only while `.bookmarks-shown` is present; hiding bookmarks in fullscreen currently removes that grid. Mobile uses a 600px breakpoint.
- `public/dashboard.js` owns presentation, the shared-preference draft, Settings lifecycle, visibility, and back-forward cache handling. Its form serialization assumes every preference is a scalar form control, and preference change detection uses reference equality.
- `public/dashboard-helpers.js` requires an exact preference schema. `src/dashboard-preferences.js` strictly validates persisted JSON on reads. Adding a preference without an explicit compatibility path would make existing records unreadable.
- `public/dashboard-integration-settings.js` currently creates and owns dialog-only Home Assistant and Wake-on-LAN controllers. Its poller runs every five seconds only while Settings and the page are visible. `public/dashboard-configuration.js` supplies read ownership, mutation exclusion, and timeouts.
- `GET /api/home-assistant/devices` already returns stable device `selectionId` values derived from the canonical Home Assistant origin and raw device ID. It also returns bounded sensor readings and opaque control tokens. Device selection IDs survive renames, token replacement, and restarts; a different origin produces different IDs. Do not expose raw device/entity IDs or persist control tokens.
- Home Assistant device responses currently lack a public connection-generation identity and a server-side check for connection changes during an awaited read. Calendar and Linkwarden already demonstrate this protection in `src/app.js`.
- `POST /api/devices/<id>/wake` already enforces cooldown and records attempts. It returns HTTP 429 with a human-readable cooldown error, not a structured retry duration. Keep that contract unchanged.

## Implementation Plan

### 1. Extend shared preferences without breaking stored settings

- Add `homeAssistantDeviceSelections`, defaulting to `[]`, in `public/dashboard-helpers.js`. Store only device `selectionId` strings matching the existing `d_` plus 43-character base64url hash format. Bound selection to 256 devices, reject duplicates and malformed values on writes, and canonicalize ordering so equivalent selections compare equal. Explain the limit in Settings rather than silently dropping selections.
- Keep scalar preference normalization unchanged. Add explicit structural validation and value comparison for the selection array; do not compare arrays by reference. Ensure initialization, cache validation, snapshot validation, legacy migration, and no-op saves accept a canonical array without losing other preferences.
- Add a stored-record decoder in `src/dashboard-preferences.js` that recognizes the exact previous preference schema, validates every previous field, and supplies only the new empty selection default. Preserve existing initialization status and revision. Reads must not rewrite rows. Subsequent changed saves persist the complete new schema through the existing transaction and compare-and-swap revision check. Reject corrupt JSON, unknown fields, and malformed new selections rather than replacing them with defaults.
- Accept the exact previous schema for old shared browser-cache decoding, with empty selections, while retaining strict complete-schema validation for new API writes. Older loaded clients must reload before saving; do not let a missing selection field erase newer selections. Keep cached preferences non-authoritative until the server confirms them.
- Keep selections in the existing `dashboard_preferences` JSON record. No new selection table, browser-only selection store, or raw connection URL preference is needed because existing selection IDs are already origin-scoped. At maximum selection count, the complete preferences and conflict snapshot must remain within the existing 65,536-byte request/response limits.

### 2. Give Home Assistant reads a public connection identity

- In `src/app.js`, add `homeAssistantConfigurationId()` following the existing calendar identity pattern: a SHA-256 base64url hash of a versioned discriminator, saved origin, and encrypted credential record, or `null` when absent. Include this opaque identity in public Home Assistant status and device responses. Do not derive a new public token directly from plaintext credentials.
- Capture connection identity before awaiting Home Assistant device retrieval. Recheck it before returning a successful snapshot or reporting a read failure. If configuration changed, return HTTP 409 with `HOME_ASSISTANT_CONFIGURATION_CHANGED`, and do not issue control tokens for an obsolete snapshot. Return the current captured identity with configured/unconfigured results and ordinary failures.
- Keep successful connect and disconnect response contracts compatible, adding identity where applicable. Update `public/dashboard-home-assistant.js` to decode public identity and set it to `null` after confirmed disconnect. Failed connects retain the last confirmed identity and configuration.
- Selection identity and connection identity have different purposes: selection IDs remain stable for the same origin when credentials change; configuration IDs invalidate in-flight reads and cached measurements when credentials change. Disconnect clears visible readings but does not implicitly write preferences. Reconnecting the same origin restores still-saved matching selections; connecting another origin never reinterprets them as devices from that instance.
- Keep `/api/dashboard/settings` integration metadata unchanged. The shared Home Assistant status controller described below supplies connection observation, so this task does not require a second Home Assistant metadata path through the settings snapshot.

### 3. Share integration state between Settings and dashboard

- Add a small subscription mechanism to `public/dashboard-configuration.js`, retaining its existing `onChange` API for current callers and tests. Allow `createIntegrationSettings()` to receive Home Assistant and Wake-on-LAN controllers instead of always creating private instances. Keep a default owned-controller path for isolated Settings tests; injected controllers belong to their caller and must not be paused or disposed when Settings closes.
- Introduce `public/dashboard-devices.js` as the dashboard integration coordinator. It owns the shared Home Assistant status and Wake-on-LAN controllers, the existing five-second integration poller, a Home Assistant snapshot reader, and wake-request state. Pass its controllers into Settings and subscribe both views to their confirmed state. One status/list polling owner must serve both views; opening Settings must not create duplicate poll loops.
- Run the shared status and Wake-on-LAN list polling while the page is visible, regardless of Settings visibility. Local configuration/device mutations already adopt confirmed data and trigger follow-up reads; use these notifications to update dashboard rows immediately. Preserve existing connection secrets, dirty URL drafts, Wake-on-LAN editor drafts, session guards, and mutation ownership. Change generic read-error wording from dialog-only retry language where necessary.
- Add `public/dashboard-home-assistant-devices.js` for the read-only device snapshot controller. Refresh when a readable connection first appears, its configuration identity changes, selections need unavailable data, or the Home Assistant picker opens without a snapshot. Poll snapshots every 30 seconds while selected devices exist or the picker is open. Use ordinary cached GET requests, not repeated `?refresh=1` calls. Stop this loop when neither consumer needs it.
- Give snapshot requests deadlines, a bounded response reader, strict shape/ID/duplicate checks, and generation ownership. Use an 8 MiB maximum for device responses; reject oversize or malformed responses visibly without replacing confirmed data. Adopt only display fields and readings; discard controls and their tokens. Treat `unavailable` and `unknown` as explicit statuses, and require finite numeric values for available readings.
- On confirmed identity changes, abort obsolete device reads and immediately clear old readings. Match each device result to the expected configuration identity. On HTTP 409, refresh status and schedule a new safe GET instead of adopting stale data. Ordinary same-identity failures retain the last confirmed snapshot with stale/error feedback. Status failures retain last confirmed configuration without claiming a disconnect.
- On `visibilitychange`, suspend read polling and invalidate late responses while hidden; refresh on return. On persisted `pagehide`, suspend without destroying controllers, then resume on `pageshow`. On final unload, dispose timers, subscriptions, and requests once. Do not abort an accepted mutation solely because Settings closes, and never retry mutations automatically.

### 4. Add the Home Assistant selection picker and draft handling

- Extend **Settings → Home Assistant** in `public/index.html` with an accessible device fieldset, loading/error guidance, and labeled checkboxes. Keep the connection form separate. Show names and area where helpful; distinguish duplicate names using existing public metadata without exposing raw IDs. Disabled devices remain visibly unavailable rather than appearing healthy.
- Add `public/dashboard-device-selection.js` to render keyed picker rows and manage an explicit selection draft. Preserve checkbox nodes, focus, and checked values during snapshot refreshes. Keep selections for temporarily missing devices rather than silently removing them; provide a labeled removable missing-selection row and clear guidance. For a different connected origin, mark unmatched saved IDs as not available from the current connection.
- Checkboxes participate in the existing Save preferences workflow, not the connect/disconnect workflow. Update `fillForm()`, submit serialization, preference-change detection, input dirty tracking, reload-shared-preferences handling, and save-pending disabling in `public/dashboard.js` to handle selection arrays explicitly. Build submission from all scalar controls plus the explicit selection draft; never normalize a scalar-only form object in a way that resets selections accidentally.
- Capture selection draft and `draftRevision` together when Settings opens. Background snapshots update confirmed dashboard state but must not replace a dirty selection draft. Fix the existing form-fill condition so all pristine drafts, not only initially unconfirmed ones, can adopt a new snapshot and its revision atomically. A HTTP 409 adopts confirmed server state for display while keeping the user's draft and old revision until Reload shared preferences is explicitly chosen.
- After a confirmed preference save, replace the selection draft with returned canonical selections. Closing without saving discards selection edits on the next open. A connection switch invalidates the device snapshot and changes picker availability, but does not silently save, remap, or remove draft selections. Selection edits must not clear connection token drafts or submit connection mutations.

- Implement wake dispatch in the coordinator as a separate per-device request path, not `createConfigurationController.mutate()`: waking is an action, not a replacement configuration value. - Send one same-origin `POST /api/devices/<id>/wake` per explicit click with a deadline and no automatic retries. Announce success in a dedicated section-level status region: the packet was sent, not that the PC powered on. Surface bounded server errors for HTTP 429 and HTTP 502; on HTTP 404, report removal and refresh the list. Do not invent a cooldown countdown from the error text or assume a fixed server cooldown.
- Network failures or timeouts after dispatch have uncertain outcomes; say so and leave retry to the user. Preserve pending state through harmless list polls, Settings open/close, and page suspension so duplicate clicks cannot dispatch a second request. Late results from a removed row must not recreate it or overwrite feedback for a newer action. Preserve keyboard focus on surviving keyed rows and handle focused-row removal accessibly.
- Keep existing server cooldown, UDP sending, device CRUD, and wake audit behavior unchanged. Background reads, preference saves, page load, and Home Assistant selection changes must never send wake packets.

## Acceptance Criteria

- Desktop places the Home Assistant/Wake-on-LAN column between information/weather and bookmarks, with equal upper/lower sections and contained list overflow. Hiding bookmarks does not hide or collapse the device column.
- Mobile and intermediate layouts keep every section accessible without horizontal overflow and preserve existing display preferences, photos, and Settings accessibility.
- Selected Home Assistant devices and supported readings are the only Home Assistant dashboard content. Selection survives reload, restart, and another browser, without storing credentials or control tokens.
- Existing stored preferences load with empty selections and unchanged old values. New saves use the existing revision conflict mechanism; polling cannot erase a dirty draft or clear selections during an unrelated preference edit.
- A different Home Assistant origin never displays devices using the previous origin's selections. Credential changes and disconnect invalidate cached readings and obsolete requests without destroying saved selection preferences.
- Every saved Wake-on-LAN dashboard row contains only a name and Wake button. Wake dispatch is manual, duplicate-safe, and reports packet acceptance, cooldown, failures, and uncertain outcomes correctly.
- Local settings mutations update dashboard views immediately, remote confirmed changes appear through visible-page polling, and failures retain same-source confirmed data with clear stale feedback.
- Automated tests cover the new behavior and existing dashboard, connection, device-management, credential-security, and wake-audit behavior remain intact.

## Risks And Decisions

- Preference arrays require explicit serialization and structural comparison. The current scalar-only form loop and exact-schema reader must be changed together before connecting the picker to saves.
- Reuse the public origin-scoped `selectionId`; raw IDs and expiring action tokens are unnecessary. Opaque connection identity protects read freshness, not persisted selection identity.
- Missing selections are retained until explicitly removed. Returning to the same canonical origin can restore them; changing origins does not automatically migrate them. Replacing an actual Home Assistant instance behind the same origin cannot be distinguished automatically by the existing origin-scoped ID contract.
- The device APIs still return controls for existing API clients. This UI discards them and adds no Home Assistant action buttons. Server API changes remain additive except the new stale-read HTTP 409 guard.
- Shared polling must have one owner. Closing Settings must not stop dashboard refreshes or dispose injected controllers; all lifecycle tests should verify this boundary.
- Five-second status/device-list polling reuses existing synchronization cadence; 30-second Home Assistant snapshot polling respects the default cache interval and is not a live event subscription. Large responses fail visibly at the documented client bound rather than being silently truncated.
- Cooldown is server-controlled. Show the existing HTTP 429 message and do not parse human-readable text into a brittle client timer.
- Three columns reduce weather width. Geometry tests must cover scale settings, long strings, zoom-equivalent narrow viewports, and fullscreen, not only an empty dashboard screenshot.
