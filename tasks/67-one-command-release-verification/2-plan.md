## Scope

Make `bash scripts/release.sh` the single operator command that checks prerequisites, automatically verifies committed project source, verifies package/build readiness, builds or reuses the AMD64/ARM64 image, and completes publication only when all required evidence passes. Preserve `--help` and side-effect-free `--validate`. Verification is part of this command, not a new checklist the user must execute separately.

Current version `0.17.35` unconditionally disables publication and leaves N1/N2 unresolved. This task includes resolving those two documented blockers with regression tests before replacing that unconditional guard with mandatory verification gates. It also addresses the inherited-Git-configuration test warning from `tasks/_archives/66-container-release-template/5-code-review.md`, because those tests will execute automatically during release. Do not simply remove the guard, widen the server allowlist, add a verification bypass, or print success while publication remains unavailable.

Do not change dashboard behavior, deployment storage/network contracts, or the configured repository/image. No production publication, remote tag/source push, package linking, credential provisioning, privileged host setup, or dependency installation into the user's working tree is authorized during implementation verification. The implemented no-argument command will publish when an operator explicitly runs it afterward with all prerequisites satisfied.

## Implementation Plan

### 1. Define the one-command verification contract

1. Keep `scripts/release.sh` as the sole publication entry point. Accept no arguments, `--validate`, or `--help`; reject unsupported and explicit empty arguments before credentials or external effects. `--help` requires only Bash; `--validate` retains its current local-only behavior and must not invoke suites, install dependencies, contact services, or create state.
2. For normal publication, resolve the project from the script location, check Bash/Python 3.11+/Node 24+/npm/Git/curl/Docker prerequisites, validate settings/version/notes, acquire the existing checkout lock, and capture clean `main` plus exact configured fetch/push destinations and remote-main agreement. Do not automatically commit, bump the version, or push source for the operator. These source/setup requirements remain prerequisites, not manual verification commands.
3. Define the fixed ordered gates: local settings/source validation; locked dependency installation in a private committed snapshot; shell/Python/JavaScript syntax and version consistency; application tests; isolated release tests; production-tree packaging smoke; selected Buildx/plugin/platform readiness; private authentication and read-only package readiness; bounded remote publication classification; staging build/reuse and strict manifest/config verification; runtime smoke on both immutable platform images; final tag/promotion/release/package verification. Failures before staging must cause no registry login/build/push, remote Git write, promotion, release creation, or link write. Private auth preparation/package reads occur only after local verification succeeds.
4. Run mandatory local gates once per invocation, inside the lock, before remote publication work. Do not rerun them at every existing `scan` or after the lock-holder re-exec. Completed-publication retries still run required local verification; they must not rebuild, repush tags, re-promote, or recreate releases. Keep the existing narrowly guarded completed-retry association exception.
5. Print short phase/progress lines and clear success/failure results. Before mutation, errors should say publication did not begin; after staging/tag/promotion begins, preserve the existing partial-state warning. Report failed gate, exit status or timeout, and a useful sanitized diagnostic. Do not claim a local check verifies remote publication or ARM64 execution.

### 2. Make automated test fixtures safe and nonrecursive

1. Replace `BashPublicationTests.setUp`'s broad ambient-environment inheritance with a controlled fixture environment. Remove inherited Git repository/worktree/index/object/config/SSH/transport selectors, shell startup hooks, credential variables, and Node/Python preload controls. Use fixture HOME/XDG paths, disable system/global Git configuration, and explicitly disable hooks/signing in the owned repositories. Preserve only required executable paths, locale, fixture author/committer identity, and explicitly configured per-test connection settings. Apply this environment to setup Git and the real Git subprocesses behind the fake command port; do not change real release Git authentication policy to fix fixture isolation.
2. Add regressions that inject an external hook, `GIT_CONFIG_COUNT` key/value overrides, explicit Git config files, and repository/index selectors. Require no external hook execution, no writes outside owned fixtures, and successful operation against the intended temporary repositories. Use only review-owned temporary sentinels, never user repositories or credentials.
3. Remove the old `GUARD` source-deletion transformation after the unconditional production guard is genuinely replaced by verified gates. Publication fixtures must exercise the ordinary checked-in script without editing its source or setting a production skip flag.
4. Extend fake ports to simulate the exact automatic verification command boundaries, including npm installation/tests, Python unittest invocation, production smoke, and runtime probes. Delegate ordinary Python helper invocations to the real interpreter. A fixture invocation of the outer release command must log simulated suite success/failure rather than launching another complete test suite. Implement this only in test executables/configuration, never through `SKIP_TESTS`, an environment enablement flag, recursive-mode argument, or a production fixture detector.
5. Separately integration-test the real verification runner against small owned projects with actual passing/failing test processes. This proves the runner does execute checks, propagate failures, enforce deadlines, and avoid recursion; fake-port call assertions alone are not sufficient.

### 3. Add bounded local verification

1. Add `scripts/release-verify.py` as a standard-library helper for fixed local gates and owned image-smoke resources; it must not publish anything or expose a bypass. Keep publication policy/orchestration in Bash and strict data/API identity in `scripts/release-data.py`. Reuse the existing bounded process-group capture behavior where appropriate rather than adding an unrelated framework or arbitrary configured hooks.
2. Create a private snapshot from the captured committed Git source using the existing safe archive/export boundary, outside the checkout under an owned temporary directory. Include committed tests/scripts/notes/manifests, never worktree `.env`, data, credentials, ignored caches, or existing `node_modules`. Revalidate source/configuration after checks and before any publication write; abort if source or release inputs changed. Build from the same captured commit, not a newly sampled worktree.
3. Install the snapshot's locked development dependencies using `npm ci --ignore-scripts` with bounded fetch retries/timeouts and an owned npm user-config/cache location. Do not run npm install in the user's checkout, rewrite dependency resolutions, install host packages, or forward release credentials to test/install children. Preserve explicitly required proxy/CA trust without exposing token values or ambient application configuration.
4. Run `bash -n` separately for each release shell file, parse the release Python/helper/test files without leaving bytecode state, and invoke `node --check` for every JavaScript file under `src/`, `public/`, and relevant scripts/tests. Do not rely on current `npm run check` glob behavior: it passes multiple filenames to one `node --check` invocation and does not establish per-file coverage. Update that script or share a deterministic per-file checker with the release runner, so the documented command and automated gate agree.
5. Verify `VERSION`, `package.json`, both root lockfile version fields, configured notes path/heading, and README version agree. Execute `npm test`, `python3 -B -m unittest discover -s test/release-template -v`, and `node scripts/check-production.js` against isolated committed inputs. Make `check-production.js` honor an explicitly owned temporary parent supplied by the runner instead of depending on a pre-created global `/tmp/opencode` directory on every operator machine. Keep its production-only dependency, HTTP/key, and shutdown assertions.
6. Use explicit gate budgets: dependency install up to 300 seconds, each application or release suite up to 1,200 seconds, syntax/metadata up to 120 seconds, and production-tree smoke up to 180 seconds. Bound captured output to 16 MiB per gate and stderr to 1 MiB, draining both concurrently; output overflow, timeout, nonzero status, or missing mandatory executable is failure, never success or permission to continue. Terminate/reap only owned child process groups. Preserve useful sanitized diagnostics, not raw authenticated remote responses or secret-bearing environment dumps.
7. Do not automatically run browser downloads or privileged browser-library setup. The mandatory release contract is Node/application tests, release tests, syntax/metadata, production packaging, and both image runtime smokes. Browser E2E remains a separately documented developer check; do not describe its omission as browser certification. Explicitly report environment-limited test skips; missing mandatory runtime/packaging checks cannot be silently skipped.

### 4. Resolve publication safety blockers

1. Fix N1 in `scripts/release-common.sh`/`scripts/release.sh`: model promotion confirmation as a one-way invocation state. Before promotion, an alias may equal the captured predecessor or prepared digest; after confirming promotion, every later publication guard must require the prepared digest exactly. A predecessor reappearance, missing/foreign alias, failed/malformed read, or changed confirmed tag must stop before release POST or package linking. Never refresh the predecessor, roll back, or repair the alias automatically.
2. Add fault-injection regressions at the precise post-confirmation/pre-release boundary, including return to predecessor, absence, foreign digest, transport/HTTP/malformed evidence, and confirmed-tag replacement/disappearance. Assert no release POST/link occurs after the fault and accepted earlier remote state is preserved. Retain lost-response reconciliation without duplicate writes.
3. Fix N2 by identifying and retaining the actual selected Docker Buildx executable, not only builder/context metadata. Planning confirmed local `docker info --format '{{json .ClientInfo.Plugins}}'` exposes a `buildx` entry with an absolute plugin `Path` (`/usr/libexec/docker/cli-plugins/docker-buildx` here). Capture bounded plugin evidence under the original Docker configuration, validate the unique executable, and bind its resolved path/content identity to this invocation before changing `DOCKER_CONFIG`. Do not hardcode this workstation's plugin location.
4. Make the private Docker configuration discover that same plugin, for example through a run-owned `cli-plugins/docker-buildx` link to the validated executable. Verify plugin identity again under private auth before login/build/promotion, and refuse unsupported discovery, disappearance, replacement, or a different selected plugin. Check config-local and system plugin installations with real local discovery probes and fixture scenarios; do not resolve N2 by assuming `BUILDX_CONFIG` controls executable discovery or by inheriting registry credential helpers. Preserve explicit host/context precedence, TLS metadata, builder selection, and relative path semantics.
5. Keep package readiness before registry login/build/tag/promotion/release writes and preserve all final association checks. Retain the stable-`1.25.x` guard for new links. On observed server `28.2.0`, proceed only for an exact existing association; missing/unlinked/conflicting/unavailable identities must fail early with a specific instruction to obtain a separately approved server/association decision. Do not provision/link packages, broaden the allowlist, or require the user to repeat verification commands as a workaround.

### 5. Verify both built platforms before promotion

1. Preserve one `docker buildx build --platform linux/amd64,linux/arm64` staging push and strict immutable index/configuration/label verification. Reuse verified staging on eligible retries. No second release build, architecture-specific registry tag scheme, or archive-upload workflow is introduced.
2. After staging content verification and before version-tag publication, `latest` promotion, or Gitea release creation, automatically smoke-test the immutable per-platform image content for both `linux/amd64` and `linux/arm64`. Select platform child digests only from the verified index, pull/run by digest with explicit `--platform`, and verify actual reported architecture rather than trusting the requested CLI flag. Do not test an unrelated mutable local image or rebuild another image for the smoke.
3. Use only run-owned container names and temporary data volumes, loopback ephemeral ports, disabled NFS/integrations, and an isolated allowed-host configuration. Require Node/application startup, local production dependency resolution, absence of development/secret/release files, HTTP settings readiness, automatic key creation, and graceful SIGTERM exit zero. Clean up only owned containers/volumes on success/failure/signals. A missing emulator/native execution path must stop with host-preparation guidance, never trigger privileged installation or skip ARM64 while reporting a two-platform release as verified.
4. Bound image pull/run/readiness/shutdown operations and reject runtime probe failure before promotion. Staging may already have been pushed at this point; failure messaging must distinguish staging evidence from a published version release and must not delete accepted remote state. Completed retries may pull/run the bound images read-only but must not rebuild or mutate version/tag/release/alias state.

### 6. Integrate verification with publication and retries

1. Replace the unconditional publication guard only as part of integrating the mandatory gate sequence and the tested N1/N2 fixes. No `--force`, `--skip-tests`, success cache, marker-file enablement, or environment bypass is allowed. An unsupported machine/account still gets one actionable failure from the same command, not a pretend successful release.
2. Use the existing checkout lock for the whole invocation, including local checks; do not create a second competing lock protocol. Ensure child verification fixtures cannot inherit the live release lock or token environment. Revalidate source/configuration/notes and fresh remote evidence after slow tests/image probes before each existing mutation boundary.
3. Include every new verification/syntax/smoke helper affecting release authority in the script/identity hash calculation in `settings`. Record this deliberate local adaptation. Old publication identity cannot be adopted after script/config changes; require a new unused version rather than rewriting tags or silently migrating ownership.
4. Keep bounded inventories, exact source/main agreement, deterministic annotated tag identity, non-force tag pushes, immutable digest promotion, notes-only Gitea releases, strict package identity, and readback-based lost-response reconciliation. Refuse tag-only/release-only and conflicting states. Do not introduce automatic rollback, cleanup/retention, source pushing, relinking, or remote repair.
5. Test full ordered events for fresh release, staging reuse, completed retry, and each gate failure. Test both from the repository root and another working directory. Verification must run exactly once per top-level invocation and never recursively; every failure before staging must show zero publication writes. Existing fixture timeouts may be extended only for real runner integration cases, not removed globally.

## Acceptance Criteria

- After one-time setup, clean already-pushed `main` can use only `bash scripts/release.sh` for mandatory verification and release; no separate test/check commands or verification-bypass settings are required or supported.
- Local verification runs exactly once, uses captured committed source and private dependency/test state, and fails closed on required gate failures before publication work. The working dependency tree, `.env`, data, credentials, and unrelated processes are untouched.
- Every relevant JavaScript file is syntax-checked individually; version/notes mirrors, Node/application tests, release tests, and production packaging run automatically. Fixtures neither execute host Git hooks nor inherit repository/index/config selectors, and simulated release tests do not recursively launch the suite.
- N1 regressions prove that only the prepared alias is accepted after confirmed promotion and no later release POST/link follows predecessor reappearance or failed evidence. N2 regressions/probes prove identical executable selection before and under private Docker auth, or fail safely before publication.
- One staging build covers AMD64/ARM64; both immutable platform images pass automatic architecture/startup/HTTP/shutdown smoke before version-tag/promotion/release writes. Missing ARM64 execution capability is an explicit failure, not a skip or privileged auto-install.
- Unsupported-server missing/unlinked packages stop before staging/publication; exact existing links remain read-only without widening stable-`1.25.x` write authority. Final identities and publication remain freshly verified.
- Fresh, staging-reuse, completed-retry, source-change, timeout, overflow, verification failure, partial publication, and lost-response scenarios have isolated behavioral tests. Completed retries never rebuild, retag, re-promote, or recreate matching releases.
- `--help`, unsupported-argument refusal, and credential/network/state-free `--validate` retain their narrow contracts. Version/docs accurately describe what is automated, what setup remains, and what evidence was actually obtained.
- Implementation verification creates no live registry push, remote source/tag/release/link mutation, credential provisioning, or privileged setup. `4-implemented.md` distinguishes real local multi-platform evidence from simulated publication tests and any blocked prerequisites.

## Risks And Decisions

- **One command is not automatic setup:** credentials, trusted TLS, an already-pushed clean `main`, exclusive external writers, and native/emulated AMD64/ARM64 execution remain operator prerequisites. The command verifies them and reports actionable failures; it does not acquire authority by repairing infrastructure or changing remote associations.
- **Scope of activation:** the previous unconditional guard may be replaced only alongside mandatory gates and proven N1/N2 corrections. If either correction cannot be verified, report this goal as blocked rather than weakening it into a silent test-skipping publisher or claiming the one-command release works.
- **Server compatibility:** planning for task 66 observed Gitea `28.2.0`; this task does not certify its package-link replacement/refusal semantics. Existing exact association is the only supported path on that family. Reviewing new server families is separate work, not part of verification automation.
- **Verification latency and recursion:** the previous Python suite took about nine minutes; running it automatically is intentional. Use bounded phases and deterministic fake command seams rather than bypass flags, duplicated suites, or recursion guards that become production skip mechanisms. Required checks must not time out under the old 60-second remote-read budget.
- **Staging is a remote write:** runtime testing the real staging digest happens after staging publication but before public version/alias/release writes. Runtime failure may leave staging evidence; it never authorizes deletion, rollback, or publication continuation. Do not promise that all failures leave no remote artifact.
- **Test/install confidentiality:** application tests are executable committed code. Run them before reading publication credentials, sanitize inherited execution/Git controls, and use isolated source/install/storage rather than the live application tree. Preserve necessary platform trust/proxy settings explicitly, without forwarding release secrets.
- **Identity compatibility:** adding gate/smoke helper hashes changes publication identity. Existing historical tags/releases remain untouched and cannot be adopted under changed scripts. Use a new version and preserve source/config identity through the entire invocation.
- **Multi-platform evidence:** configuration and fake manifests are not ARM64 execution. Real smoke may block on the current host; report that honestly and require host preparation rather than relaxing the runtime gate. Browser E2E and production service integrations are not silently certified by these release checks.
