## Outcome

Implemented the one-command verification/release workflow on branch `67-one-command-release-verification`, version `0.17.36`. After one-time tool/credential/builder setup and independently committing/pushing clean `main`, the operator uses `bash scripts/release.sh`; mandatory verification is no longer a separate manual checklist. The previous unconditional publication guard is replaced by fail-closed gates and N1/N2 corrections, not a bypass. No live registry push, remote Git source/tag push, release creation, package linking, credential provisioning, or privileged setup was performed during implementation.

## Changes

- Added `scripts/release-verify.py`: export committed inputs, install development dependencies privately, verify version/notes/README mirrors and shell/Python/individual JavaScript syntax, run application/release suites, and perform production-tree packaging smoke before reading publication credentials. Source/configuration remains revalidated before writes. No arbitrary hook framework, success cache, or skip/force setting is introduced.
- Automatic application tests run serially to reduce concurrent native startup/ephemeral-port pressure. Each required gate has bounded concurrent output capture, an explicit deadline, short progress messages, and actionable failure context. Browser downloads/E2E remain outside the mandatory release contract.
- Fixed N1 with one-way promotion confirmation: later guards accept only the prepared digest. Tests inject predecessor reappearance, missing/foreign alias, and failed/malformed post-confirmation evidence and require no release POST/link afterward.
- Fixed N2 by capturing the selected Buildx executable's resolved path/content hash, pinning it into private Docker plugin discovery, and rechecking identity before login/build/promotion. Actual system and config-local executable probes passed without registry login. Existing context/host/TLS/builder behavior and strict package/server authority remain intact.
- Preserved one AMD64/ARM64 staging build, digest verification, source-bound annotated identity, promotion without rebuilding, bounded inventories, conservative partial-state refusal, and completed retries without publication rebuild/rewrites. Completed retries authenticate privately for image pulls without changing registry/tag/release/alias objects; exact existing package associations remain read-only.
- Added daemon-side immutable-image smoke through `docker exec`: verify actual Node architecture, local production dependencies, excluded development/secret/release files, HTTP/key readiness, and SIGTERM exit zero. Use no published host ports, workstation HTTP probes, host networking, or client bind paths. Data is in exact owned daemon-side named volumes; the selected local/remote Docker connection is preserved.
- Added parent-visible intent/readback manifests containing unique names, nonce labels, daemon/connection identity, and confirmed resource IDs. Cleanup refuses collisions/foreign identities, reconciles lost creates by exact name/ownership, preserves uncertain in-flight-create evidence, and never deletes shared images, deployment volumes, or registry objects. The cleanup deadline is retained across worker/parent attempts rather than reset on retry.
- Added Linux child-subreaper supervision in `scripts/release_process.py`, tracking PID/start identities and adopted separate-session/double-fork descendants. Timeout/overflow/signals allow bounded cooperative cleanup before owned-only escalation/reaping. The lock supervisor survives worker failure and performs independent exact daemon cleanup. Unconfirmed ownership diagnostics are retained; token/curl/Docker auth and copied context TLS keys are removed independently.
- Added portable Node/Python temporary-parent helpers, migrated all hardcoded `/tmp/opencode` test paths, and updated production smoke. An explicitly selected parent must be existing, absolute, owned, writable, outside the project, and nonsymlink. Harness storage is only an available preference; no global directory or host package is created.
- Hardened release fixtures against inherited Git config/hooks/signing/repository/index controls and removed the old guard-source transformation. Unmodified release scripts run against fake command ports that simulate verification boundaries without recursive suites or a production test-mode flag. Real runner, process, temporary-parent, plugin, and resource tests independently cover behavior beyond ordering mocks.
- Replaced `npm run check`'s multi-filename `node --check` command with `scripts/check-syntax.js`, checking each file under `src/`, `public/`, `scripts/`, and `test/`. Added every release-authority helper to script identity. Updated version mirrors, README, release/deployment/testing documentation, and new `docs/releases/0.17.36.md`. Application source, dependency resolutions, Dockerfile runtime, `.dockerignore`, Compose data/network/mount contracts, archived tasks, and `todo.md` are unchanged.

## Limits and operating prerequisites

- A one-command release is not automatic setup. Trusted TLS, independent Git authentication, the private token file, clean already-pushed `main`, actual AMD64/ARM64 execution support on the selected daemon, and exclusive external repository/image/package writers remain required. No host/emulation installation is attempted.
- The observed Gitea `28.2.0` family is still not approved for new association writes. Exact existing association is supported read-only; missing/unlinked/conflicting/unavailable evidence stops before staging. The stable-`1.25.x` write guard was not broadened. No live token/package inspection or association mutation was attempted.
- Runtime failure may leave accepted staging evidence. Tag-only/release-only or changed-identity states are still refusals, not rollback/repair authority. Signal cleanup is bounded and may retain sanitized ownership evidence when a daemon/process outcome cannot be confirmed; SIGKILL/power loss cannot guarantee cleanup. Private auth is never deliberately retained as diagnostic evidence.
- Earlier local system/config-local plugin discovery and both-platform builds passed. Current AMD64 runtime passed, but current ARM64 execution is blocked by `exec format error`; publication must fail until the selected Docker host can execute ARM64. Remote-daemon routing/ownership is covered by deterministic command-port scenarios, not a real remote-daemon deployment. Browser E2E, live package UI rendering, actual registry publication, and production integrations were not certified.
