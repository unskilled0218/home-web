# plan

## scope

Implement `1-goal.md`: choose individual Linkwarden bookmark links in Settings, persist the choices installation-wide, show only selected links on the dashboard, and open those links in new tabs. Keep the current collection grouping, desktop/mobile disclosure modes, fullscreen behavior, provider limits, shared-preference revision checks, and connection protections. A new tab opens in the browser displaying the dashboard; selecting another installed browser is not supported by ordinary web links and is outside this task. Do not add a native launcher, extension, bookmark editing, provider-wide search service, unrelated layout redesign, or shutdown fixes. This planning stage changes no implementation code, dependencies, version, user data, or `todo.md`.

## Current Structure

- `src/app.js` issues stable source/account-scoped collection `selectionId` values and temporary credential-scoped `collectionToken` handles. `/api/bookmarks` validates the token, obtains a bounded direct-folder result, checks configuration ownership, and currently returns numeric bookmark IDs without durable selection IDs.
- The connection `configurationId` includes encrypted credential data and changes on reconnect. It guards stale requests, but must not identify persistent link choices because token refresh should preserve them.
- `public/dashboard-bookmarks.js` owns the collection tree, cached folder contents, disclosure state, request queue, four-request concurrency, generation/authority guards, and five-minute content refresh. Its current load eligibility depends on dashboard disclosure and already-loaded folders.
- `public/dashboard-bookmark-tree.js` renders every loaded bookmark and every collection. It preserves keyed DOM nodes and focus. Links validate HTTP/HTTPS but currently lack `target="_blank"`.
- `public/dashboard-helpers.js` normalizes and validates complete shared preferences. `decodeStoredDashboardPreferences()` already supplies missing device selections for old persisted records. `src/dashboard-preferences.js` stores preference JSON in SQLite with compare-and-save revisions; no new SQL table is needed.
- `public/dashboard.js` coordinates confirmed preferences, dirty drafts, explicit reload, integration actions, and form ownership. `public/dashboard-device-selection.js` provides a useful local precedent for an independent keyed checkbox draft, missing choices, and Save preferences.
- `public/index.html` has display/connection controls in Settings → Bookmarks but no picker. `docs/linkwarden.md`, bookmark controller/API tests, and `e2e/dashboard-home.spec.js` currently describe or assert all-link rendering and must be updated deliberately.

## Implementation Plan

### 1. Define persistent choices and a safe upgrade transition

- Add `bookmarkLinkSelections` to shared preferences, plus a small shared validation helper, preferably `public/bookmark-selection-data.js` imported by the preference and bookmark boundaries without creating import cycles.
- Represent the value as `null` for never configured, or an array of `{ selectionId, collectionSelectionId }` records. An empty array means the user explicitly chose no links. `selectionId` identifies the bookmark; `collectionSelectionId` is a durable folder discovery hint, never a request authorization token. Do not store names, URLs, secrets, configuration IDs, or expiring tokens in preferences.
- Set a named maximum of 256 unique bookmark choices. Validate exact record keys, versioned bookmark ID syntax (`b_` plus a 43-character base64url SHA-256 digest), existing stable collection ID syntax, duplicate bookmark IDs, and maximum count. Canonicalize record order by bookmark selection ID without silently dropping invalid choices or trimming over-limit input.
- Extend `normalizeSettings()`, `PREFERENCE_KEYS`, canonical preference validation, stored decoding, legacy migration, and shared-cache decoding. Validate structured fields with their dedicated helper rather than primitive reference equality. Stored records missing the new field decode to `null`, including records also missing the earlier device-selection field. Live preference writes must include the new canonical field; stale old-client writes fail validation rather than erase choices.
- Keep SQLite's current JSON preference row and revision ownership. A read-time upgrade supplies defaults without overwriting rows or bumping revisions merely because a browser loaded them. The next explicit Save preferences persists the canonical value; unrelated preference saves retain `null` until bookmark selection is actually edited.
- For both new and existing installations, `null` displays “Choose links in Settings → Bookmarks”; `[]` displays “No bookmark links selected.” Neither shows all links or auto-selects a catalog. Explain this visible upgrade transition in documentation.
- Prove the maximum canonical bookmark choices plus maximum device choices and existing preferences fit the 65,536-byte request/response budget. Keep existing size guards rather than raising them without evidence.

### 2. Issue stable bookmark identities at the server boundary

- In `src/app.js`, project every safe direct-folder bookmark into its existing public fields plus `selectionId`. Derive the ID with SHA-256 over a versioned tuple containing normalized Linkwarden base URL, username, and numeric provider bookmark ID. Do not include URL, title, collection membership, credentials, timestamps, or `configurationId` in bookmark identity.
- Return the corresponding stable `collectionSelectionId` for the resolved folder alongside the result, using the same collection identity decision as the tree serializer. Extract a narrowly named identity helper if needed so tree and result cannot drift. Keep numeric bookmark IDs in the existing API shape for compatibility.
- Preserve collection token authorization, provisional connection validation, configuration checks after awaits, safe error responses, cache behavior, and response bounds. Persistent selection IDs are identifiers, not bearer capabilities; never accept them instead of `collectionToken` to request a folder.
- Update `normalizeBookmarkLinks()` and result acceptance to validate and retain public selection IDs, and verify response folder identity matches the job. Keep safe HTTP/HTTPS filtering. Do not invent a browser-only identity fallback for mismatched or malformed provider payloads.
- Confirm same source/account/bookmark retains its selection ID through title/URL changes, credential re-encryption, reconnect, and token renewal. Different source/account with reused numeric bookmark IDs produces different IDs.

### 3. Separate catalog demand from filtered dashboard presentation

- Keep `createBookmarkController()` as the single content/request owner. Add a narrow configuration method for confirmed selected-link records and explicit picker-open/folder-disclosure state. Picker disclosure must be independent of desktop/mobile dashboard disclosure.
- On a cold load, queue selected folder hints from the current tree even when their ancestors are collapsed, so selected links can be discovered before rendering the pruned dashboard. Do not require visible dashboard folders to bootstrap themselves. With no selected links and the picker closed, avoid loading every dashboard folder just because desktop defaults expanded.
- When the Bookmarks Settings tab is open, load disclosed picker folders on demand regardless of dashboard filtering or fullscreen hiding. Initially disclose roots, allow child expansion and Retry folder, and retain all safe returned links for selection. Do not automatically crawl all 256 folders on every settings poll.
- Extend the existing queue eligibility to the union of selected-folder demand, explicit picker demand, and bounded refresh of already-loaded data. Preserve one request per folder, four active requests, one tree/token-recovery owner, visibility pause, mutation invalidation, five-minute cadence, and existing count/byte limits. Prioritize selected folders before newly requested unselected catalog folders; report capacity/truncation honestly if a requested selected link cannot be established.
- Derive a selected-only dashboard projection from confirmed preferences and current source-owned cached records; preserve the full catalog for the picker. Group selected links beneath their collection and ancestor paths; prune groups without a selected loaded descendant. Do not expose unselected link titles or destinations through a mode change or stale DOM node.
- Match bookmarks by stable selection ID across loaded folders, not label or URL. If a bookmark moved, keep the saved identity; the old folder hint may yield an unavailable selection until the new folder is discovered in Settings. Selecting/saving the same discovered bookmark updates its folder hint explicitly. Do not claim an exhaustive account-wide missing result from a partial lazy catalog, and do not automatically rewrite saved hints or remove choices.
- Distinguish never configured, explicit empty, loading selected folders, stale/error, truncated/unresolved, missing/unavailable choices, disconnected, authentication failure, and access denial. Use last successful same-source content only where existing security rules permit it. Configuration/source changes invalidate content immediately but preserve preference records as unmatched choices; reconnecting the same source/account may resolve them again. Generation guards must reject late old-source results.
- Keep filter/projection decisions in one helper or controller boundary consumed by the renderer, not independently reimplemented in the picker and dashboard. The dashboard uses confirmed preferences only; ticking an unsaved draft checkbox must not change displayed links.

## Acceptance Criteria

- The dashboard displays only confirmed selected, safe bookmarks; the independent Settings catalog permits selecting previously hidden links. Empty/null choices never fall back to showing the full account.
- Choices persist across browser and server restart and synchronize across browsers using SQLite-backed revision checks. Dirty drafts and unrelated form data survive catalog/remote refreshes and conflicts until explicit save/reload.
- Identity is source/account/bookmark-scoped and unaffected by labels, destinations, credential renewal, or request tokens. Missing, moved, denied, truncated, and transient-error states neither select replacements nor destructively rewrite preferences.
- Selected folders load without a disclosure/filter bootstrap deadlock. One bounded content owner serves picker and dashboard, and stale source results cannot reappear after replacement/disconnect.
- Mouse and keyboard link activation creates a protected new tab in the current browser, leaving the dashboard intact. Unsafe schemes remain excluded; no native integration is introduced.
- Existing layout, fullscreen, security, request-budget, and unrelated integration behavior remains intact, with focused and full verification recorded.

## Risks And Decisions

- Upgrade behavior intentionally stops showing every bookmark until choices are made. `null` versus `[]` provides distinct guidance without silently selecting a potentially private full catalog or writing guessed defaults.
- Folder membership is a discovery hint, not bookmark identity. Lazy bounded access cannot guarantee account-wide detection of a moved/deleted link. Report unresolved choices accurately and let explicit picker discovery/save repair hints; never imply unseen records were conclusively deleted.
- Selection data shares the full preference revision, so concurrent updates must use existing conflict handling rather than last-writer-wins patches or a second storage owner. Old clients missing the new preference are rejected until reloaded.
- Stable source/account identities preserve choices across same-account re-authentication, whereas credential-sensitive configuration IDs continue to fence request results. Mixing these roles would erase choices or leak content across sources.
- Protected cached content remains subject to current authentication/access-denial rules. Retaining opaque selected IDs is not permission to retain denied bookmark labels or URLs in a visible picker.
- Catalog fetching must not become a second polling loop or eager account crawl. New picker demand and selected hints join the existing bounded controller and recovery machinery.
- Selection is presentation policy, not backend access control; the trusted-LAN API continues to provide authorized folder data for the picker. No authentication model changes are part of this task.
- The earlier question about another browser does not authorize a native launcher or extension. Standard anchors support new tabs only in the browser hosting the dashboard.
