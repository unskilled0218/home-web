# plan

## scope

Make the current photo dashboard's Settings installation-wide as defined in `1-goal.md`. Persist its complete display preference set in SQLite, synchronize visible browsers every five seconds, migrate valid legacy preferences once, and propagate public weather/calendar/Linkwarden configuration changes into already open clients. Reuse existing integration persistence and encrypted credentials. The legacy `/api/home/settings` schema belongs to retired widget layouts; add a current-dashboard preference store/API instead of replacing those records. Actual viewport, fullscreen state, unsaved drafts, and temporary folder disclosure remain browser session state.

## Implementation Plan

### 1. Define one canonical preference contract

- In `public/dashboard-helpers.js`, expose the current dashboard preference keys and shared default/normalization/validation helpers usable from Node and the browser. Include every preference currently associated with `form="preferences"`, covering all six Settings tabs and both display profiles. Exclude `location`, credentials, revisions, request tokens, and transient controller state from the stored preference object; weather location remains in its existing server store.
- Define server defaults using an explicit `UTC` timezone rather than each browser's detected zone. Retain existing enum/boolean/default values, including mobile views visible at scale 1, Compact bookmarks, and fullscreen hiding disabled. A legacy record's valid saved timezone can become the global timezone during migration.
- Keep numeric normalization consistent with native form constraints: scales, duration, and opacity use their existing 0.1 steps; interval and blur use integer steps and existing bounds. Clamp/quantize legacy values before migration, retain the interval/duration dependency, and validate timezone, color, enum, and strict boolean fields. Existing service consumers can keep `normalizeSettings`; use the new canonical preference helpers at the global persistence boundary so a server-loaded value cannot make Settings invalid.
- Strictly validate live save bodies as complete preference objects with allowed fields and valid types/ranges/steps; reject malformed or unknown data with 400 rather than silently accepting credential/session fields. Legacy migration accepts a plain object with recognized valid preference content, discards obsolete/unknown fields including location, and produces the full canonical object. Null, arrays, corrupt JSON, and unrelated objects are not migration candidates.
- Define a shared snapshot containing `{ initialized, revision, preferences, integrations }`. `integrations` contains public weather location/revision, public calendar status/configuration identity, and existing public Linkwarden status/configuration identity. It contains no password, token, or encrypted credential fields. Validate snapshot shape separately from preference payloads.

### 2. Add revision-checked SQLite persistence and a read-only aggregate snapshot

- Extend `src/db.js` with an additive singleton `dashboard_preferences` table containing canonical preference JSON, revision, and update timestamp. Expose read, initialize-if-absent, and revision-checked save operations, using transactions and the existing connection. Preserve the former home settings, weather cache/location, devices, and integration records.
- A missing record reads as server defaults with `initialized: false` and revision 0; GET must not insert a record. First successful initialization/save creates revision 1. Normal saves compare the supplied revision and increment on actual changes; an identical valid save at the current revision returns the existing revision. Validate loaded persisted records and report corruption/storage failure instead of overwriting them with defaults.
- Add `GET /api/dashboard/settings` in `src/app.js` returning the preference snapshot plus public integration metadata from existing stores/status helpers. Build this response from synchronous local reads without requesting provider forecasts, calendar events, collections, bookmarks, or photo manifests. Apply existing local-network/Host checks and `no-store` JSON headers.
- Read each integration's public metadata independently with an `available` flag and bounded safe error state. Corrupt/unavailable integration metadata must not turn a valid preference read or committed preference save into failure. Unavailable metadata represents unknown status, not a disconnected source; guarded observers keep their current usable service state and retry on later snapshots. Preference-storage corruption itself remains a 503.
- Add `POST /api/dashboard/settings/initialize` for one-time migration. Validate a canonical candidate, then insert only if the row is absent and return the winning persisted snapshot plus a `created` boolean. Competing candidates adopt the same winner; this route cannot replace an established record. An integration configuration change does not initialize display preferences.
- Add `PUT /api/dashboard/settings` accepting `{ revision, preferences }`. Validate the bounded body and nonnegative safe revision, atomically create/update against that revision, and return the committed snapshot. Return 409 with a clear message and current shared snapshot on a stale revision, 400 for invalid payloads, 503 for storage failures, and 405 for unsupported methods. Apply current Origin and JSON-body checks. Save preferences never writes integration credentials/location.

### 3. Make public integration metadata sufficient for prompt discovery

- Use `store.getWeatherLocation()` to publish the existing location revision and coordinates/label in the aggregate snapshot. Keep location saves and provider retrieval in their existing API/service, independently of preference revision.
- Add an opaque calendar `configurationId` derived from server URL, username, and the stored encrypted password record, following the existing Linkwarden identity approach. Return it in calendar status, successful connect/event responses, and relevant error/disconnected responses; no record uses `null`. It survives restart and distinguishes rapid same-URL credential saves without exposing secret material or relying on second-resolution timestamps.
- Capture calendar configuration identity before awaited event retrieval and verify it before publishing success/failure. Return a changed-source 409 without old events when the saved configuration changed meanwhile. Keep serialized calendar mutations, encrypted persistence, event bounds, and private-CA behavior. Extend calendar response normalization to retain the public identity.
- Reuse Linkwarden's existing configuration ID and public status; the aggregate GET only reads local configuration, so a five-second poll never loads its collection tree. Continue using the existing weather/bookmark/calendar data refresh owners for actual content.
- Add guarded configuration-observation hooks to weather, calendar, and bookmark controllers. Capture them before every request whose response can carry integration metadata: aggregate GET, initialization POST, preference PUT, and its possible 409 snapshot reply. A hook returns an apply callback valid only while that controller's configuration/mutation epoch is unchanged and it was not captured during that service's local mutation. Keep this epoch distinct from ordinary data refresh generations. A newer owned source adoption, local mutation, or access retirement invalidates an older observer, preventing delayed snapshot metadata from reverting a newer service state.
- Applying unchanged public metadata must be a no-op: no timer reset, request, cache discard, or disclosure reset. A genuine weather location change updates the authoritative location and loads its matching cached snapshot once. A genuine calendar identity/readability change clears old-source events and updates connection status, then fetches events once if its current shared profile eligibility and document visibility allow it. Linkwarden adopts changed source/status through its existing adoption rules, clearing old data only for a real source change and loading one new tree.
- Feed calendar status and effective refresh eligibility together when synchronizing so a simultaneous remote connect and both-profiles-hidden preference does not start an unnecessary event request. Initially unconfigured controllers must accept a configured source discovered by the global poll; calling the current calendar `refresh` alone is insufficient because it returns early for unconfigured state.
- Preserve upstream authentication/access-denial blocks for unchanged identities: decryptable stored credentials alone do not prove restored access. Remote successful reconnects produce a new identity and can restore the corresponding source. Guard old event/forecast/folder responses after metadata adoption.
- Bound local calendar browser mutation requests to 25 seconds, retaining the existing weather/bookmark deadlines and generation checks. Abort unsettled client reads on the deadline and release their pending ownership. Distinguish deadline failure from obsolete-request cancellation and report an unconfirmed mutation outcome; the previous `configured: true`/empty-error state must not make the form falsely report a successful reconnect. A timeout is failure to confirm the outcome, not proof that the server did not commit; continue public-status reconciliation so a later committed connection is discovered rather than rolled back or retried blindly.

### 4. Implement one browser settings synchronization owner and atomic migration

- Add DOM-free `public/dashboard-settings-sync.js`, accepting fetch, timers/clock, storage, snapshot callbacks, and controller-observer capture hooks. Own initial load/migration, one serialized/coalesced aggregate read, preference save, one poll timer, visibility pause/resume, and disposal. Bound same-origin reads/writes to ten seconds and bounded JSON response size. Capture integration observers before each snapshot-returning request, not only GETs, so their callbacks reflect request-start ownership.
- Read valid `dashboard.preferences.v1` only as a legacy migration candidate. After a successful GET reports uninitialized state, POST that candidate once through atomic initialization; adopt the returned winner even if another browser initialized first. A fresh browser without a candidate uses server-default preview and leaves the row uninitialized until an explicit save or another client's migration. Established server preferences always replace stale local values.
- Keep a separate `dashboard.shared-settings.v1` cache containing only the last server-confirmed initialized preference snapshot/revision and its schema marker. Use it for startup fallback during outages, never to initialize or override server state. Remove/mark the old legacy key only after a shared initialized record is confirmed. A cache-write failure does not turn a successful server save into failure or disable server synchronization.
- Treat a live latest-owned preference response as authoritative, including after a server database reset; cached revision values are not authority. Integration metadata in the same reply has its own captured observer guard and is not made current merely because the preference revision is accepted. Cancel/invalidate old aggregate reads when preference saves or visibility suspension begin. A response from a canceled generation cannot replace a newer confirmed save. Coalesce normal polls, Settings-open refreshes, and visibility refreshes rather than running competing owners.
- Poll visible documents every five seconds after the preceding cycle settles. Pause/cancel reads while hidden, refresh immediately when visible again, and use the same owner after persisted pageshow. Fully dispose on ordinary navigation. If a cycle fails, retain confirmed preferences/current service data, show synchronization failure, and retry through the same five-second timer without claiming a new confirmation.
- Implement save as a separate owned mutation using the form's captured revision and payload. Suspend/cancel aggregate reads during the PUT and apply/cache only the server-confirmed preference result. Independently deliver available metadata to the observers captured before that PUT; stale/deferred service metadata must not invalidate valid preference confirmation. Apply the same separation to migration POST and 409 snapshot bodies. A 409 can update the latest confirmed dashboard preferences while retaining the stale draft; transport/validation/storage failure preserves the previous confirmed configuration. Do not fall back to a local-only successful save.
- Provide reference-counted metadata deferral per integration for local weather location and calendar/Linkwarden connection/disconnection actions. Bracket each action with begin/finally-release for that service; continue aggregate polling and preference/other-service application every five seconds while it is pending. Invalidate pre-mutation observers, and discard that service's observations captured while deferred even if delivered after release; do not queue stale metadata for later application. When its final action ends, schedule one fresh post-action aggregate read through the existing owner, without reusing a response captured during the action. Preference saves remain independently revision-checked and retain only their own short PUT read suspension.

### 5. Wire asynchronous Settings saves, drafts, and change-specific application

- Replace `public/dashboard.js` local preference loading/saving authority with the synchronization controller. Bootstrap presentation from a valid confirmed cache or canonical server defaults, then resolve server load/migration and start data controllers once with the resulting preference set. Allow calendar construction with deferred auto-start for this composition path; preserve its default startup behavior for other callers. During initial unavailable state without confirmation, show a retrying shared-settings status and retain deterministic preview rather than promoting local values.
- Capture a preference-form draft and its base revision when Settings opens. Refresh shared metadata on opening but do not refill an already edited/open form from later synchronization callbacks. Remote snapshots update active presentation behind the dialog while the form retains its values and original base revision. Closing/reopening reloads confirmed values, matching existing draft-discard behavior.
- Before Save preferences, retain existing hidden-panel native validation and collect the full canonical preference payload. Disable the associated display controls and save/reload actions while the owned PUT is pending, leaving independent integration forms usable. On success, show **Preferences saved for all browsers.**, update confirmed values/base revision, and refill the preference form. On failure, restore enabled controls and preserve the draft. Do not optimistically apply an unconfirmed draft as a successful shared save.
- For a 409, retain the user's form values/base revision and show that another browser changed shared preferences. Add a non-submit **Reload shared preferences** action that explicitly replaces display draft values with the latest confirmed snapshot and updates the form base revision; it must not reset credential/search drafts. Do not silently rebase a stale whole-form payload to the newer revision and overwrite remote fields on a second click.
- Replace full `apply` calls on every observation with change-group application. Presentation changes update active desktop/mobile visibility, scales, alignment, and order. Timezone/clock format changes update/restart the existing clock owner once. Weather units/timezone update its canonical presentation/cached query only when those keys change. Calendar time formatting re-renders existing events without reconfiguring its source or timer. Calendar eligibility is the existing desktop-or-mobile visibility rule.
- Configure photos only for actual slideshow/background preference changes; clock, bookmark, unit, and integration-status updates must not reset image order, layers, or animation. Apply bookmark mode/fullscreen policy only when those values or local viewport/fullscreen context change, retaining its disclosure maps and fresh folder data. An unchanged five-second response must produce no service configuration/request work.
- Route aggregate integration metadata through the guarded observer callbacks, not through direct localStorage writes or stale calls to controller `start`. Preserve open URL/username/password/token drafts when another browser changes connection status. Keep connection actions independent of the preferences form, updating their current source through the existing mutation owner and requesting a fresh aggregate snapshot afterward.
- Keep the three mobile view ordering and actual fullscreen entry local to each browser. Shared mobile/desktop fields and fullscreen-hiding policy apply according to that browser's current context. Temporary bookmark folder toggles, search results, and fullscreen entry do not write the global preference record.

## Acceptance Criteria

- Every current Settings preference has one canonical server record and survives restart. A successful Firefox change appears in Chromium and other isolated clients, both after reload and within the normal five-second visible-client synchronization cycle.
- Shared desktop/mobile fields remain independent within that one record, and each browser projects them according to its local viewport/fullscreen context. No saved preference remains browser-authoritative.
- Existing valid local values can initialize an absent global record once; competing initialization/save operations select one atomic winner. Established server values override stale legacy data, and cache failures/outages cannot publish local-only successful saves.
- Saves are revision-checked and atomic. Remote snapshots update presentation without replacing open drafts; stale saves return conflict, failed saves retain prior confirmation and draft, and explicit reload/reapply provides a safe recovery path.
- Weather location and calendar/Linkwarden public configuration changes propagate into initially unconfigured open clients without reload. Credentials remain in encrypted server storage, and older aggregate/content replies cannot roll back owned mutations or restore retired data.
- Every metadata-bearing GET/POST/PUT/conflict reply uses request-start service guards independently from preference confirmation. Local connection work defers only that service's metadata, does not block remote preference polling, and releases through bounded client ownership/status reconciliation.
- Unchanged polling neither resets the slideshow/clock/service timers nor adds content/provider requests. One settings owner pauses/resumes correctly, and legitimate changed fields affect only their required presentation/data owners.
- All existing layout, mobile scaling, weather cache/update-time, bookmark disclosure/fullscreen, calendar, photo, and Settings behaviors remain covered and passing. Cross-engine verification is executed and accurately recorded.
- Settings messages and dedicated documentation describe global settings, the five-second cadence, migration, conflicts, and failure behavior; version and implementation records follow the task workflow.

## Risks And Decisions

- The old `home_settings` record stores retired widget geometry and an incomplete preference schema. A separate current-dashboard singleton avoids destructive migration or accidental revival of the former UI while reusing its revision-checked persistence pattern.
- GET of an absent preference record returns preview defaults without inserting. This allows a browser with valid legacy values to migrate later, until the first migration or explicit save establishes authority. Atomic initialization prevents competing local configurations from overwriting one another.
- Global default timezone is UTC; a migrated/saved timezone replaces it for all browsers. Numeric canonicalization must agree with native control steps so inherited finite fractional values do not block an unrelated global save.
- Preference revisions govern display saves, while integration IDs/location revisions govern their independent configuration. Secret fields are not copied into the preference record or aggregate DTO. Actual browser fullscreen and folder interaction remain session state.
- A fresh server response is authority; local cached revisions do not prevent adoption after database reset. Request-generation guards protect an owned save from older in-flight replies, and stale form revisions protect other browsers' writes.
- Public status synchronization is not proof that revoked upstream access returned. Preserve service access blocks for unchanged source identities, and use guarded controller observation callbacks so older aggregate metadata cannot revert newer status or mutation results.
- The existing full `apply` restarts photos and reconfigures timers, and calendar cannot discover a remote connection through its current `refresh` alone. Change-group application and explicit source adoption are necessary for this goal, not additional polling of provider content every five seconds.
- Independent integration actions can overlap while display preferences save. Reference-counted per-service metadata deferral and mutation-owned callbacks prevent stale metadata races without combining secrets and display options into one save transaction or pausing unrelated preference synchronization. Calendar mutation deadlines bound client ownership, but status reconciliation must handle an uncertain server outcome after timeout.
- The new focused Firefox case introduces a browser-install requirement in development only. Missing executables/system libraries are a verification blocker to report to the user, not a reason to claim cross-browser coverage from shared Chromium storage alone.
