## goal

Make every configured option in the dashboard's Settings global to this installation, with one server-owned configuration shared by all browsers. A successful change made in Firefox must be reflected in Chrome, a fresh browser profile, and other connected clients without repeating setup. Persist the shared configuration in the existing server SQLite database so it survives reloads and server restarts.

Share all display preferences across General, Time, Weather, Calendar, Bookmarks, and Images, including desktop position/overall scale, desktop and mobile view visibility/scales, timezone and time/date formatting, weather units, mobile bookmark mode, fullscreen bookmark hiding, slideshow options, and background appearance. Each browser applies the same saved desktop/mobile profiles to its own viewport and the shared fullscreen-hiding preference to its actual fullscreen state. Unsaved form drafts and temporary folder disclosure/fullscreen interactions remain session state rather than silently becoming saved global options.

Load and apply the server configuration when the page opens, and automatically synchronize successful changes into already open browsers within a short, documented interval. Resume synchronization when a hidden page becomes visible, and refresh known values when Settings opens. Synchronization must update the dashboard while preserving unsaved Settings drafts; a stale form save must not silently overwrite another browser's newer changes. Apply a successful Save preferences update atomically and report success only after the server confirms it.

Reuse the already shared weather location and integration configuration for calendar and Linkwarden. Connection, re-authentication, location selection, and disconnect actions must propagate their public status and resulting view changes to other open browsers as well as survive restart. Keep these actions independent of Save preferences, and keep credentials in their existing encrypted server storage. A browser that starts unconfigured must discover a connection established from another browser without requiring a manual page reload.

Replace browser-local preference authority with server authority. Provide a defined one-time migration for valid existing `dashboard.preferences.v1` values when the global preference record is uninitialized, using atomic initialization so competing browsers adopt one winning record. Established server values always take precedence over stale local values. Use server-defined defaults when no shared or migratable preferences exist, including a consistent timezone default, and validate values consistently with the Settings controls. Any browser-local cache represents the last confirmed shared snapshot, rather than a competing configuration source.

Handle unavailable storage or API failures clearly: failed saves preserve the previous confirmed configuration and the user's draft, and a browser must not claim global persistence when only a local update succeeded. Retain the last usable confirmed snapshot during synchronization failures and retry without creating duplicate settings timers or service refresh owners. Apply only changed configuration so polling does not continually restart the clock, slideshow, animations, weather retrieval, calendar requests, or bookmark loading.

The active display preferences are normalized in `public/dashboard-helpers.js`, loaded from localStorage, and saved synchronously in `public/dashboard.js`; Settings copy currently describes browser-local persistence. Weather location, calendar credentials, and Linkwarden credentials already have server persistence and dedicated APIs, but their browser controllers have separate discovery/refresh behavior. `src/db.js` and `src/app.js` also retain a revision-checked `/api/home/settings` interface for the former widget layout schema. The shared configuration for this task must represent the current photo dashboard's full preference set and integrate with existing service ownership, rather than conflate it with retired widget layouts or duplicate integration credentials.

Completion means changing and saving any Settings option in one browser produces the same saved values and the appropriate active presentation in another browser, both on fresh load and during an open session. Verify every preference category, independent desktop/mobile profiles within the shared record, atomic migration, concurrent/stale saves, draft preservation, hidden-page resumption, failed saves/synchronization, restart persistence, and remote connection/disconnection discovery from initially unconfigured clients. Use isolated browser clients with separate storage to demonstrate sharing through the server rather than same-browser storage events, and retain existing layout, cached-weather, bookmark, calendar, photo, and fullscreen checks. Update Settings messages, README's brief persistence description, and relevant dedicated documentation to explain installation-wide settings and synchronization behavior.
