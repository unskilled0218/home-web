# plan

## scope

Implement the shared weather location, server-owned SQLite weather cache, cached-first loading, current-location display in Settings, and last successful forecast update time defined in `1-goal.md`. Keep display preferences in browser storage and retain the existing location search, forecast presentation, and **Clear results** behavior. The active photo dashboard is `public/index.html` and `public/dashboard.js`; its location is currently browser-local, and `public/dashboard-weather.js` currently owns direct provider requests and hourly refreshes. Use dedicated weather persistence rather than the former widget configuration in `home_settings`.

## Implementation Plan

### 1. Define shared weather data and presentation contracts

- Add `public/weather-data.js` as a DOM-free module usable by both Node and the browser. Move bounded forecast and air-quality normalization from `public/dashboard-weather.js` into it, and expose location validation, normalized snapshot validation, unit conversion, and update-time formatting helpers. Keep browser geocoding and its abortable request helper in `public/dashboard-weather.js`.
- Define a weather snapshot containing `configured`, `location`, monotonically increasing location `revision`, requested `timezone`, normalized `forecast`, `air`, independent `forecastUpdated` and `airUpdated` epoch-millisecond timestamps, independent refresh-error flags, and `refreshing`. Missing successful data and timestamps are `null`. Reject invalid timestamps and malformed cached payloads rather than rendering them.
- Fetch and store canonical Celsius, km/h, and millimeter values. Convert copies of current, hourly, and daily temperatures, wind speeds, precipitation, and unit labels for each browser's applied preferences. Preserve missing values and round converted readings consistently; never mutate the stored canonical snapshot or convert already converted values twice.
- Keep Open-Meteo's timezone-specific daily dates and day/night flags. Store forecast variants by validated, canonicalized IANA timezone rather than relabeling UTC daily aggregates as another timezone. Preserve the existing provider bounds of seven daily rows and at most 192 hourly rows. Air quality remains one location-wide snapshot independent of timezone and units.

### 2. Add bounded, revision-aware SQLite persistence

- Extend `src/db.js` with additive weather tables: a singleton location record with coordinates, bounded label, and revision; a forecast cache keyed by timezone and location revision; and a singleton air-quality cache tied to the location revision. Persist normalized payloads, successful retrieval timestamps, last attempt timestamps, and independent failure state. Preserve existing devices and integration configuration.
- Expose store operations to read location and snapshots, compare-and-save the location using the caller's revision, replace successful forecast or air data, record failures without deleting successful payloads, and enumerate retained forecast variants for startup and recurring retrieval. Use transactions for location changes and cache invalidation. Successful cache writes must match the current location revision.
- Initialize an unconfigured location at revision zero. Saving a different coordinate pair increments the revision and clears old weather data atomically. A label-only change increments the revision and retags usable same-coordinate snapshots atomically. An identical save is idempotent and does not invalidate data or trigger unnecessary retrieval.
- Limit forecast variants to eight total, including a pinned UTC baseline and seven least-recently-used browser timezone variants. Register variants only through the refresh workflow, not ordinary snapshot reads; registration, eviction, and later writes must reject responses for an evicted registration. Keep one latest successful snapshot per retained variant and one air-quality snapshot, with no weather history.
- Treat corrupt forecast or air cache entries as missing data eligible for replacement. A malformed saved location or database failure produces a clear service error rather than silently overwriting configuration. Cover schema creation on an existing database and persistence after closing and reopening the store.

### 3. Build the server weather service and lifecycle

- Add `src/weather.js` with a weather service accepting the store, provider fetch implementation, clock, timer functions, and request deadline. Expose start, snapshot read, revision-checked location save, ensure-fresh scheduling, and asynchronous stop operations. Keep provider URL construction and requests in this server module; use fixed Open-Meteo forecast and air-quality endpoints, not caller-supplied URLs.
- Start retrieval asynchronously for the saved location and all retained timezone variants, always including UTC. Refresh retained variants and air quality hourly without browser activity. Maintain one scheduler and one serialized refresh queue, deduplicated by location revision and timezone; forecast and air requests may run independently within a refresh operation. Browser requests must not create additional recurring provider timers.
- Bound each provider request to ten seconds, reject unsuccessful or malformed provider responses, and bound response size before parsing. Persist each successful part immediately with its server retrieval timestamp. Record each failed part independently while retaining its successful payload and timestamp. Catch request and persistence errors so the periodic service continues retrying and produces no unhandled rejections.
- Make ensure-fresh requests asynchronous and coalesced. Request fresh retrieval only when a variant is missing or its last attempt is at least one hour old; coalesce an existing attempt and preserve hourly retry timing after failures. Registering a missing timezone schedules that variant, while location-wide air quality is fetched only when due. A fresh snapshot returns without another provider call.
- On a successful coordinate change, cancel queued old work, abort in-flight old requests, invalidate generations, and schedule the new location immediately. Check both revision and retained variant registration before every database write. On a rejected location save, keep the existing service state intact. Serialize configuration mutations so concurrent saves cannot interleave invalidation and scheduling.
- Construct the service in `src/server.js`, inject it into `createDashboardServer`, and start it without delaying HTTP readiness or cached responses. Stop timers, cancel queued work, abort and settle active requests before closing SQLite on SIGINT or SIGTERM. Keep `src/app.js` construction side-effect-free so existing test servers do not start real provider requests; absent weather-service injection returns a weather-specific 503 only for weather routes.

### 4. Expose cached-first weather APIs

- Add `GET /api/weather?timezone=<IANA-zone>` to return the saved location and database-backed snapshot immediately, without awaiting provider requests or registering a timezone. Use UTC when omitted. A missing variant returns the current location with no forecast, never another timezone's forecast. Apply existing local-network and Host checks and `no-store` JSON responses.
- Add `PUT /api/weather/location` accepting only `{ location: { latitude, longitude, label }, revision }`. Reject invalid coordinates, labels, revisions, and bodies with 400; reject outdated revisions with 409 and a reload instruction. Return 503 for persistence failure and 200 with the committed location snapshot on success, independently of subsequent provider availability. Apply the existing Origin and bounded JSON-body checks.
- Add `POST /api/weather/refresh` accepting a validated timezone and returning 202 with current scheduling status after ensure-fresh handling. Do not await provider completion or offer a force-refresh flag that bypasses coalescing and cadence limits. Reject unsupported weather-route methods with 405 and invalid timezones with 400.
- Return per-part provider failures as snapshot status, not an HTTP failure that discards usable cached data. Reserve 503 for unavailable service or storage. Keep revision, registration, and scheduler details needed for concurrency internal except the public location revision.

### 5. Replace browser provider refreshes with server snapshot loading

- Refactor `createWeatherController` in `public/dashboard-weather.js` to own server snapshot requests, location mutations, polling, cancellation, and request generations. On initialization, ignore any legacy local location, fetch the saved snapshot for the applied timezone, emit it for rendering, and only then request asynchronous freshness through the refresh endpoint. Start this location discovery even when weather display is disabled so Settings can still show the saved location.
- Poll snapshots every five seconds while the server reports an outstanding refresh or no data following an accepted refresh, then every sixty seconds normally. Use one browser polling timer, pause it while the page is hidden, and resume with a snapshot read followed by ensure-fresh when visible. Stop fast polling after a terminal failure; unavailable APIs retain same-location data and use the normal retry interval. Weather visibility must not stop server retrieval.
- Preserve canonical browser state and derive presented units from applied preferences. Unit changes re-render without provider calls. Timezone changes cancel old requests, load the matching cached variant, then ensure freshness. Appearance-only changes must neither discard weather nor reschedule provider retrieval. Retain the existing pagehide, pageshow, and disposal lifecycle behavior.
- Treat the server response location as authoritative and notify `public/dashboard.js` without recursively calling configure. Reject older location revisions and obsolete request generations. When another browser changes location, the next snapshot updates this browser's location, clears old-location data, and updates Settings without saving or replacing unrelated local preference drafts.
- Change result selection in `public/dashboard.js` to await a revision-checked server save. Disable competing location selections while pending, retain the previous location and weather on failure, and show a weather-location-specific status. On success, apply the committed location and fetch its matching timezone snapshot. A 409 reloads server state and requires explicit reselection rather than silently overwriting another browser's change.
- Keep **Clear results** limited to canceling geocoding and clearing the result list and search status. It must not save or clear the shared location, cancel a location save already accepted, change the search query or draft preferences, or trigger weather retrieval. Browser storage may retain a legacy location field for compatibility, but it must never configure weather or automatically upload that value.

- Update Settings copy and `docs/dashboard.md` to distinguish server-saved location from browser-local display preferences, browser-direct geocoding from server provider retrieval, hourly unattended refreshes, bounded timezone caching, cached-first loading, and the visible update time. ## Acceptance Criteria

- A successfully selected location persists in SQLite, survives restart, appears in a fresh browser, and is visible whenever Settings → Weather opens. Server location overrides any legacy local location.
- Cached current conditions, hourly and daily forecasts, and available AQI render before a delayed provider refresh completes. New successful data replaces the corresponding cached part without clearing other usable data.
- The server retrieves weather at startup, after coordinate changes, and hourly with all browsers closed. Multiple browsers share its schedule and do not multiply provider requests for the same timezone.
- Forecast variants remain bounded to eight and AQI to one current-location snapshot. Daily dates, forecast values, unit labels, hourly timezone formatting, and day/night flags match each browser's applied preferences.
- Failed refreshes preserve last successful values and timestamps, report failure independently by provider part, and retry hourly. Old-location and evicted-variant responses cannot restore obsolete data.
- Weather shows the persisted last successful forecast retrieval time, formatted in the selected dashboard timezone. Cached reloads preserve it; newer forecasts advance it; failed refreshes and air-only updates do not.
- Location-save failure or revision conflict does not falsely select or overwrite a location. **Clear results** preserves location, weather, search query, and unsaved preference drafts.
- Shutdown stops weather work before SQLite closes, and all required syntax, Node, and Chromium checks pass without live weather-provider dependence.

## Risks And Decisions

- The shared location is installation-wide because the dashboard has no user accounts. Revision-checked saves prevent stale browsers from silently replacing another client's newer choice. The server is the source of truth; existing local locations require one explicit selection to establish server configuration.
- Canonical units avoid a cache entry for every unit combination. Timezone variants preserve Open-Meteo daily forecast semantics without introducing custom daily weather aggregation. UTC is always available for unattended baseline retrieval; an evicted browser timezone can briefly have no forecast until its next asynchronous retrieval completes.
- An ensure-fresh request does not guarantee a new provider call for already fresh data. It guarantees server-managed freshness, preserving the hourly cadence and preventing refresh amplification. Initial missing data, new timezone registration, startup, and coordinate changes initiate retrieval immediately.
- Successful retrieval time differs from the provider's observation time. The visible label represents when the server successfully obtained the displayed forecast, as required by the goal. Failed attempts never advance that timestamp.
- Geocoding remains browser-direct, while coordinates for recurring weather retrieval are sent by the server. Document both paths accurately. The existing public provider endpoints and usage terms still apply.
- Cache reads must remain independent of provider promises. Database-write errors must not yield a fresh timestamp for data that was never persisted. Location-save success must not depend on external provider availability.
- The browser suite currently assumes localStorage locations and intercepts browser provider URLs. Updating those fixtures is necessary to avoid false passing results or real external requests. Inject weather services explicitly in Node tests and keep default app construction free of provider side effects.
