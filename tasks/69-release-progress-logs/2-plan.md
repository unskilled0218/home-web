## Scope

Make `bash scripts/release.sh` visibly report ongoing work, especially during dependency installation, application tests, the lengthy Python release suite, production packaging, staging builds, and image runtime checks. Currently `scripts/release-verify.py:47-65` prints a gate start but waits for `DATA.capture()` to finish before showing selected summaries or a failure tail; ordinary shell `run()` also captures output without live progress. Preserve the one-command contract, early/non-bootstrapping ARM64 checks, command limits, supervision, source/plugin identity, immutable runtime gates, credential timing, and publication/retry policy.

This task adds operator-facing console progress, not a dashboard log viewer, a persistent logging service, an arbitrary hook framework, or a raw HTTP/credential debug mode. Do not change application behavior or silently repair task 67's separate cleanup/isolation/coverage findings. Do not merge/archive task 68 automatically; use the current checked-in task 68 implementation as the starting point and create a separate implementation branch for this task.

## Implementation Plan

### 1. Define visible progress and confidentiality boundaries

1. Create a new implementation branch named `69-release-progress-logs`. Keep planning limited to this document; do not modify implementation code until implementation is requested.
2. Enable concise progress by default for the normal release command, with no extra operator command, environment toggle, or verification bypass. Retain `--help`, local-only `--validate`, unsupported-option refusal, and explicit-empty-argument handling without new Docker/network/state effects.
3. Use human-readable, line-oriented records with a trusted phase/gate label, stream identity when appropriate, elapsed seconds, and start/running/completed/failed/interrupted state. Send new progress records to stderr so existing helper stdout remains suitable for JSON, digests, OIDs, status codes, and shell command substitution. Preserve existing public success/failure content unless directly improved for clarity, but route its delivery through the same bounded console boundary as progress; retained shell/Python prints must not bypass backpressure protection.
4. For local verification, display useful sanitized stdout/stderr lines while the child is still running. For authenticated Git, registry, package, Docker-login/build, and image-probe operations, emit fixed application-owned phase/substep messages and elapsed heartbeats only; never enable indiscriminate streaming of their raw responses, commands, environment, curl configuration, Docker auth, or container inspection documents. The user can see ongoing publication work without gaining a secret-bearing debug trace.
5. Emit an elapsed heartbeat every ten seconds during a quiet opted-in operation, independent of child output. Continue scheduling ticks when a child closes stdout/stderr before exiting; do not fall into a single blocking `process.wait()` that suspends heartbeat/deadline handling. State that the command is still running, not that it is healthy or a percentage complete. Stop running-command heartbeats immediately on exit/cancellation; any subsequent cleanup progress must be labelled separately. Preserve the existing final `Publication verified` statement only after all required readbacks succeed.
6. Establish bounded display policy: at most 4 KiB of pending input per logical line, 64 KiB of queued console records per invocation, an 8 KiB sanitized diagnostic tail per gate, and 1 MiB of displayed child-log content per local gate, separate from the existing raw capture limits. Drop an overlong input record before displaying any of it; report suppression with a fixed message and suppress further text from that stream until EOF because a sensitive-region marker may have been lost. After the display budget is reached, suppress further live child text but continue stateful sanitation and keep bounded heartbeat/final status records. Any replayed sanitized tail counts toward the same child-log display budget; quota exhaustion permits only fixed omission/status messages. Display truncation must never disable raw-output overflow checks or turn an unsuccessful gate into success.

### 2. Extend bounded capture without changing command results

1. Extend `scripts/release-data.py`'s existing selector-based `capture()` with an internal optional progress observer receiving stdout/stderr data and elapsed-time ticks. Defaults remain silent. Keep the same raw byte buffers, return shape, stdout/stderr/body/header limits, absolute command deadline, exit status, `CommandFailed`/`Refusal` behavior, stdin handling, and owned-process cleanup. Never send body/header/auth/input data to an observer.
2. Keep observer policy outside generic capture. Add a small fixed-purpose `scripts/release_progress.py` if needed to own bounded decoding, sanitization, display quotas, heartbeats, and the console sink; do not expose configurable callbacks or executable hooks through release settings or environment variables. Reuse the helper from the verifier and selected CLI actions rather than duplicating logging policy in Bash and Python.
3. Decode incrementally across read boundaries; retain incomplete UTF-8 and incomplete logical lines within the stated bounds. Give each observed stdout/stderr stream one sanitizer state from its first byte through EOF, owned by the gate's progress session rather than individual display calls. Treat carriage returns as bounded record boundaries and remove terminal control/ANSI escape sequences so captured output cannot rewrite prior status or inject terminal controls. At EOF, process a final safe partial line once; if it is inside a sensitive or uncertain region, omit it. Do not echo an incomplete fragment that might later prove to be a sensitive record.
4. Sanitize before display, not after chunks have already been printed. Redact known forwarded proxy credentials/URL userinfo and their decoded forms, common authorization/token/password/secret assignments, and known sensitive sentinel values available to the caller without reading live credentials. Suppress environment/configuration dumps and PEM private-key blocks rather than guessing that each line is safe. Maintain sensitive-region state across records until a recognized safe terminator; dumps without a reliably recognized terminator remain suppressed through EOF. Oversized records, malformed decoding, or uncertain sensitive-region boundaries switch the affected stream to fixed-message-only suppression until EOF. Neither queue drops nor the display quota resets this state or stops sanitation of subsequent captured bytes. Do not read the publishing token merely to prepare a local-log redactor, or claim arbitrary executable output can be made universally secret-free. Gate children must continue receiving only their existing approved environment.
5. Replace the raw concatenated stdout/stderr suffix diagnostic with the bounded tail of already-sanitized, stream-labelled records produced by that same progress session. Retain the tail before console queueing so queue drops cannot trigger raw replay; preserve per-stream state while recording safe records in observer-arrival order without claiming exact ordering between concurrent streams. Never initialize a fresh sanitizer on an arbitrary raw suffix or reconstruct context from the last 8 KiB. If state or the sanitized tail is unavailable, emit a fixed omission message and gate/status only. Keep raw capture buffers byte-exact and private for their existing evidence consumers, separate from the sanitized tail. Derive displayed skip/final summaries from already-sanitized records or strictly parsed numeric fields, never a parallel raw-text replay. Preserve useful safe failure context without replaying the full log twice or bypassing display quotas.
6. Ensure a slow, closed, or unread output destination cannot block pipe draining, deadline checks, cancellation, final failure handling, or lock release. Choose a supervisor-owned console forwarding boundary for normal release invocations: capture the top-level Bash worker's human-facing stdout/stderr into continuously drained private channels and deliver them through one bounded console sink; nested helper stdout consumed by command substitution or files remains byte-exact and internal. Route the supervisor's own phase/exception/cleanup diagnostics through that same sink, including error paths before the worker starts and after it exits. Keep drainage active during process teardown, daemon cleanup, and auth disposal, not only while the main worker is running. Preserve the content and original stdout/stderr destination of retained public output; new progress remains stderr. Do not indiscriminately turn captured authenticated command output into forwarded human output. Standalone gate/progress integrations must use the same bounded sink primitive when no outer supervisor is present.
7. Add an explicit internal human-progress action/wrapper only for selected long-running shell commands if necessary, preserving the ordinary `run`/`command` machine-data behavior. It must support fixed labels and heartbeat-only policy for authenticated operations, preserve captured output files, and return the same exit categories required by `attempt()` and lost-response reconciliation. Do not add logging to every evidence-reading command globally.
8. Bound console delivery separately from execution: never synchronously block the capture/supervisor control loop, use `tee`, or change inherited shared stdout/stderr descriptor flags in ancestor processes. Drop/suppress queued console records when the invocation's 64 KiB queue is full; disable delivery on a closed sink without changing the command result or publication policy. Allow at most two seconds total console-sink shutdown grace per invocation after execution/resource cleanup, never two seconds per record. Then discard undeliverable messages and terminate/reap any owned sink worker without retaining the release lock for console delivery. If no message can be delivered, return the already-determined release status without attempting a blocking fallback write to another console descriptor. Missing logs do not grant success or authorize new writes. Preserve sanitized ownership evidence under the existing cleanup-failure policy even if its announcement cannot be displayed.
9. Inventory and connect every normal-release human-output route: shell phase `printf`, `stop()`, ERR/INT/TERM handling, verifier start/summary/exception prints, data-helper failures, and supervisor cleanup warnings. No direct write from the supervisor or an orphaned worker may retain an inherited external console destination outside the chosen boundary. Keep CLI-only paths and machine-protocol helper execution from gaining a log worker, state file, or extra external effects merely to support normal-release forwarding. Do not pass the live release lock or credential contents to a separate sink process, or let sink failure skip process/resource cleanup or auth disposal. These changes address review F1 without claiming to repair task 67's unrelated daemon-cleanup sequencing defect.

## Acceptance Criteria

- Normal release invocation shows local verification logs while children are running and fixed phase/substep progress for publication/runtime work; quiet opted-in operations report elapsed activity every ten seconds.
- Logs do not contaminate helper stdout, JSON, OIDs, digests, HTTP status output, or captured command files. Existing command results, failure categories, gate ordering, and readback-based publication authority remain intact.
- Raw authenticated output, token/config/environment dumps, private keys, and known fixture credentials never appear in new live output or failure tails. One per-stream sanitizer tracks sensitive regions through suppression and EOF; failure tails contain only already-sanitized records or a fixed omission message, never reprocessed raw suffixes. Local records are bounded and safe for non-TTY capture without terminal rewriting.
- Child output, the invocation-wide console queue, sanitized diagnostic tails, emitted local-log volume, command execution, and sink shutdown are independently bounded. All normal-release phases, retained summaries, shell/Python exception/trap output, and supervisor cleanup diagnostics share the bounded console boundary. Slow or closed stdout/stderr consumers cannot stall cancellation, prevent lock release, extend command deadlines indefinitely, or turn a failed check into success; final sink shutdown adds at most two seconds and never uses a blocking fallback.
- Early ARM64 refusal, mandatory verification once, no bootstrap, immutable both-platform runtime checks, retry no-republication guarantees, source/plugin identity, and existing cleanup/credential boundaries are preserved.
- Persistent tests prove pre-exit visibility, heartbeats after pipe EOF and cessation on child exit, stateful sanitation through failure/suppression/EOF, display suppression versus raw overflow, exact machine output, and top-level slow/broken-console lock release using owned fixtures, without production bypasses or live publication.
- Version mirrors and relevant documentation are synchronized; planning itself changes no implementation code.

## Risks And Decisions

- **Local logs versus authenticated diagnostics:** useful pre-credential test output may be streamed through sanitation, but authenticated external responses and build output remain captured. Fixed phases and elapsed heartbeats provide visibility there without exposing a general credential-bearing debug channel.
- **Sanitization lifecycle (review F2):** test code and tool output are not a universal trusted text format. Never promise detection of every deliberately encoded secret. Give sensitive-record decisions one per-stream owner from first byte through EOF; retain an independently bounded sanitized tail instead of reparsing raw suffixes. An overlong/malformed or uncertain sensitive record suppresses that stream through EOF, and display suppression never resets state. Prefer a fixed omission message over unclassified output.
- **Console ownership (review F1):** a nonblocking observer alone is insufficient while shell phases and Python exception/cleanup handlers still inherit the external console. The normal-release supervisor owns continuously drained worker-output channels and one bounded console sink through startup, execution, cleanup, and final diagnostics. Preserve internal machine stdout, prohibit shared ancestor descriptor-flag changes, drop undeliverable records, and cap final sink shutdown at two seconds without fallback writes or lock retention. Do not replace concurrent capture with `tee` or an unbounded thread/queue.
- **Progress is not authority:** heartbeat activity and command completion are informational. They never authorize a publish, retry, rollback, association change, gate skip, or runtime certification. Keep partial-state warnings and final readbacks authoritative.
- **Existing task state:** task 69 begins on top of the checked-in task 68 implementation. Do not infer authorization to merge/archive task 68 or fix all inherited task 67 warnings. Any new helper affecting release execution must participate in script identity, so historical publication ownership cannot be silently adopted after changes.
