## Scope

Make `bash scripts/release.sh` visibly report ongoing work, especially during dependency installation, application tests, the lengthy Python release suite, production packaging, staging builds, and image runtime checks. Currently `scripts/release-verify.py:47-65` prints a gate start but waits for `DATA.capture()` to finish before showing selected summaries or a failure tail; ordinary shell `run()` also captures output without live progress. Preserve the one-command contract, early/non-bootstrapping ARM64 checks, command limits, supervision, source/plugin identity, immutable runtime gates, credential timing, and publication/retry policy.

This task adds operator-facing console progress, not a dashboard log viewer, a persistent logging service, an arbitrary hook framework, or a raw HTTP/credential debug mode. Do not change application behavior or silently repair task 67's separate cleanup/isolation/coverage findings. Do not merge/archive task 68 automatically; use the current checked-in task 68 implementation as the starting point and create a separate implementation branch for this task.

## Implementation Plan

### 1. Define visible progress and confidentiality boundaries

1. Create a new implementation branch named `69-release-progress-logs`. Keep planning limited to this document; do not modify implementation code until implementation is requested.
2. Enable concise progress by default for the normal release command, with no extra operator command, environment toggle, or verification bypass. Retain `--help`, local-only `--validate`, unsupported-option refusal, and explicit-empty-argument handling without new Docker/network/state effects.
3. Use human-readable, line-oriented records with a trusted phase/gate label, stream identity when appropriate, elapsed seconds, and start/running/completed/failed/interrupted state. Send new progress records to stderr so existing helper stdout remains suitable for JSON, digests, OIDs, status codes, and shell command substitution. Preserve existing public success/failure output unless directly improved for clarity.
4. For local verification, display useful sanitized stdout/stderr lines while the child is still running. For authenticated Git, registry, package, Docker-login/build, and image-probe operations, emit fixed application-owned phase/substep messages and elapsed heartbeats only; never enable indiscriminate streaming of their raw responses, commands, environment, curl configuration, Docker auth, or container inspection documents. The user can see ongoing publication work without gaining a secret-bearing debug trace.
5. Emit an elapsed heartbeat every ten seconds during a quiet opted-in operation, independent of child output. State that the command is still running, not that it is healthy or a percentage complete. Stop heartbeats immediately on completion/cancellation. Preserve the existing final `Publication verified` statement only after all required readbacks succeed.
6. Establish bounded display policy: at most 4 KiB of pending input per logical line, 64 KiB of queued display records, and 1 MiB of displayed child-log content per local gate, separate from the existing raw capture limits. Drop an overlong input record before displaying any of it; report suppression with a fixed message. After the display budget is reached, suppress further child text but keep bounded heartbeat/final status records. Display truncation must never disable raw-output overflow checks or turn an unsuccessful gate into success.

### 2. Extend bounded capture without changing command results

1. Extend `scripts/release-data.py`'s existing selector-based `capture()` with an internal optional progress observer receiving stdout/stderr data and elapsed-time ticks. Defaults remain silent. Keep the same raw byte buffers, return shape, stdout/stderr/body/header limits, absolute command deadline, exit status, `CommandFailed`/`Refusal` behavior, stdin handling, and owned-process cleanup. Never send body/header/auth/input data to an observer.
2. Keep observer policy outside generic capture. Add a small fixed-purpose `scripts/release_progress.py` if needed to own bounded decoding, sanitization, display quotas, heartbeats, and the console sink; do not expose configurable callbacks or executable hooks through release settings or environment variables. Reuse the helper from the verifier and selected CLI actions rather than duplicating logging policy in Bash and Python.
3. Decode incrementally across read boundaries; retain incomplete UTF-8 and incomplete logical lines within the stated bounds. Treat carriage returns as bounded record boundaries and remove terminal control/ANSI escape sequences so captured output cannot rewrite prior status or inject terminal controls. At EOF, process the final safe partial line once. Do not echo an incomplete fragment that might later prove to be a sensitive record.
4. Sanitize before display, not after chunks have already been printed. Redact known forwarded proxy credentials/URL userinfo and their decoded forms, common authorization/token/password/secret assignments, and known sensitive sentinel values available to the caller without reading live credentials. Suppress environment/configuration dumps and PEM private-key blocks rather than guessing that each line is safe. Do not read the publishing token merely to prepare a local-log redactor, or claim arbitrary executable output can be made universally secret-free. Gate children must continue receiving only their existing approved environment.
5. Route both live local output and the existing nonzero failure tail through the same sanitation policy. Do not retain a raw fallback diagnostic when parsing/redaction fails. On malformed, oversized, or unsupported diagnostic text, show a fixed sanitized omission message with the gate/status instead. Preserve useful safe failure context and suite skip/final summaries without replaying the full log twice.
6. Ensure a slow, closed, or unread output destination cannot block pipe draining, deadline checks, or cancellation. Use a bounded sink with independently bounded shutdown rather than synchronous unbounded `print()` calls inside the selector loop, `tee`, or a shell pipeline. Do not change inherited shared stdout/stderr descriptor flags in ancestor processes. When the display queue fills, drop/suppress display records; when the sink closes, stop display attempts without changing the subprocess result or publishing decision. Never wait indefinitely to flush logs at exit or hold the release lock for a stalled console.
7. Add an explicit internal human-progress action/wrapper only for selected long-running shell commands if necessary, preserving the ordinary `run`/`command` machine-data behavior. It must support fixed labels and heartbeat-only policy for authenticated operations, preserve captured output files, and return the same exit categories required by `attempt()` and lost-response reconciliation. Do not add logging to every evidence-reading command globally.

Avoid timestamps or log prefixes on machine-readable stdout.
4. Provide heartbeat-only progress for the potentially 7,200-second staging build and other selected long-running authenticated commands without dumping raw build/login/Git/API output. ### 4. Prove timeliness, secrecy, and failure behavior

1. Extend `test/release-template/test_verification.py` and add focused progress-helper tests as needed. Use real owned subprocesses that flush one safe line, wait on a test-controlled handshake, then emit stderr and finish. Assert the parent receives the first displayed line before releasing the child to exit, not merely that text exists in the final collected result. 2. Test quiet heartbeat timing with an injected monotonic clock at the helper boundary and at least one real quiet-process integration case. Assert heartbeats cease after exit/cancellation and final output distinguishes success, failure, timeout, and interruption. Keep production intervals fixed; test injection is an internal seam, not a release environment bypass.
3. Require no sensitive fixture text or terminal-control bytes in live records or failure tails. Do not use real tokens, private files, or production services.
4. Verify raw return buffers and extra body/header streams remain byte-exact and are never copied to the progress sink. Existing silent `capture()`/`command()` callers must remain silent.
5. Use an owned blocked output pipe, a slow reader, and a closed reader to prove bounded queue memory, uninterrupted simultaneous child-pipe draining, command timeout, SIGINT/SIGTERM, descendant cleanup, and bounded sink shutdown. Check an unrelated process sentinel remains alive. Do not change cleanup budgets or globally ignore output errors to make a test pass.
6. Extend fake publication ports to simulate safe phase/progress boundaries without recursively launching suites. 7. Add byte-exact helper CLI regressions for JSON/settings, OID/digest/status output, and `run` output files with progress enabled at surrounding orchestration boundaries. ## Acceptance Criteria

- Normal release invocation shows local verification logs while children are running and fixed phase/substep progress for publication/runtime work; quiet opted-in operations report elapsed activity every ten seconds.
- Logs do not contaminate helper stdout, JSON, OIDs, digests, HTTP status output, or captured command files. Existing command results, failure categories, gate ordering, and readback-based publication authority remain intact.
- Raw authenticated output, token/config/environment dumps, private keys, and known fixture credentials never appear in new live output or failure tails. Local records are bounded, sanitized across chunk boundaries, and safe for non-TTY capture without terminal rewriting.
- Child output, display queues, emitted local-log volume, command execution, and sink shutdown are independently bounded. Slow or closed log consumers cannot stall cancellation, extend command deadlines indefinitely, or turn a failed check into success.
- Early ARM64 refusal, mandatory verification once, no bootstrap, immutable both-platform runtime checks, retry no-republication guarantees, source/plugin identity, and existing cleanup/credential boundaries are preserved.
- Persistent tests prove pre-exit visibility, heartbeat lifecycle, sanitation, suppression versus overflow, exact machine output, and slow/broken-sink behavior using owned fixtures, without production bypasses or live publication.
- Version mirrors and relevant documentation are synchronized; planning itself changes no implementation code.

## Risks And Decisions

- **Local logs versus authenticated diagnostics:** useful pre-credential test output may be streamed through sanitation, but authenticated external responses and build output remain captured. Fixed phases and elapsed heartbeats provide visibility there without exposing a general credential-bearing debug channel.
- **Sanitization limits:** test code and tool output are not a universal trusted text format. Never promise detection of every deliberately encoded secret. Avoid forwarding publication credentials, suppress known sensitive record classes, test split-record leaks, and use fixed messages when safe display cannot be established.
- **Console backpressure:** a naive observer calling blocking `print()` from `capture()` would defeat its deadlines. Bound the sink independently and prefer dropping display records over blocking mandatory supervision; do not replace concurrent capture with `tee` or an unbounded thread/queue.
- **Progress is not authority:** heartbeat activity and command completion are informational. They never authorize a publish, retry, rollback, association change, gate skip, or runtime certification. Keep partial-state warnings and final readbacks authoritative.
- **Existing task state:** task 69 begins on top of the checked-in task 68 implementation. Do not infer authorization to merge/archive task 68 or fix all inherited task 67 warnings. Any new helper affecting release execution must participate in script identity, so historical publication ownership cannot be silently adopted after changes.
