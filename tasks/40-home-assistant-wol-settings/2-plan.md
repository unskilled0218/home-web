# plan

## scope

Implement `1-goal.md` by adding Home Assistant connection settings and Wake-on-LAN device management inside the current Settings dialog. Reuse existing APIs, encrypted credentials, and SQLite device records. Do not add device readings, entity controls, wake buttons, automatic wake actions, dashboard widgets, new preference keys, database migrations, or runtime dependencies.

## Implementation Plan

### 1. Add accessible settings panels

- Update `public/index.html` with Home Assistant and Wake-on-LAN tabs after Bookmarks and before Images. Add matching panels, unique IDs, `aria-controls`, `aria-labelledby`, initial hidden state, and roving tab indices. `createSettingsTabs` discovers tabs from markup and should need no category-specific changes.
- Add a separate Home Assistant connection form with instance URL, password-type access token, Connect/update and Disconnect buttons, saved public connection status, and a `role="status"` action message. Describe installation-wide persistence, blank-token reuse, dedicated Home Assistant users, trusted-LAN access, and server-side private CA setup.
- Add a saved-device list and one separate Wake-on-LAN create/edit form with name, MAC address, broadcast address, optional IPv4 address, and optional group. Provide Add device, Save device, Cancel edit, Edit, and Delete actions with explicit `type="button"` where appropriate. Do not associate either integration form with `preferences`.
- Match backend constraints: name and group are at most 80 characters; name, MAC, and broadcast are required. Explain directed subnet broadcast addresses with `192.168.1.255` as an example. Treat server validation as authoritative and show its errors without clearing drafts.
- Extend `public/dashboard.css` only where required for the list and actions. Use wrapping or stacked device rows rather than a wide table; keep actions and forms reachable in the existing panel scroller at 390px and narrower widths.

### 2. Implement focused configuration controllers

- Add `public/dashboard-home-assistant.js` and `public/dashboard-wol.js` with injected fetch and state-change callbacks, following the existing controller testing pattern. Separate confirmed server snapshots, request errors, and pending mutations from DOM form drafts. Provide refresh, mutation, getState, and dispose operations; do not put tokens in controller snapshots or browser storage.
- Use same-origin requests, JSON request headers, bounded request deadlines, safe public error messages, and explicit HTTP status checks. Treat 204 DELETE responses as successful without parsing JSON. Validate expected response shapes before accepting snapshots. Never render server strings with `innerHTML` or expose raw request bodies through error messages.
- Guard each controller against duplicate mutations and stale reads. Starting a mutation invalidates or suppresses earlier refresh responses; a post-mutation refresh must not let an earlier read undo confirmed local success. Clear pending state in `finally`, retain the last confirmed snapshot on refresh failure, and cancel reads on disposal. Do not automatically retry mutations, including requests that time out after the server may have committed them; refresh public state to reconcile instead.
- Home Assistant uses GET and PUT `/api/home-assistant` and DELETE `/api/home-assistant`. Consume only `homeAssistant` status from PUT; do not display or request its device list. Use `configured`, `accessTokenPresent`, `encryptionReady`, `needsReauthentication`, and `baseUrl` to distinguish unconfigured, connected, encryption-unavailable, and re-authentication states. An unavailable GET must not be represented as a disconnect.
- Submit `{ url, accessToken }`; allow an empty token only when a readable saved token exists for the unchanged normalized origin. Require a new token for first setup, changed origins, or re-authentication. Backend normalization and encrypted-token reuse remain authoritative. Preserve the last working status on failed PUT. Confirm Disconnect because it deletes credentials.
- Wake-on-LAN uses GET and POST `/api/devices`, PUT `/api/devices/<id>`, and DELETE `/api/devices/<id>`. Submit all five supported configuration fields and accept canonical server values, including normalized MAC addresses and nullable IP addresses. Use stable numeric IDs, not list positions. Update the confirmed list only after successful mutation responses and reconcile with a fresh GET.
- On 404 for an edited or deleted device, explain that another client removed it, refresh the list, and preserve the user's draft without silently creating a new device. Show duplicate MAC 409 errors inline. Keep wake timestamps read-only and omit them from mutation payloads.

### 3. Wire forms, drafts, and scoped synchronization

- Import the controllers in `public/dashboard.js` and bind rendering and events through a focused new `public/dashboard-integration-settings.js` module. Keep the entrypoint responsible for dialog and page lifecycle; keep integration form handling and safe list construction in the new module.
- Populate a clean Home Assistant form from the latest confirmed status; track dirty input independently of global preference drafts. Always update public connection status and action availability without replacing dirty URL or token fields. Clear the submitted token and reset the clean baseline after a confirmed successful connect/update; clear credentials after confirmed disconnect. Clear unsent token input when the dialog closes. Failed submissions keep drafts while the dialog remains open.
- Use a single Wake-on-LAN editor with an explicit create/edit mode and dirty baseline. Selecting Edit fills the confirmed device and moves focus to the form; Cancel returns to create mode. Refreshes update list rows without destroying the active editor, dirty fields, focus, or validation messages. If a remote update changes the edited device, show that saved values changed and let the user cancel/reload or explicitly submit their draft; do not overwrite it during polling.
- Confirm Delete with the device name and state that its saved wake audit records will also be removed. Cancellation sends no DELETE. Successful deletion removes the row, returns an editor for that device to create mode, and restores focus to a sensible surviving control. Render names and addresses with `textContent`.
- Add one integration-only refresh scheduler in `dashboard-integration-settings.js` using `SETTINGS_POLL_MS` from `public/dashboard-settings-sync.js`. It refreshes both controllers concurrently when Settings opens and every five seconds while the dialog is open and the document is visible. Stop it on close, hidden state, and non-persisted page exit; refresh immediately on reopening, visible resumption, and persisted page restoration. Coalesce overlapping refreshes and avoid accumulating timers or listeners.
- Keep the existing shared-preferences/weather/calendar/Linkwarden scheduler unchanged. These new configuration screens have no active dashboard presentation outside Settings, so their dedicated reads need not run when Settings is closed. Do not enlarge `/api/dashboard/settings` with an unbounded device list or couple the new API failures to preference synchronization. One new scheduler owns both integration reads, rather than creating separate polling owners per tab.
- Refresh after successful integration mutations and reconcile independently after uncertain mutation outcomes. A failed Home Assistant read must not stop Wake-on-LAN refreshes, and vice versa. Saving preferences must neither submit integration drafts nor overwrite them; pending integration mutations must not disable unrelated preference saves. Keep Settings open after integration actions so success or failure remains visible.

## Acceptance Criteria

- Settings contains eight accessible tabs; both new forms work on desktop and mobile without changing existing dashboard presentation.
- Home Assistant supports shared connection setup/update/disconnect with backend token rules and encryption intact. Failed reconnects preserve the prior connection, and no saved token is redisplayed or cached in the browser.
- Wake-on-LAN supports saved-device list/create/edit/delete with canonical server values, duplicate MAC and missing-device feedback, optional fields, and confirmed deletion. No UI action sends wake packets or controls Home Assistant entities.
- Existing server data survives the addition of the screens. Ordinary configuration reads and edits preserve wake history; explicit device deletion retains the existing cascading audit deletion behavior with a clear warning.
- Another browser sees confirmed changes within the next five-second refresh while Settings is visible, and immediately after opening or resuming it. Dirty drafts remain intact; closed/hidden Settings does not keep its integration loop running.
- Network, validation, timeout, and refresh failures remain distinct from confirmed success; stale reads cannot undo newer mutation state. Unrelated preference saving and synchronization continue to work.
- Syntax, unit/API, and browser checks pass, including restart persistence, mobile layout, keyboard access, security assertions, and existing dashboard regressions.

## Risks And Decisions

- The goal's preservation requirement applies to introducing settings and ordinary reads/edits. `src/db.js` already uses `ON DELETE CASCADE` for wake audits. Retain this explicit deletion contract, warn before deletion, and test it; retaining orphan audit history would require a separate schema/product decision.
- Neither Home Assistant configuration nor Wake-on-LAN CRUD has revision-checked writes. Do not claim conflict rejection or silently retrofit a new persistence protocol. Refreshes preserve drafts and disclose remote changes; explicit saves retain existing last-successful-write semantics. Document this limitation where concurrency is described.
- Home Assistant PUT validates connectivity and currently returns device/control data as well as status. Ignore those fields in the settings controller and avoid additional `/api/home-assistant/devices` polling. Do not broaden this task into redesigning that API.
- Integration refreshes have a single dialog-scoped owner separate from existing active-dashboard synchronization. This avoids adding an unbounded device payload to the bounded shared snapshot and keeps integration failures isolated without changing backend APIs.
- A request timeout does not prove a mutation failed on the server. Never retry it automatically or claim rollback; reconcile through subsequent reads and retain the user's draft until the outcome is clear.
